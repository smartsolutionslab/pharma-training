# pharma-training

Generated by [Software Fabric](https://github.com/smartsolutionslab/software-fabric). Every choice behind this project is recorded in `fabric.yaml` and explained in `docs/adr/`.

## First steps

- Connect the model, an Azure OpenAI resource in the EU: see [Connect the model (Azure OpenAI, EU)](#connect-the-model-azure-openai-eu). The application starts without it.
- For the evals workflow, add the repository secret `AZURE_OPENAI_API_KEY` and the repository variable `AZURE_OPENAI_ENDPOINT`, both for the same EU resource the application uses. Set the repository variable `EVALS_SCHEDULED` to `true` to run the evals weekly; they are off by default, and every run costs money.

- Create the frontend's lockfile and commit it: `cd web && pnpm install`, then commit `web/pnpm-lock.yaml`. CI installs with `--frozen-lockfile` and fails until it is there.

## Connect the model (Azure OpenAI, EU)

The project's AI actions (in MVP 1, drafting a course's questions and checking its content for the editorial team) call a model deployed in your own Azure OpenAI resource. Content sent to it is health-sector training material, so it stays in the EU (DSGVO; [ADR 0001](docs/adr/0001-azure-openai-optional-and-in-the-eu.md)):

1. Create the Azure OpenAI resource in an EU region, such as Sweden Central, Germany West Central, France Central or West Europe.
2. Deploy the model with the deployment type **Data Zone Standard (EU)** or regional **Standard**, never **Global Standard**: a global deployment may process requests in any Azure region.
3. Give the AppHost the resource's endpoint and key, which stay out of the repository:

   ```bash
   dotnet user-secrets set Parameters:azure-openai-endpoint https://<resource>.openai.azure.com --project src/AppHost
   dotnet user-secrets set Parameters:azure-openai-api-key <key> --project src/AppHost
   dotnet user-secrets set Parameters:azure-openai-deployment <deployment> --project src/AppHost
   ```

   The deployment is optional: it defaults to `gpt-5-mini`, and whatever it is, it must name a deployment in that resource.

In a deployment, set the same three parameters in the deployment's secret store; never in `appsettings*.json` or a commit.

Without an endpoint and key the application still starts, and everything but the AI actions works: a request that needs the model answers `503` problem details with the code `model-not-configured`. The tests never need them.

The evals workflow (`.github/workflows/evals.yml`) reads the repository secret `AZURE_OPENAI_API_KEY` and the repository variable `AZURE_OPENAI_ENDPOINT`; point them at the same EU resource.

The client also runs against an OpenAI-compatible endpoint that already ends in `/v1`: set `azure-openai-endpoint` to `https://api.openai.com/v1`, `azure-openai-api-key` to an OpenAI key and `azure-openai-deployment` to a model name. OpenAI's own API is not bound to the EU, so use it only with content that may leave the EU, never with the project's real training content.

## Run locally

You need:

- The .NET SDK 11.0.100, or a later feature band of 11.0 (`global.json`).
- Docker, installed and running: the AppHost starts the project's database and services in containers, and the integration tests do too.
- Node.js 22 and pnpm 10, the major `web/package.json`'s `packageManager` pins (`corepack enable` provides it): the AppHost's `web` resource runs `pnpm` and does not start without both on `PATH`.

Then start the AppHost, which starts everything else:

```bash
dotnet run --project src/AppHost
```

Or, with the [Aspire CLI](https://aspire.dev), `aspire run`, which finds the AppHost through `aspire.config.json`. `aspire doctor` checks the prerequisites above when something does not start.

### Blob storage

The AppHost runs Azurite, the Azure Storage emulator, as the resource `storage`, with a container per module (`<module>-blobs`, named after the module); each service reads only its own, as the connection string `blobs`, and signs short-lived upload and read URLs for it with the emulator's account key (`IBlobUrls`, docs/adr/0002). The web app's origin, `http://localhost:5173`, may `PUT` and `GET` with those URLs straight from the browser: the AppHost sets that CORS rule on the emulator when it starts. Signing in a deployed account, where Aspire disables the account key, is a separate decision (keyless signing).

### Local users

Keycloak imports these from `src/AppHost/realms/realm.json`, development only. Each one's password is its username.

- `developer`: the realm role `manager`, which each module's sample policy `<module>.manage` requires.
- `visitor`: no role.
- `editor`: the realm role `editor`, the platform's editors (the Redaktion), which `editorial.edit` requires.
- `owner`, `employee-a`, `employee-b`: no realm role; their pharmacy roles (owner, employee) come from the Organisation module, not from Keycloak.

Keycloak imports the realm only when it does not exist yet, and keeps it in a data volume. After `realm.json` gains a role or a user, an existing local Keycloak keeps the old realm: stop the AppHost, find the volume with `docker volume ls` (its name contains `keycloak`), remove it with `docker volume rm <name>`, and start the AppHost again.

## Test

```bash
dotnet test --project tests/Architecture.Tests/Architecture.Tests.csproj
```

`dotnet test --project` exists only on Microsoft.Testing.Platform, which `global.json`'s `"test": { "runner": "Microsoft.Testing.Platform" }` selects. Keep that section when a tool rewrites `global.json`: without it `dotnet test --project` fails with `MSB1001: Unknown switch`. `bash .github/scripts/check-test-runner.sh` names the file instead, and `.github/scripts/test.sh` runs it before the tests; the architecture rule `GlobalJsonSelectsTheTestingPlatform` does the same where the tests run without `dotnet test` (an IDE, or `dotnet run --project <test project>`).

## Evals

`tests/Evals` scores the project's LLM use cases with the project's own model, judged by that model: relevance for every example, groundedness for those with context, and the project's own checks. Each metric's mean over a use case's examples must reach `settings.backend.llm.extras.evals.threshold` in `fabric.yaml`. A run calls the real model and costs money, so the regular tests never run it; `.github/workflows/evals.yml` does, by hand or weekly when the repository variable `EVALS_SCHEDULED` is `true`, and uploads the report.

```bash
dotnet test --project tests/Evals/Evals.csproj
dotnet tool restore && dotnet aieval report --path TestResults/evals --output TestResults/evals/report.html
```
