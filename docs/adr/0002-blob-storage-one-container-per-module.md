# 0002: Blob storage, one container per module

**Status:** Accepted

## Context

- Issue #3 asks for blob storage with short-lived upload and read URLs: course material (handouts, media) is uploaded by the browser and read back by it, without streaming files through a service host.
- The topology is services: every module runs in its own host with its own database (AGENTS.md, "Topology: services"), and modules never reach into each other's storage. A storage account shared by all modules needs a rule for which service may sign for what.
- The developer chose option (c) on #3: one container per module, and each service signs only for its own container. Signing uses the storage account's key, which the local emulator (Azurite) has; signing without a key (a user delegation key under a managed identity) is a separate decision.
- Aspire's storage integration (`Aspire.Hosting.Azure.Storage` 13.6.5) runs Azurite and creates containers, but has no CORS setting, and a browser cannot use a signed URL on another origin without one.

## Decision

- **One storage account, a container per module.** `src/AppHost/AppHost.cs` adds the account `storage`, run on Azurite with a data volume, and in its loop over the services a container `<module>-blobs` named after the module. Each service reads its own container, and only its own, as the connection string `blobs` (the account's connection string with `ContainerName=<module>`). `AppHostBlobContainersTests` holds the model to it.
- **A module takes `IBlobUrls`** (`src/BuildingBlocks/Storage`), registered for every module by `AddModuleInfrastructure` (`AddModuleBlobStorage`). It has no container parameter: a service signs for the container its configuration names and no other. `BlobName` (relative, at most 1024 characters, no empty, `.` or `..` segment) and `BlobUrlLifetime` (more than zero, at most 15 minutes) guard what is signed. No module names the Azure Storage SDK; `BlobStorageSdkStaysInBuildingBlocks` fails the build otherwise.
- **The URLs are service SAS on one blob, signed with the account key** (`AzureBlobUrls`, `sr=b`): an upload URL has `Create` alone (`sp=c`: it creates its blob, and cannot read, overwrite or delete it, or touch another; what else `Create` allows on that one blob is under Consequences), a read URL `Read` alone (`sp=r`). Both expire at most 15 minutes after signing, rounded down to the second, and carry no start time (`st`), so a clock behind the storage service's never makes a fresh URL fail. Where the blob endpoint is https, both are signed for https only (`spr=https`), so a signature never works over plain http; the emulator's http endpoint gets no protocol, which it would otherwise refuse. `BlobStorageTests` sends each kind to Azurite and checks what it may and may not do.
- **A module reads what was uploaded through `IStoredBlobs`** (`AzureStoredBlobs`, registered by `AddModuleBlobStorage` beside `IBlobUrls`, with no container parameter either): `FindAsync(BlobName)` answers the blob's content type, length, whether it is a block blob, its ETag (the quoted header value), whether Copy Blob created it (its copy source or copy id is set; not its copy status, which a blob put directly reports too) and the Content-Disposition and Content-Encoding its uploader set (a blank one is none), or none when nothing lies under the name; `ReadStartAsync(StoredBlob, count)` answers the first `count` bytes of the blob found, by a ranged download, or all of a shorter blob. The read carries `If-Match` with the ETag `FindAsync` saw, so the bytes and the checked properties come from one blob version. A blob changed in between fails the condition (412 `ConditionNotMet`), reads as no bytes, and is refused. So the module that accepts an upload checks it before recording it (see Consequences). Only the storage service's `BlobNotFound` reads as "no blob": any other failure, a 404 for a missing container (`ContainerNotFound`) included, is thrown as the SDK's `RequestFailedException`, since it says the module's storage is not what its configuration names, not that an upload is late.
- **A missing setting fails when the first URL is signed, not at startup**, naming it: the connection string `ConnectionStrings:blobs` (the AppHost's `<module>-blobs`), its `ContainerName`, or its `AccountKey` (keyless signing is a separate decision).
- **The web app's origin may use the URLs from the browser, in run mode.** `src/AppHost/Wiring/BrowserUploads.cs` (`AllowBrowserAccessFrom`) sets, once Azurite is ready, one CORS rule on the blob service for `http://localhost:5173` (and the allocated origin where a test run randomizes ports): `GET`, `HEAD`, `PUT`, `OPTIONS`; allowed headers only what an upload or read sends (`content-type`, `x-ms-blob-type`, `x-ms-blob-content-type`, `x-ms-version`, `x-ms-date`, `x-ms-client-request-id`, so no `x-ms-copy-source` or page-blob headers from a browser) and exposed only `etag`, `content-type`, `content-length`, `x-ms-request-id`; max age an hour, keeping the account's other properties. The web app waits for storage, and nothing waiting for storage to be healthy goes on before the rule is set. Another origin's preflight is refused.

## Consequences

- The account key covers every container. One container per module is enforced by configuration (each service is given only its own container's connection string) and by `IBlobUrls` having no container parameter, not by the storage service: a service that built a client from its connection string's key could sign for another module's container. Keyless signing with a user delegation key and a role assignment scoped to the container would enforce it in the storage service; that is part of the keyless-signing decision.
- Deployment needs that decision first. Storage accounts Aspire provisions in Azure disable shared-key access, so there is no account key to sign with; the deployed account also needs CORS rules for the deployed web origin, set where it is provisioned. Until then this design is for local runs and tests.
- `Create` is the narrowest permission that lets a browser put a new blob, but it is wider than "put these bytes once": on its one blob, within its lifetime, an upload URL also allows a snapshot, staging blocks, a page blob of any size, and a server-side copy from a URL the holder names. A SAS cannot limit size or content type. The module that accepts an upload (#15) checks the blob before it records it, and refuses what it did not ask for: anything but a block blob of the kind's content type, empty or above the kind's size, created by Copy Blob rather than put directly, carrying a Content-Disposition or Content-Encoding its uploader gave it, or whose leading bytes are not the kind's (a PDF starts with `%PDF-`, an MP4 has `ftyp` at bytes 4 to 7 and a listed major brand at bytes 8 to 11), since the content type is only what the uploader declared. The properties are checked before any bytes are read. A refusal says only that the file is not a PDF or MP4 video; it names no signature, offset or brand. "Created by a server-side copy" means Copy Blob, which sets `CopyId` and `CopySource`; Put Blob From URL is not verified to set either, so a blob put from a URL the holder names may pass as uploaded. It still has to pass the content type, disposition, encoding, size and leading-bytes checks. Put Blob From URL is tracked in #159.
- The leading-bytes check stops mislabelling, not hostile content. A PDF with `/JavaScript` passes. Read-side hardening (the `rscd` and `rsct` overrides on a read URL, `nosniff`) is a done-when line on #41 and #50.
- The PDF check wants `%PDF-` at byte 0. The PDF specification allows the header anywhere in the first 1024 bytes, so this is stricter; that is accepted. The MP4 check allows only the listed major brands (`isom`, `iso2` to `iso6`, `mp41`, `mp42`, `avc1`, `dash`, `M4V `). A QuickTime movie, a HEIF or AVIF image or a 3GP file is refused. Azurite enforced create-only (a second PUT is refused); Azure's behaviour is documented, not tested here.
- A read URL serves the blob with the content type its uploader set, inline, from the storage account's origin, which all modules' containers share. An uploaded `text/html` would render there. Editorial accepts only a PDF or MP4 content type, with no Content-Disposition or Content-Encoding of the uploader's. The module that hands out read URLs (#41, #50) either accepts only the types it expects at upload, or signs the read URL with a `Content-Disposition` or `Content-Type` override; that choice belongs to those issues, since a video or PDF shown inline needs one and a download another.
- In publish mode `AddAzureStorage` declares a real storage account, and Aspire's default role assignments for a service's reference to it are account-wide, not per container. Nothing publishes today; the keyless-signing decision narrows them to the module's container.
- Under (c) a file another module needs is stored twice, once in each module's container.
- Blobs no chapter uses are never deleted: an upload URL taken and never used for a chapter, an upload refused, the file of a chapter replaced or removed, all stay in the container. A chapter copied into the next version (`DraftNext`) shares its blob with the chapter it was copied from, so a cleanup must count references across all of a course's versions, not one version's chapters. Within a version one blob is the file of at most one chapter (`editorial.file-in-use`). A sweep that deletes unreferenced blobs past an age is proposed as a follow-up.
- How Learning reads a blob Editorial owns, to take its copy, is open, for #41. The options: the integration event carries a read URL (it must outlive 15 minutes until the consumer runs, and a bearer credential then sits in the outbox); Learning gets read access to Editorial's container (contradicts each service signing for its own container); Learning asks Editorial over HTTP (there are no service-to-service calls today); or Editorial writes the copy into Learning's container (Editorial would sign for a container not its own).
- The integration fixture strips volumes, so tests start from an empty Azurite, as they do from empty databases. Azurite adds a container to every local run.
- `fabric upgrade` regenerates files this decision changed and may conflict on them: `src/AppHost/AppHost.cs`, `src/AppHost/AppHost.csproj`, `src/BuildingBlocks/Modules/ModuleInfrastructure.cs`, `src/BuildingBlocks/BuildingBlocks.csproj`, `Directory.Packages.props` and `README.md`. Keep this decision's changes when resolving them.
