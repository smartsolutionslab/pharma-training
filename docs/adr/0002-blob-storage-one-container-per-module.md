# 0002: Blob storage, one container per module

**Status:** Accepted; amended for #114 (PR-E, the owner's decision B2): deployed services sign keyless with a user delegation key, each service's identity is granted its own container alone, and the deployed account has the CORS rule.

## Context

- Issue #3 asks for blob storage with short-lived upload and read URLs: course material (handouts, media) is uploaded by the browser and read back by it, without streaming files through a service host.
- The topology is services: every module runs in its own host with its own database (AGENTS.md, "Topology: services"), and modules never reach into each other's storage. A storage account shared by all modules needs a rule for which service may sign for what.
- The developer chose option (c) on #3: one container per module, and each service signs only for its own container. Signing uses the storage account's key, which the local emulator (Azurite) has; signing without a key (a user delegation key under a managed identity) was left to a separate decision.
- That decision is the owner's B2 on #114: deployed, there is no account key (Aspire provisions storage accounts with shared-key access off, and it stays off); each service signs with a user delegation key under its own managed identity, and its identity holds a data role scoped to its own module's container.
- Aspire's storage integration (`Aspire.Hosting.Azure.Storage` 13.6.5) runs Azurite and creates containers, but has no CORS setting, and a browser cannot use a signed URL on another origin without one.

## Decision

- **One storage account, a container per module.** `src/AppHost/AppHost.cs` adds the account `storage`, run on Azurite with a data volume, and in its loop over the services a container `<module>-blobs` named after the module. Each service reads its own container, and only its own, as the connection string `blobs` (the account's connection string with `ContainerName=<module>`). `AppHostBlobContainersTests` holds the model to it.
- **A module takes `IBlobUrls`** (`src/BuildingBlocks/Storage`), registered for every module by `AddModuleInfrastructure` (`AddModuleBlobStorage`). It has no container parameter: a service signs for the container its configuration names and no other. `BlobName` (relative, at most 1024 characters, no empty, `.` or `..` segment) and `BlobUrlLifetime` (more than zero, at most 15 minutes) guard what is signed. No module names the Azure Storage SDK; `BlobStorageSdkStaysInBuildingBlocks` fails the build otherwise.
- **The URLs are SAS on one blob** (`AzureBlobUrls`, `sr=b`): an upload URL has `Create` alone (`sp=c`: it creates its blob, and cannot read, overwrite or delete it, or touch another; what else `Create` allows on that one blob is under Consequences), a read URL `Read` alone (`sp=r`). Both expire at most 15 minutes after signing, rounded down to the second, and carry no start time (`st`), so a clock behind the storage service's never makes a fresh URL fail. `BlobStorageTests` sends each kind to Azurite and checks what it may and may not do.
- **Run mode signs with the account key, deployments with a user delegation key.** Where the connection string `blobs` has an `AccountKey` (Azurite), a URL is a service SAS signed with it, and nothing else is asked. Published, it has the blob service's endpoint and the container and no key (`Endpoint=https://<account>.blob.core.windows.net/;ContainerName=<module>`), and a URL is a user delegation SAS with the same blob, permission and expiry: `AzureBlobUrls` asks an `IUserDelegationKeySource` (`src/BuildingBlocks/Storage`) for a key valid for an hour, keeps it, and asks for a new one only when a URL would outlive it. URLs signed at once share one request for a key, and a key never replaces a kept one that outlives it. A keyless URL is valid over https alone (`spr=https`; run mode's account-key URLs are unchanged, Azurite serves http), and it is signed for the account its endpoint's host names, so an endpoint that is not `https://<account>.blob.core.windows.net/` (a custom domain, a proxy) fails when the first URL is signed, naming it. The source registered by `AddModuleBlobStorage`, `ManagedIdentityUserDelegationKeys`, asks the storage service under the managed identity whose client id the AppHost passes as `AZURE_CLIENT_ID` (a `BlobServiceClient` with a `ManagedIdentityCredential`, `Azure.Identity`, referenced by `src/BuildingBlocks` alone); `AzureStoredBlobs` reads blob properties under the same identity. `AzureBlobUrlsUserDelegationTests` checks the URLs and the key's reuse with the key source substituted.
- **Published, each service's identity may use its own container alone** (`src/AppHost/Wiring/BlobStorage.cs`, `BlobContainerAccess.cs`). Aspire's default roles for a reference to the account (Storage Blob, Table and Queue Data Contributor on the whole account) are cleared (`ClearDefaultRoleAssignments`), and `WithBlobContainer` grants the service's identity, `<module>-identity`, Storage Blob Data Contributor scoped to its container and Storage Blob Delegator on the account, which grants no data access of its own but lets it ask for user delegation keys, in a Bicep module of its own, `<module>-roles-storage`. A user delegation SAS grants no more than its signer's own roles, so a key the service is issued signs for its own container alone. `AppHostStorageTests` holds the published Bicep to exactly these two grants per service, and to shared-key access staying off.
- **A module reads what was uploaded through `IStoredBlobs`** (`AzureStoredBlobs`, registered by `AddModuleBlobStorage` beside `IBlobUrls`, with no container parameter either): `FindAsync(BlobName)` answers the blob's content type, length, whether it is a block blob and whether a server-side copy created it (its copy source or copy id is set; not its copy status, which a blob put directly reports too), or none when nothing lies under the name, so the module that accepts an upload checks it before recording it (see Consequences).
- **A missing setting fails when the first URL is signed, not at startup**, naming it: the connection string `ConnectionStrings:blobs` (the AppHost's `<module>-blobs`), its `ContainerName`, or, without an `AccountKey`, the managed identity `AZURE_CLIENT_ID` (the message names both).
- **The web app's origin may use the URLs from the browser, in run mode.** `src/AppHost/Wiring/BrowserUploads.cs` (`AllowBrowserAccessFrom`) sets, once Azurite is ready, one CORS rule on the blob service for `http://localhost:5173` (and the allocated origin where a test run randomizes ports): `GET`, `HEAD`, `PUT`, `OPTIONS`; allowed headers only what an upload or read sends (`content-type`, `x-ms-blob-type`, `x-ms-blob-content-type`, `x-ms-version`, `x-ms-date`, `x-ms-client-request-id`, so no `x-ms-copy-source` or page-blob headers from a browser) and exposed only `etag`, `content-type`, `content-length`, `x-ms-request-id`; max age an hour, keeping the account's other properties. The web app waits for storage, and nothing waiting for storage to be healthy goes on before the rule is set. Another origin's preflight is refused.
- **Published, the edge's origin and the web app's public address alone may use them** (`AllowBrowserAccessFromEdge`, in the same file): the account's blob service gets one CORS rule, with the same methods, headers, exposed headers and max age as run mode's (the same constants), for two origins and no wildcard: `https://host.<the Container Apps environment's default domain>`, where the edge, which serves the web app, is reached, and the parameter `frontend-url`, which main.bicep hands the storage module as `frontend_url`. The domain is the environment's Bicep output `AZURE_CONTAINER_APPS_ENVIRONMENT_DEFAULT_DOMAIN`, read by name, since the property Aspire reads it with is not public.

## Consequences

- Deployed, the storage service enforces one container per module: a service's identity has a data role on its own container alone, and the keys it is issued sign for no other. In run mode Azurite's account key covers every container, so there it is enforced only by configuration (each service is given its own container's connection string) and by `IBlobUrls` having no container parameter.
- A deployed service asks the storage service for a key about once an hour per instance; a URL is never signed with a key that expires before it. Revoking the account's user delegation keys (or a service's role) stops every URL signed with them. Signing needs the identity's token and the key request to succeed, so a storage or identity outage surfaces where the first URL after it is signed.
- The deployed rule names the environment's default domain and `frontend-url` as it is set, so a custom domain for the web app is allowed by setting `frontend-url` to it. A CORS origin is compared exactly, so `frontend-url` must be an origin (scheme and host, no path, no trailing slash). A third origin needs the rule changed, in `AllowBrowserAccessFromEdge`.
- `Create` is the narrowest permission that lets a browser put a new blob, but it is wider than "put these bytes once": on its one blob, within its lifetime, an upload URL also allows a snapshot, staging blocks, a page blob of any size, and a server-side copy from a URL the holder names. A SAS cannot limit size or content type. The module that accepts an upload (#15) checks the blob's properties before it records it, and refuses what it did not ask for: anything but a block blob of the kind's content type, empty or above the kind's size, or created by a server-side copy rather than put directly. Azurite enforced create-only (a second PUT is refused); Azure's behaviour is documented, not tested here.
- A read URL serves the blob with the content type its uploader set, inline, from the storage account's origin, which all modules' containers share. An uploaded `text/html` would render there. The module that hands out read URLs (#41, #50) either accepts only the types it expects at upload, or signs the read URL with a `Content-Disposition` or `Content-Type` override; that choice belongs to those issues, since a video or PDF shown inline needs one and a download another.
- Under (c) a file another module needs is stored twice, once in each module's container.
- How Learning reads a blob Editorial owns, to take its copy, is open, for #41. The options: the integration event carries a read URL (it must outlive 15 minutes until the consumer runs, and a bearer credential then sits in the outbox); Learning gets read access to Editorial's container (contradicts each service signing for its own container); Learning asks Editorial over HTTP (there are no service-to-service calls today); or Editorial writes the copy into Learning's container (Editorial would sign for a container not its own).
- The integration fixture strips volumes, so tests start from an empty Azurite, as they do from empty databases. Azurite adds a container to every local run.
