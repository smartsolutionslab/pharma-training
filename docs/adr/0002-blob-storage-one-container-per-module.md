# 0002: Blob storage, one container per module

**Status:** Accepted; amended for #114 (PR-E, the owner's decision B2): deployed services sign keyless with a user delegation key, each service's identity is granted its own container alone, and the deployed account has the CORS rule. Amended for #41: read URLs carry signed response overrides, a module copies another module's blob into its own container server side (`IBlobCopies`), and Learning reads Editorial's files through read URLs Editorial releases.

## Context

- Issue #3 asks for blob storage with short-lived upload and read URLs: course material (handouts, media) is uploaded by the browser and read back by it, without streaming files through a service host.
- The topology is services: every module runs in its own host with its own database (AGENTS.md, "Topology: services"), and modules never reach into each other's storage. A storage account shared by all modules needs a rule for which service may sign for what.
- The developer chose option (c) on #3: one container per module, and each service signs only for its own container. Signing uses the storage account's key, which the local emulator (Azurite) has; signing without a key (a user delegation key under a managed identity) was left to a separate decision.
- That decision is the owner's B2 on #114: deployed, there is no account key (Aspire provisions storage accounts with shared-key access off, and it stays off); each service signs with a user delegation key under its own managed identity, and its identity holds a data role scoped to its own module's container.
- Aspire's storage integration (`Aspire.Hosting.Azure.Storage` 13.6.5) runs Azurite and creates containers, but has no CORS setting, and a browser cannot use a signed URL on another origin without one.

## Decision

- **One storage account, a container per module.** `src/AppHost/AppHost.cs` adds the account `storage`, run on Azurite with a data volume, and in its loop over the services a container `<module>-blobs` named after the module. Each service reads its own container, and only its own, as the connection string `blobs` (the account's connection string with `ContainerName=<module>`). `AppHostBlobContainersTests` holds the model to it.
- **A module takes `IBlobUrls`** (`src/BuildingBlocks/Storage`), registered for every module by `AddModuleInfrastructure` (`AddModuleBlobStorage`). It has no container parameter: a service signs for the container its configuration names and no other. `BlobName` (relative, at most 1024 characters, no empty, `.` or `..` segment) and `BlobUrlLifetime` (more than zero, at most 15 minutes) guard what is signed. No module names the Azure Storage SDK; `BlobStorageSdkStaysInBuildingBlocks` fails the build otherwise.
- **The URLs are SAS on one blob** (`AzureBlobUrls`, `sr=b`): an upload URL has `Create` alone (`sp=c`: it creates its blob, and cannot read, overwrite or delete it, or touch another; what else `Create` allows on that one blob is under Consequences), a read URL `Read` alone (`sp=r`). Both expire at most 15 minutes after signing, rounded down to the second, and carry no start time (`st`), so a clock behind the storage service's never makes a fresh URL fail. Where the blob endpoint is https, both are signed for https only (`spr=https`), on both signing paths, so a signature never works over plain http; the emulator's http endpoint gets no protocol, which it would otherwise refuse. `BlobStorageTests` sends each kind to Azurite and checks what it may and may not do.
- **Run mode signs with the account key, deployments with a user delegation key.** Where the connection string `blobs` has an `AccountKey` (Azurite), a URL is a service SAS signed with it, and nothing else is asked. Published, it has the blob service's endpoint and the container and no key (`Endpoint=https://<account>.blob.core.windows.net/;ContainerName=<module>`), and a URL is a user delegation SAS with the same blob, permission and expiry: `AzureBlobUrls` asks an `IUserDelegationKeySource` (`src/BuildingBlocks/Storage`) for a key valid for an hour, keeps it, and asks for a new one only when a URL would outlive it. The source registered by `AddModuleBlobStorage`, `ManagedIdentityUserDelegationKeys`, asks the storage service under the managed identity whose client id the AppHost passes as `AZURE_CLIENT_ID` (a `BlobServiceClient` with a `ManagedIdentityCredential`, `Azure.Identity`, referenced by `src/BuildingBlocks` alone); `AzureStoredBlobs` reads blob properties under the same identity. `AzureBlobUrlsUserDelegationTests` checks the URLs and the key's reuse with the key source substituted.
- **Published, each service's identity may use its own container alone** (`src/AppHost/Wiring/BlobStorage.cs`, `BlobContainerAccess.cs`). Aspire's default roles for a reference to the account (Storage Blob, Table and Queue Data Contributor on the whole account) are cleared (`ClearDefaultRoleAssignments`), and `WithBlobContainer` grants the service's identity, `<module>-identity`, Storage Blob Data Contributor scoped to its container and Storage Blob Delegator on the account, which grants no data access of its own but lets it ask for user delegation keys, in a Bicep module of its own, `<module>-roles-storage`. A user delegation SAS grants no more than its signer's own roles, so a key the service is issued signs for its own container alone. `AppHostStorageTests` holds the published Bicep to exactly these two grants per service, and to shared-key access staying off.
- **A module reads what was uploaded through `IStoredBlobs`** (`AzureStoredBlobs`, registered by `AddModuleBlobStorage` beside `IBlobUrls`, with no container parameter either): `FindAsync(BlobName)` answers the blob's content type, length, whether it is a block blob, its ETag (the quoted header value), whether Copy Blob created it (its copy source or copy id is set; not its copy status, which a blob put directly reports too) and the Content-Disposition and Content-Encoding its uploader set (a blank one is none), or none when nothing lies under the name; `ReadStartAsync(StoredBlob, count)` answers the first `count` bytes of the blob found, by a ranged download, or all of a shorter blob. The read carries `If-Match` with the ETag `FindAsync` saw, so the bytes and the checked properties come from one blob version. A blob changed in between fails the condition (412 `ConditionNotMet`), reads as no bytes, and is refused. So the module that accepts an upload checks it before recording it (see Consequences). Only the storage service's `BlobNotFound` reads as "no blob": any other failure, a 404 for a missing container (`ContainerNotFound`) included, is thrown as the SDK's `RequestFailedException`, since it says the module's storage is not what its configuration names, not that an upload is late. Deployed, it reads under the service's managed identity.
- **Read URLs carry signed `rsct` and `rscd` (#41).** `CreateReadUrlAsync` takes a `BlobReadHeaders`, required, so no read URL is signed without overrides: `BlobReadHeaders.Inline(type)` accepts only `application/pdf` and `video/mp4`, the two types the player shows; `BlobReadHeaders.Attachment(type)` any type; both only one bare lower-case `type/subtype` (no parameters, whitespace or line break). `AzureBlobUrls` sets them as the SAS's `ContentType` and `ContentDisposition` (`inline` or `attachment`) on both signing paths, so the storage service serves the blob with the type and disposition the module chose, whatever its uploader set, and they are part of the string signed: a URL whose override was changed is refused (`AzureBlobUrlsTests`, `AzureBlobUrlsUserDelegationTests`, and against Azurite `BlobStorageTests`).
- **A module copies a blob into its own container with `IBlobCopies` (#41)** (`AzureBlobCopies`, registered by `AddModuleBlobStorage` beside `IBlobUrls` and `IStoredBlobs`). `CopyFromAsync(BlobUrl source, BlobName target)` takes a read URL another module signed on its own blob (so (c) holds: the module signs only for its own container, and reads another's only through a URL that module chose to sign) and copies it server side with Put Blob From URL (`SyncUploadFromUriAsync`, `overwrite: false`). The target name is derived by the module, not generated, so a blob already under it counts as copied (`BlobCopyOutcome.AlreadyThere`), including a copy refused because another writer created it in between (409 `BlobAlreadyExists`); anything else the storage service refuses, an expired source first, is thrown. A source whose scheme, host or port differs from the module's own blob service endpoint is refused with a `GuardException` before any request is made, so a message cannot make a module fetch from an arbitrary host. The client's network timeout is 10 minutes. Why Put Blob From URL, verified against Azurite 3.38.0's source (`dist/src/blob/handlers`):
  - Start Copy Blob (`StartCopyFromUri`) cannot prove a signed source in run mode: Azurite validates a source carrying a `sig` with an HTTP HEAD to the source URL from inside its container (`BlobHandler.validateCopySource`), and that URL holds the host port Aspire mapped, which does not reach Azurite from inside its container.
  - Copy Blob From URL (synchronous) skips that check within one account, but on Azure it is limited to sources of 256 MiB, and a video may be 2 GiB.
  - Put Blob From URL in Azurite reads the source through the socket the request arrived on (`BlockBlobHandler.readCopySource`), so it works behind the port mapping; it is synchronous, so the caller needs no polling; on Azure it is documented for sources up to 5000 MiB.
  - Azurite implements Put Blob From URL from 3.38.0; the image Aspire pins by default, 3.35.0, answers it 501 `APINotImplemented`. So `src/AppHost/Wiring/BlobStorage.cs` pins the emulator to `mcr.microsoft.com/azure-storage/azurite:3.38.0` (`WithImageTag`); a later Aspire that pins a newer Azurite may drop the pin.
- **A missing setting fails when the first URL is signed, not at startup**, naming it: the connection string `ConnectionStrings:blobs` (the AppHost's `<module>-blobs`), its `ContainerName`, or, without an `AccountKey`, the managed identity `AZURE_CLIENT_ID` (the message names both).
- **The web app's origin may use the URLs from the browser, in run mode.** `src/AppHost/Wiring/BrowserUploads.cs` (`AllowBrowserAccessFrom`) sets, once Azurite is ready, one CORS rule on the blob service for `http://localhost:5173` (and the allocated origin where a test run randomizes ports): `GET`, `HEAD`, `PUT`, `OPTIONS`; allowed headers only what an upload or read sends (`content-type`, `x-ms-blob-type`, `x-ms-blob-content-type`, `x-ms-version`, `x-ms-date`, `x-ms-client-request-id`, so no `x-ms-copy-source` or page-blob headers from a browser) and exposed only `etag`, `content-type`, `content-length`, `x-ms-request-id`; max age an hour, keeping the account's other properties. The web app waits for storage, and nothing waiting for storage to be healthy goes on before the rule is set. Another origin's preflight is refused.
- **Published, the edge's origin alone may use them** (`AllowBrowserAccessFromEdge`, in the same file): the account's blob service gets one CORS rule, with the same methods, headers, exposed headers and max age as run mode's (the same constants), for `https://host.<the Container Apps environment's default domain>`, where the edge, which serves the web app, is reached. The domain is the environment's Bicep output `AZURE_CONTAINER_APPS_ENVIRONMENT_DEFAULT_DOMAIN`, read by name, since the property Aspire reads it with is not public.

## Consequences

- Deployed, the storage service enforces one container per module: a service's identity has a data role on its own container alone, and the keys it is issued sign for no other. In run mode Azurite's account key covers every container, so there it is enforced only by configuration (each service is given its own container's connection string) and by `IBlobUrls` having no container parameter.
- A deployed service asks the storage service for a key about once an hour per instance; a URL is never signed with a key that expires before it. Revoking the account's user delegation keys (or a service's role) stops every URL signed with them. Signing needs the identity's token and the key request to succeed, so a storage or identity outage surfaces where the first URL after it is signed.
- The deployed rule names the environment's default domain. A custom domain for the edge needs its origin added to the rule, in `AllowBrowserAccessFromEdge`.
- `Create` is the narrowest permission that lets a browser put a new blob, but it is wider than "put these bytes once": on its one blob, within its lifetime, an upload URL also allows a snapshot, staging blocks, a page blob of any size, and a server-side copy from a URL the holder names. A SAS cannot limit size or content type. The module that accepts an upload (#15) checks the blob before it records it, and refuses what it did not ask for: anything but a block blob of the kind's content type, empty or above the kind's size, created by Copy Blob rather than put directly, carrying a Content-Disposition or Content-Encoding its uploader gave it, or whose leading bytes are not the kind's (a PDF starts with `%PDF-`, an MP4 has `ftyp` at bytes 4 to 7 and a listed major brand at bytes 8 to 11), since the content type is only what the uploader declared. The properties are checked before any bytes are read. A refusal says only that the file is not a PDF or MP4 video; it names no signature, offset or brand. "Created by a server-side copy" means Copy Blob, which sets `CopyId` and `CopySource`; Put Blob From URL is not verified to set either, so a blob put from a URL the holder names may pass as uploaded. It still has to pass the content type, disposition, encoding, size and leading-bytes checks. Put Blob From URL is tracked in #159.
- The leading-bytes check stops mislabelling, not hostile content. A PDF with `/JavaScript` passes. On the read side every URL names its type and disposition with signed overrides (see Decision); `nosniff` is argued unnecessary below, not set.
- The PDF check wants `%PDF-` at byte 0. The PDF specification allows the header anywhere in the first 1024 bytes, so this is stricter; that is accepted. The MP4 check allows only the listed major brands, matched exactly (case and the trailing space included): the ISO base media brands `isom` and `iso2` to `iso9`, MP4's `mp41` and `mp42`, `avc1`, DASH's `dash`, CMAF's `cmfc` and `cmf2`, Apple's `M4V `, Sony's `XAVC` and `MSNV`, and `mmp4`. A QuickTime movie, a HEIF or AVIF image or a 3GP file is refused, and so is `f4v `: it is Flash video, an MP4-like container a browser's `video/mp4` player is not made for, from a format that is no longer maintained. Azurite enforced create-only (a second PUT is refused); Azure's behaviour is documented, not tested here.
- A read URL serves the blob with the content type and disposition it was signed with (`rsct`, `rscd`), never the uploader's, from the storage account's origin, which all modules' containers share. Inline is signed only for `application/pdf` and `video/mp4`; anything else is an attachment. So an uploaded `text/html` cannot be rendered there through a read URL a module signs.
- **`nosniff` is not set, and not needed.** Azure Blob Storage cannot add `X-Content-Type-Options` to a response: a SAS overrides only `rscc`, `rscd`, `rsce`, `rscl` and `rsct`, and a blob's properties have no custom response header. The argument that it adds nothing these URLs need: every read URL names its type explicitly, and an inline one is `application/pdf` or `video/mp4`. Browsers sniff a navigation's or a media element's body only when the supplied type is missing, `unknown/unknown`, `application/unknown`, `*/*`, or (with the Apache-bug check) `text/plain`, and for `application/octet-stream` downloads (WHATWG MIME Sniffing, §7); an explicit `application/pdf` or `video/mp4` is never sniffed into `text/html`. Scripts and styles are what `nosniff` mainly governs: a PDF included as a script runs, if at all, in the including page's origin, not ours or the storage account's, and browsers block `video/*` as script outright. Verified: Azurite 3.38.0 sends no `X-Content-Type-Options` (`BlobStorageTests` pins it), and applies `rsct` and `rscd` to the GET response and includes them in the string it signs (`BlobSASAuthenticator`, `BlobHandler`), so a changed override fails the signature (`BlobStorageTests`). Not verified: whether Azure sends `nosniff`, and the deployed account's behaviour; there is no deployed account yet, so that is checked with #114.
- Put Blob From URL on Azure is documented for sources up to 5000 MiB, which bounds a chapter's file; a 2 GiB copy is not observed, neither its duration nor whether the 10-minute network timeout suffices. If the deployed service times out, staged Put Block From URL is the follow-up, to be observed under #114. A copy is a bearer read URL in a message until it is used: `ChapterFilesReleasedV1` (`src/Contracts/Editorial`) carries Editorial's read URLs for Learning to copy; that decision and its limits are recorded below.
- Under (c) a file another module needs is stored twice, once in each module's container.
- Blobs no chapter uses are never deleted: an upload URL taken and never used for a chapter, an upload refused, the file of a chapter replaced or removed, all stay in the container. A chapter copied into the next version (`DraftNext`) shares its blob with the chapter it was copied from, so a cleanup must count references across all of a course's versions, not one version's chapters. Within a version one blob is the file of at most one chapter (`editorial.file-in-use`). A unique index on a version's chapter files backs that rule; a database that held the duplicate rows #140 allowed would need a migration that cleans them up before the index can be created. None does, since nothing is deployed (#114 and #129 are open). A sweep that deletes unreferenced blobs past an age is proposed as a follow-up.
- **Learning reads a blob Editorial owns through read URLs Editorial releases (#41).** When a version with PDF or video chapters is published, `PublishCourseVersionHandler` signs a read URL on each chapter's file (`BlobUrlLifetime.Maximum`, 15 minutes; `rsct` the kind's type, `rscd` `inline`, `ChapterUploads.ReadHeadersFor`) and publishes `ChapterFilesReleasedV1` (`src/Contracts/Editorial`) in the same unit of work as `CourseVersionPublishedV1`, which stays unchanged; a refused or lost publish signs and sends nothing, and a text-only version releases no files. Learning copies each file into its own container with `IBlobCopies`. Rejected: a `CourseVersionPublishedV2` with the URLs (Catalog, Compliance and Learning consume V1, which would have to be published twice or migrated, and only Learning needs the files); read access for Learning on Editorial's container (breaks (c), each service signing for its own container alone); Learning asking Editorial over HTTP (there are no service-to-service calls); Editorial writing into Learning's container (Editorial would sign for a container not its own). Its known limits:
  - A bearer read URL for Editorial's blob sits in Editorial's outbox until it is sent, and in a dead letter if the copy fails, until it expires, at most 15 minutes after signing; after that it is worthless.
  - If Learning has not copied a file within 15 minutes of the publish, the copy fails at the storage service and is retried (Wolverine: 1 to 32 s, about a minute), then dead-lettered; a replay after expiry fails again. Until a follow-up issue (Editorial re-releases a version's files on request) is done, the chapter answers 409 `learning.media-not-ready` for good.
  - A publish now signs one read URL per file chapter before it commits. In run mode that needs no I/O. Deployed, it may ask for a user delegation key (about once an hour), so a storage or identity outage makes a publish fail with 500 rather than publish without files.
- **Learning's copy lives at `course-versions/{version}/chapters/{chapter}.pdf|.mp4` in `learning-blobs` (#41)** (the AppHost resource; the blob container itself is named `learning`, `ChapterMedia.NameFor`). `ChapterFilesReleasedV1Consumer` copies each released file there with `IBlobCopies`, one after another. The name is derived from the version and the chapter, not generated, so it is the consumer's deduplication: a file already there counts as copied, and the consumer writes no row. It does not check that Learning holds the version, since the release may arrive before `CourseVersionPublishedV1`. Blobs in `learning-blobs` are never deleted either; the cleanup follow-up above covers both containers.
- The integration fixture strips volumes, so tests start from an empty Azurite, as they do from empty databases. Azurite adds a container to every local run.
