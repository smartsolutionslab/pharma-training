# 0004: The invitation mail goes over SMTP, and only the token's hash is stored

**Status:** Accepted; amended 2026-11-23: one mail per invitation version, and every link of a version works; amended 2026-11-23 (#158): invitation mail is limited, and only services that send mail get the mail settings; amended 2026-11-24 (#265): an address is mailed at most once per 10 minutes and a sender at most 100 times per UTC day, across pharmacies; amended 2026-11-24 (#294): invitations take every instant from the database's clock, `Retry-After` counts from it, and the renew cooldown has a ceiling; amended 2026-11-24 (#369): a sender's row is created if missing and held until the commit, so a sender's concurrent mails, the first two included, count one after the other; amended 2026-11-24 (#375): an address's row is created if missing and held until the commit too, always before the sender's, and a wait for either row ends after a lock timeout as a request to try again

## Context

- Issue #9 has a pharmacy's management invite an address, renew the invitation or revoke it. The invited person needs a link to accept the invitation, and the link must carry a secret only they receive.
- `docs/domain/README.md` said "Keine E-Mails in MVP 1", and the invitation was planned to go "per Mail über den IdP". Keycloak sends only its own mails (verification, reset password, required actions), not an arbitrary text with a link into the web app.
- On 2026-11-21 the owner chose answer (a) on #9: Organisation sends the invitation mail itself over SMTP. That is Mailpit locally. Deployed, it is a connection string `mail` and a parameter `mail-from`, both Aspire parameters, and the connection string is secret because it may hold credentials. The text is our own, in German, with the link `{frontend}/invitations/accept#token=…`. Self-registration in the realm belongs to #13.
- Before #9 the aggregate stored the raw token in `organisation.memberships.token`, compared raw tokens on accept, and `InvitationToken.ToString()` returned the secret.
- The mail must not be lost. AGENTS.md (Module style: domain-driven design): "Work that must not be lost, or that another module needs, is an integration event, not a domain-event reaction". A first version of this PR sent the mail from a domain-event reaction; review finding 4656162415 on PR #138 showed how it lost mail (see Alternatives), and reply 4656164651 set the direction this ADR records.

## Decision

- **SMTP from the service, through a building block.** `src/BuildingBlocks/Mail` has `IMailSender` (`SmtpMailSender`, MailKit 4.18.2) and `IFrontendLinks` (`FrontendLinks`). A module that sends mail registers both itself, with `services.AddModuleMail(configuration)` in its `IModule.AddServices` (Organisation's `OrganisationModule`); `AddModuleInfrastructure` no longer does it for every module (#158), so a host whose module sends no mail registers no `IMailSender`, no `IFrontendLinks` and no `MailSettingsValidation`. Only `BuildingBlocks.csproj` references MailKit or MimeKit; `MailSdkStaysInBuildingBlocks` fails the build otherwise. Registering reads nothing. No error names a password.
- **Only a service that sends mail says so, and only it gets the settings.** A service host's project says `<SendsMail>true</SendsMail>` beside `<ModuleName>` (only `src/Services/Organisation/Host/Host.csproj` does); absent means false. The AppHost reads it as it reads `<ModuleName>` (`ServiceHostProjects.SendsMail`): `true` or `false` in any letter case, and any other value stops the AppHost naming the project file and the value. No line per module, no module list. The architecture rule `EveryHostThatSendsMailSaysSo` fails when a service host's module registers `IMailSender` and its project lacks the flag, or the other way round, naming the project.
- **The settings come from the AppHost**, in the services' loop, for a service whose project says `<SendsMail>true</SendsMail>` alone (`WithMail`, `src/AppHost/Wiring/MailServer.cs`, and `Frontend__BaseUrl`, which nothing but the mail's links reads). Keycloak and those services send through one SMTP server, declared once in `MailServer`:
  - `mail`: in run mode, Mailpit's allocated SMTP endpoint (`smtp://localhost:<port>`, no credentials). Mailpit exists only in run mode. In publish mode it is no plain connection string: the AppHost composes `smtp://<smtp-username>:<smtp-password>@<smtp-host>:587` from the same `smtp-*` parameters Keycloak reads (docs/adr/0005), stores it in the Key Vault `secrets` as `mail-connection-string` (`DeploymentSecrets.Store`), and each service that sends mail reads `ConnectionStrings:mail` as a Key Vault reference; the others reference no such secret, so `GrantEachAppTheSecretsItReadsAsync` does not grant it to them. `smtp-host` names the host alone, as Keycloak's `SMTP_HOST` does; the port is 587, submission with STARTTLS, which Azure Communication Services' SMTP relay answers on, and `smtp` to a host that is not loopback requires STARTTLS (below). Main.bicep does not URI-escape the value it assembles, so `smtp-username` and `smtp-password` must be URI-safe (letters, digits, `-`, `.`, `_`, `~`), as the broker's credentials must (docs/adr/0005); Azure Communication Services' `<resource>.<app id>.<tenant id>` user is.
  - `Mail:From`: in run mode the parameter `mail-from`, `noreply@example.com` by default. In publish mode it is Keycloak's sender, `smtp-from`, with no default, as `frontend-url` has none, so a deployment that forgot it does not send from a placeholder address; there is no second `mail-from` parameter to set to the same address.
  - `Frontend__BaseUrl`: the web app's endpoint in run mode, where the web app's dev server runs (it is run mode only, docs/adr/0005), and the parameter `frontend-url` in publish mode. That parameter is the deployed web app's public URL, which no endpoint reference knows. It must be https; http is accepted only for a loopback host, because the link carries the token.
- **Outside Development a service that sends mail does not start without usable mail settings.** `AddModuleMail` registers `MailSettingsValidation` with `ValidateOnStart`. Outside Development it checks `ConnectionStrings:mail`, `Mail:From` and `Frontend:BaseUrl` with the parsers the send and the link use, so the check and the send cannot disagree, and fails the host's start naming each bad key with its AppHost parameter, never a value. In Development (`aspire run`, the integration tests) it reads nothing, and a missing setting fails the first send or link, naming it.
- **The mail goes to the stored address exactly.** `EmailAddress` refuses the characters mail reads as syntax (`< > " , ; ( ) [ ] \ :`), so no stored address is a display name, comment, list or route, and `SmtpMailSender` sends to `OutgoingMail.To` as it is, refusing one that would parse to another mailbox. `PharmacyName`, which goes into the subject and text, refuses control characters and the bidi embeddings, overrides and isolates.
- **The connection string** is `smtp://[user[:password]@]host[:port]` or `smtps://…`:
  - A path other than `/`, a query or a fragment is refused at start-up: a password with an unescaped `/`, `?` or `#` would otherwise make the user the host (`smtp://user:42/…` is host `user`, port 42), and the service would mail there after a clean start.
  - `smtps` connects with TLS, on port 465 by default.
  - `smtp` to a host that is not loopback requires STARTTLS, with or without credentials, so neither a password nor a mail with its link travels in clear off the machine.
  - `smtp` to a loopback host without credentials (Mailpit) uses STARTTLS when the server offers it. Port 25 is the default.
  - The whole send is bounded at 10 s on the `TimeProvider`; MailKit's default is two minutes per step. The caller's token is honoured only before the send starts.
  - The settings are read at every send and link, so a setting supplied later is used without a restart; outside Development they are also checked at start-up.
- **A refused recipient is scrubbed from the exception.** MailKit's `SmtpCommandException` carries the server's text, which often echoes the address (`550 5.1.1 <anna@example.org>: …`). `SmtpMailSender` rethrows it as `MailNotSentException`, whose message names only the step and the codes and which keeps no inner exception, so the address reaches neither the log nor a dead letter. Connection, TLS, authentication and protocol failures (`IOException`, `SslHandshakeException`, `AuthenticationException`, `SmtpProtocolException`) are scrubbed the same way: a `MailNotSentException` that names only the kind of failure, with no server text, no recipient and no inner exception. The 10 s bound and the caller's own cancellation before the send still pass through as an `OperationCanceledException` (`MailSendTimedOutException`), and a missing setting as a `MailNotSentException` (an `InvalidOperationException`) whose message names the setting; they carry no recipient.
- **A failure after the server took the mail counts as sent.** Once MailKit's `SendAsync` has returned, the server has the mail; a failure in `DisconnectAsync` afterwards (a dropped connection, a refused `QUIT`, a timeout, the 10 s bound firing) is logged as a Warning naming only the kind of failure, and the send completes, so nothing retries a mail the invitee already has. `SmtpMailSender` takes an `ILogger<SmtpMailSender>` for it.
- **A failed send says whether the mail may have reached the server.** `MailNotSentException.MayHaveBeenDelivered`, and the same on `MailSendTimedOutException`, the `OperationCanceledException` the 10 s bound surfaces as, is `false` when the server cannot hold the mail: a failure before MailKit's `SendAsync` started (a missing or unusable `Mail:From` or `ConnectionStrings:mail`, which keep their messages naming the setting; the caller's cancellation at the start, as `MailSendTimedOutException`; connect, TLS, login; the bound firing there), and the server's own refusal (`SmtpCommandException`) at any step, MAIL FROM, RCPT TO and DATA included. It is `true` only for a transport, protocol or timeout failure once `SendAsync` started. An exception that does not say is `true`, the side that keeps the link.
- **The mail is German plain text.** `InvitationMails.Compose(PharmacyName, EmailAddress, Timestamp, Uri)` sets To (the invited address) and Subject (`Einladung zu {Apotheke} bei PharmaTraining`). The text says when the link expires in UTC (`dd.MM.yyyy, HH:mm`, invariant culture), and says that a renewed invitation leaves only the newest link working. There is no HTML part, and MimeKit sets every header, so no pharmacy name or address can add one.
- **The token travels in the link's fragment.** The link is `/invitations/accept#token=…` at the web app's root. Browsers never send a fragment to a server, so the token appears in no access log or `Referer`. #13 builds that page and posts the token in the body of `POST /organisation/invitations/accept` (#10).
- **The token is 256 random bits, made at send time, and only its SHA-256 is stored.**
  - `InvitationTokens.Next()` makes 43 URL-safe characters (`Base64Url` of 32 bytes from `RandomNumberGenerator`). Its only caller is the mail's consumer.
  - Only the token's hash (`InvitationTokenHash`, 64 lower-case hex characters) is stored; the column `token` is dropped (migration `ReplaceInvitationTokenWithHashAndAddUniqueIndexes`). Since the amendment the hashes are `Membership.InvitationLinks`, one row each in `organisation.invitation_links` (`membership_id`, `token_hash`, a unique index on `token_hash`), and the single column `memberships.token_hash` is dropped (migration `InvitationLinksPerVersion`).
  - Each membership has an `InvitationVersion`: 1 at the invite, the next at each renewal (a founder keeps 1 and is never mailed). `InvitationMailedFor` is the version whose mail was sent.
  - `Pharmacy.Invite(id, email, jobFunction, role, now, limits)` takes no token: an invitation holds no link (`InvitationLinks` empty) until its mail issues one. `RenewInvitation(membership, now, limits)` moves to the next version and clears every link at once, so the old links die at the renewal's commit, and runs the invitation 14 days from the renewal.
  - `Pharmacy.IssueInvitationLink(membership, token, now)` adds the token's hash to the current version's links for an open invitation that has not run out, raises `InvitationLinkIssued` (ids only) and answers the expiry; the version's earlier links keep working. A version holds at most `Pharmacy.MaxInvitationLinksPerVersion` (5) links, so a mail retried without end cannot mint links without limit: a sixth answers `InvitationLinkLimitReached` (`organisation.invitation-link-limit-reached`). Only links whose mails may be out count: `Pharmacy.WithdrawInvitationLink(membership, token)` takes back a link whose mail never reached the server and raises `InvitationLinkWithdrawn`. A membership that is not open answers `NoOpenInvitation`, one that has run out `InvitationExpired`; nothing changes then.
  - `Pharmacy.RecordInvitationMailed(membership, version)` records that the version's mail was sent and raises `InvitationMailed`; a version that is no longer the open one answers `NoOpenInvitation`.
  - Accept looks the invitation up by `InvitationTokenHash.Of(token)` and matches any of the version's links; accept and revoke clear them all. There is no salt and no slow hash: the input is random, not a password, and a lookup by hash needs no timing-sensitive comparison.
  - `InvitationToken.ToString()` prints no value, and no domain event carries a token: `MemberInvited` holds the pharmacy, the membership and the expiry.
- **A durable local message, not a domain-event reaction.**
  - Invite and renew publish `InvitationMailRequestedV1(MembershipId, PharmacyId)` (`src/Contracts/Organisation`) through the unit of work for each `MemberInvited`, so the envelope is saved with the invitation in the same commit; a commit that loses its race (`TryCommitAsync` false, 409) rolls it back with the save. The event carries ids only, never the token, the address or a name, so its envelope and its dead letter hold no personal data.
  - Organisation's own `InvitationMailRequestedV1Consumer` takes it from the host's durable local queue (`local://…invitationmailrequestedv1/`). A module of the host consumes it, so Wolverine sends it to that local queue and not to the broker.
  - **It is kept off the broker altogether.** A first version relied on that local routing alone, but `BrokerBindingsTests` found that RabbitMQ's conventional routing still declared an exchange `…Contracts.Organisation.InvitationMailRequestedV1` and bound the `organisation` queue to it, because the convention discovers a listener for every type a handler consumes: anyone with broker credentials could publish one and have the host mail an invitation. `src/Host/Wiring/Messaging.cs` now excludes from the convention (`ExcludeTypes`, listeners and senders alike) every message type that a module of the host both publishes and consumes: a type handled by one of the host's modules' `*Consumer` classes whose contract is in the Contracts namespace of one of the host's modules (`src/Contracts/<Module>/`). It names no type and no module, so it holds for every host. The exclusion removes the exchange and the binding, so nothing the broker routes reaches the local consumer. A message published straight to the service's own queue still dispatches by type. For `InvitationMailRequestedV1` the worst case is a re-issued link to the same invited address, and the consumer's re-read still checks it. An event of another service (Compliance's `MembershipStartedV1` from Organisation) is still bound to the consumer's queue.
  - **Wolverine's request/reply queue is not declared** (`DisableSystemRequestReplyQueueDeclaration()`). Every host declared `wolverine.response.<id>` and listened on it, and that listener dispatches any envelope by its message type, so review 6012234980 (F1) forged an `InvitationMailRequestedV1` onto it and the host issued a link. No service asks another for a reply over the broker (no `InvokeAsync<T>` across it, no `RequestReply`), so nothing used the queue. Organisation consumes no other service's event, so it now has no broker listener at all.
  - **A host-local type that arrives from the broker is not refused by the handler.** A guard that checked `Envelope.Destination` for `local://` was considered and left out: Wolverine 6.64.0 does not document how the durable inbox restores an envelope's destination when it recovers envelopes after a restart, schedules a retry or replays a dead letter, and a guard that misread one of those paths would drop or dead-letter a legitimate invitation mail without SMTP ever failing, the loss this ADR exists to prevent. What keeps a forged message out is that no broker queue of the host delivers these types. **Any future broker listener on such a host (a queue of its own, a reply queue turned back on) reopens the path, and must not accept these types**; a test like `BrokerBindingsTests` has to cover it.
  - **Excluding a type from the broker convention removes its broker sender too.** If a module ever consumed one of its own events that another service also consumes, that service would stop receiving it, silently. No module does today: `InvitationMailRequestedV1` has no other consumer, and its doc comment says a module that needs to know about invitations gets an event of its own. An architecture rule that fails when a host-local type has a consumer in another service is proposed as a follow-up.
  - The consumer loads the pharmacy. If the current version is already mailed (`InvitationMailedFor` is the current `InvitationVersion`) it sends nothing and logs it at Information. Otherwise it issues a fresh link with `IssueInvitationLink`, composes the mail (so a missing `Frontend:BaseUrl` fails before anything is written), commits with `CommitAsync`, reads the membership again (below), sends, then records the version as mailed (`RecordInvitationMailed`) and commits with `TryCommitAsync`. Commit before send: a mailed link is never dead on arrival, and a commit that loses its race throws before anything is mailed. A send that fails takes its link back with `WithdrawInvitationLink`, commits that, and rethrows the send's failure, on **any** exception except a `MailNotSentException` or `MailSendTimedOutException` that says the mail may have been delivered; that one keeps its link and throws. A withdrawal that fails is logged as a Warning, and the send's failure still goes on; one that lost its race to a renewal, accept or revoke, which cleared the links itself, is logged at Information. So an SMTP outage, a server that refuses, or a missing setting adds no link: every attempt fails, Wolverine retries and dead-letters the message as before, and a replay finds the links as they were. After a send that returned nothing throws: a record that is refused, loses its race or throws (a dropped database included) is logged as a Warning naming the membership and swallowed, since a throw would mail the version again. At the link cap, which only links whose mails may be out reach, the consumer sends nothing, issues no link and throws `InvitationLinkLimitReachedException`, whose message names only the membership id and the code and which keeps no inner exception, so the message dead-letters and stays visible until a manager renews the invitation. No retry can succeed before that renewal, so the exception implements `IPermanentMessageFailure` (`src/BuildingBlocks/Messaging`), and the host's failure policy (`src/Host/Wiring/Messaging.cs`) moves a message whose consumer throws such an exception to the dead letters on its **first** failure, by a rule added before `OnAnyException().ScheduleRetry(...)`, since Wolverine takes the first rule that matches (#193's review, follow-up 2). Before, it walked the whole retry ladder, about a minute of attempts that each found the cap again. The marker names no module and the host names no module's type; any consumer may throw one for a failure that only a change by hand can clear, and never for one a dropped connection or a lost race can cause.
  - **After its commit and before the send, the consumer reads the membership's status again** through `IPharmacyStore.FindAsync`, which reads the database with `AsNoTracking`, not the copy its own DbContext tracks (a second tracked load would hand back that stale copy). It sends only if the membership is still `Invited`, **at the same `InvitationVersion`, with the hash this run stored among its links**, and otherwise drops the mail with an Information log naming the membership id. A revoke, accept or end committed between the link's commit and the send therefore mails nothing, and so does a renewal, which leaves the membership `Invited` at the next version and clears its links (review 6012234980, F2); either way the link this run would mail is already dead, and the run that holds the current version's link (the renewal's own mail) mails it. Another run of the same version adds its link beside this one and kills none. **The re-read sits inside the withdraw path** (#193's review, follow-up 1): a re-read that throws (a dropped connection, a timeout, a cancellation) sent nothing, so it takes back this run's link, commits that and rethrows the same exception, exactly as a send failure that cannot have delivered does. Before, each such failure left a committed link that no mail carried, so repeated re-read failures reached the cap and dead-lettered the message with nothing sent.
  - A failure throws: except an `IPermanentMessageFailure` (the link cap, above), which dead-letters at once, Wolverine retries it at 1, 2, 4 … 32 s, then dead-letters it in the organisation database's `wolverine.wolverine_dead_letters`, from which `replayable = true` delivers it again; published, that replay runs as the module's database role, never as the administrator (ADR 0005).
  - An invitation that is no longer open (revoked, accepted, ended) is dropped with an Information log, one that has run out with a Warning, a missing pharmacy with a Warning; each names only the membership id and the error's code. The consumer publishes nothing, so nothing loops.
  - **No deduplication on `Metadata.EventIdentifier`.** The mail cannot be atomic with the database: recording the event id in the hash's commit would skip, on retry, a send that failed after that commit, and lose the mail. The key is the invitation's version and its mailed mark instead: a redelivery after the mark is committed sends nothing, and a retry before it (the send failed, perhaps after the server took the mail) mails a second link that joins the first, so whichever mail the invitee opens works.
- **Invitation mail is limited** (#158), so a manager, or a script with a manager's token, cannot make the service mail without end through the sender domain, whose reputation it spends:
  - **What counts as one mail:** each successful invite and each successful renewal, the requests that publish `InvitationMailRequestedV1`. The consumer's retries and re-issued links do not count; `MaxInvitationLinksPerVersion` (5) already bounds them. A founder is never mailed and never counted. A refused request counts toward neither limit, and changes and raises nothing.
  - **Renew cooldown, N = 10 minutes per invitation.** `Membership.InvitationRequestedAt` (column `memberships.invitation_requested_at`, nullable) is when the newest mail was requested, set by the invite and each renewal. A renewal before `InvitationRequestedAt + N` is refused, `InvitationRenewedTooSoon` (`organisation.invitation-renewed-too-soon`), retry at `InvitationRequestedAt + N`. The cooldown has a ceiling (#294), the recipient rule's predicate exactly: a renewal is refused only while `now < InvitationRequestedAt + N` **and** `InvitationRequestedAt < now + N`. A stored instant N or more ahead (`now + N` itself included) is not trusted, so the renewal goes on to the remaining checks and, if it passes them, stores `now` and heals the row; one less than N ahead is trusted, so a faulty instant blocks renewing for less than two cooldowns. The renew handler logs such an instant as a Warning before any limit is checked, so also when another limit then refuses (`InvitationMailClock.WarnWhenRequestedAhead`), naming the pharmacy id, the membership id, the stored instant and `now`, never the address. A membership without the instant (a founder, an invitation stored before the migration) has no cooldown. The cooldown applies to renewals only; an invite is a new membership, and invite-revoke-invite loops are caught by the daily cap and the recipient cooldown (#265).
  - **Daily cap, M = 50 per pharmacy per UTC calendar day.** The pharmacy keeps one tally, `Pharmacy.InvitationMailDay` (`pharmacies.invitation_mail_day`, `date`, nullable: the UTC day of its latest counted mail) and `Pharmacy.InvitationMailsThatDay` (`pharmacies.invitation_mails_that_day`, `integer NOT NULL DEFAULT 0`). On the same UTC day at M, a mail is refused, `TooManyInvitationsToday` (`organisation.too-many-invitations-today`), retry at the next 00:00 UTC; otherwise a new day restarts the tally at 1 and the same day adds 1. A stored day of tomorrow (a request that read the clock just before 00:00 UTC and committed after one that read it just after) is the counted day: the mail adds to that day's tally and the day stays. A stored day before today, or beyond tomorrow, counts for nothing: today's tally starts afresh at 1. So a stored day far ahead (a hand-edited row, a stored `9999-12-31`) never locks invitation mail; it gives up at most that row's tally. The invite and renew handlers log a stored day beyond tomorrow as a Warning naming only the pharmacy id, the stored day and today (`InvitationMailClock`), since only a hand-edited row, or a database clock that moved back (a failover, a restore), puts it there. The day is the UTC calendar day (00:00 UTC is 01:00 or 02:00 in Germany), so no time zone data is needed in the containers. Migration `AddInvitationMailLimits`, without a backfill.
  - **The mail limits take their time from the database's clock, not each instance's `TimeProvider`** (#158). The invite and renew handlers read `IDatabaseClock.NowAsync` (Application), which `DatabaseClock` (Infrastructure) answers with PostgreSQL's `now()` through the module's `DbContext`, and use that instant for the whole operation: the cooldown, the daily cap, `InvitationRequestedAt` and the 14-day expiry. Why: the tally is one stored (day, count) pair shared by every instance, and no rule over one pair reconciles instance clocks days apart. Read on each instance's clock, a stored day far ahead either restarts the tally (two instances days apart alternate 1, 2, 1, 2… and lift the cap) or, clamped, locks the pharmacy's mail until the calendar catches up, since a refusal writes nothing. With one clock, the only skew left is a request racing 00:00 UTC by the length of a transaction, which the tomorrow rule above absorbs. It costs one `SELECT now()` round trip per invite or renewal. Accepting an invitation and issuing its link take the database's clock too (#294): `AcceptInvitationHandler` and `InvitationMailRequestedV1Consumer` read `IDatabaseClock.NowAsync`, so the expiry is stamped and checked on one clock, and a host whose clock is days off neither accepts a run-out invitation nor drops an open one's mail. Accept reads it after the verified-address check and the lookup by token hash, so an unverified account or an unknown link costs no clock read; that instant also starts the membership (`StartedAt`, `MembershipStartedV1`). So `MembershipStartedV1.StartedAt` comes from the database's clock (#294), while its `Metadata.OccurredAt` is the host's `TimeProvider`: one event carries two clocks that may differ by the host's skew. Of its consumers (Certification, Compliance and Learning), only Certification's `MembershipStartedV1Consumer` reads a time, and it reads `StartedAt` alone; none reads `OccurredAt`. Ending a membership and registering a pharmacy stay on the host's `TimeProvider`: they are no invitation instants. `Retry-After` counts from the instant of the refusal on the database's clock, not from the host's (below), so it is exact whatever the instance's skew.
  - **Order of checks** (as amended by #265): invite: pharmacy found (404), capability (403), already member or invited (409), the pharmacy's daily cap (429), the recipient cooldown (429), the sender's daily cap (429). Renew: pharmacy found (404), capability (403), no open invitation (404), the invitation's cooldown (429), the pharmacy's daily cap (429), the recipient cooldown (429), the sender's daily cap (429). So a revoked invitation renewed a moment after its invite still answers 404 `organisation.no-open-invitation`, an address invited again in the same pharmacy still answers 409, and only the first refusal that applies is reported.
  - **The counts live on the `Pharmacy` aggregate, in Organisation's database, never in memory**, and need no lock, serializable transaction or unique constraint: every counted mail changes the aggregate, whose root carries the `xmin` row version (docs/adr/0002). Two concurrent invites or renewals of one pharmacy load the same tally; the first commit moves the row version, the second updates no row and answers 409 `organisation.pharmacy-changed`, as concurrent invites always have. So the tally never exceeds M and no race bypasses a cooldown, on any number of instances.
  - **The refusal is 429 with `Retry-After`.** `PharmacyFailures.From` maps both errors with `ApiError.RetryLater(error, retryAt, refusedAt)` (`src/Kernel`), a `RetryLaterFailure` with status 429, the instant it may be retried at and the instant it was refused at, the domain's `now`, which for invite and renew is the database's (#294). The `To*HttpResult` methods (`src/BuildingBlocks/Http/Wiring/ResultHttpExtensions.cs`) put them in the problem as `retryAt` and `refusedAt` (ISO 8601, UTC) beside `code`, and `RetryAfterHeaderFilter`, on every module's route group (`ModuleEndpoints.MapModuleEndpoints`), sets `Retry-After` to `max(1, ceil(retryAt - refusedAt))` whole seconds, without reading the host's clock. `refusedAt` stays visible: it is the instant `retryAt` was computed from, on the same clock, so a client can compute the wait without trusting its own clock, and it discloses nothing but the database's time. A refusal without it (the two-argument `ApiError.RetryLater(error, retryAt)`, which other modules may use) carries no `refusedAt` and is counted on the host's `TimeProvider`, `max(1, ceil(retryAt - now))`. Invite and renew declare the 429 in the OpenAPI document.
  - **Accepting is limited per user** (#158): `POST /organisation/invitations/accept` admits a user (the token's `sub`) at most 10 times a minute and 100 times a day, `Organisation:AcceptLimit:PerMinute` and `Organisation:AcceptLimit:PerDay` (whole numbers from 1; any other value stops the host, naming the key). Over it the answer is 429 `organisation.accept-limit-reached` with `Retry-After`, and the accept does not run. It uses ADR 0020's building block (`AddUserRateLimit` in `OrganisationModule.AddServices`, `.RequireUserRateLimit(OrganisationLimits.AcceptInvitation)` on the endpoint), which counts in the service's memory, per replica, and starts afresh on a restart. That is acceptable here and not for the mail limits: the token is 256 random bits, so no rate makes guessing one feasible, and the limit only caps how many lookups one user can make the database do; nothing is sent and no third party's reputation is spent. The mail limits bound mails that leave the system, on any number of instances, so they live in the database (above).
  - **Configuration**, read once at start-up (docs/adr/0007, `OrganisationLimits`): `Organisation:InvitationLimits:RenewCooldownMinutes` (whole number 1 to 1440, 10 without it) and `Organisation:InvitationLimits:MailsPerPharmacyPerDay` (whole number 1 to 10000, 50 without it). Any other value stops the host, naming the key. The module registers the result as `InvitationMailLimits`, which the invite and renew handlers take by constructor and pass to the aggregate, which has no default for it.
- **Invitation mail is also limited per address and per sender, across pharmacies** (#265, the owner's decision of 2026-11-23). Each mail counted above (an invite or a renewal; never a founder, a retry, an accept, a revoke, a change or an end) also counts on its address and on the person who requests it, in the same commit as the pharmacy (`InvitationMailCounting`, Application). A revoke gives nothing back, and a refused request counts toward no limit.
  - **Recipient cooldown, R = 10 minutes per address.** Aggregate `InvitationRecipient`, table `organisation.invitation_recipients (id, last_mailed_at)`. The id is derived from the address and the address is not stored: `InvitationRecipientId.For` is a name-based UUID version 8 (RFC 9562) over SHA-256 of Organisation's namespace `3f9c2a71-8d4e-4b06-a5e2-7c1d9b0f6e38` (big-endian) and the UTF-8 address as stored (trimmed, lower-case), first 16 bytes, version 8, variant 10; namespace and layout must never change. A mail is refused while `now < LastMailedAt + R` and `LastMailedAt < now + R`, code `organisation.recipient-mailed-recently`, retry at `LastMailedAt + R`; a stored instant R or more ahead is not trusted and is replaced by `now`. The ceiling is tested first and nothing is added to a stored instant it does not trust (#326), so a `last_mailed_at` within R of `9999-12-31` is replaced too instead of overflowing. Such an instant is logged as a Warning (`InvitationMailCounting`, #326) that names only the stored instant and `now`, neither the address nor the recipient id, since the id is a pseudonym anyone who knows the address can recompute (below). Key `Organisation:InvitationLimits:RecipientCooldownMinutes` (1 to 1440, 10 without it).
  - **Sender daily cap, S = 100 per person per UTC day.** Aggregate `InvitationSender`, table `organisation.invitation_senders (person_id, mail_day, mails_that_day)`, one row per person. The sender is who makes the request (`InviteMember.By`, `RenewInvitation.By`), so a renewal counts on the manager who renews. The tally follows the pharmacy's rule, shared as `UtcDay.CountingDay`; a stored day beyond tomorrow is logged as a Warning naming the person id and both days, never the address, and today's tally restarts at 1. Code `organisation.too-many-invitations-sent-today`, retry at the next 00:00 UTC. Key `Organisation:InvitationLimits:MailsPerSenderPerDay` (1 to 10000, 100 without it).
  - **Their rows are saved with the pharmacy** in its `TryCommitAsync`, and each carries the `xmin` row version (docs/adr/0002), which stays as a backstop. Neither row races (#369 for the sender, #375 for the recipient): `IInvitationRecipientStore.LoadForMailAsync` and `IInvitationSenderStore.LoadForMailAsync` (Infrastructure's `InvitationRecipientStore` and `InvitationSenderStore`, through `InvitationMailRows`) begin the context's transaction when none is open, insert the row when it is missing (`INSERT … ON CONFLICT DO NOTHING`: a recipient last mailed at the Unix epoch, `InvitationRecipient.NotYetMailed`; a sender's tally of zero on today, `InvitationSender.NotYetMailed`), lock it with `SELECT … FOR UPDATE` until the transaction ends, and only then load it. A second request for the same row waits at the insert or the lock and counts on the row as the first committed it. So a sender's very first two mails both count on one new row, and concurrent counts on an existing sender row wait for each other instead of one answering 409; the tally stays exact and the daily cap applies to each in turn. Two requests mailing one address at once, from two pharmacies or one, both new to the address included, likewise count one after the other: the second finds the first's mail and, within the cooldown, is refused with 429 `organisation.recipient-mailed-recently`, as it would be alone, never 409 `already-exists`. The cooldown keeps its guarantee: the address gets one mail. The second read the database's clock before it waited, so its `Retry-After` may exceed R by that wait, rounded up to a second; its `retryAt` is the exact instant.
    - **One lock order.** `InvitationMailCounting` holds the recipient's row first and the sender's second, and the save then writes the pharmacy's rows; no request takes them in another order, so two requests never wait for each other's rows (a deadlock). A new row an invitation mail counts on joins this order at a fixed place, stated here and in `InvitationMailCounting`.
    - **A bounded wait.** Before the first insert the transaction sets `SET LOCAL lock_timeout = '5s'` (`InvitationMailRows.LockTimeout`; it ends with the transaction, so the pooled connection keeps nothing). A statement that waits longer for a lock, at the insert, the `FOR UPDATE` or the save, fails with 55P03: the store answers it as a lost race (`SaveDeadlocked`), and so does `ModuleUnitOfWork.TryCommitAsync` at the save, so the request answers 409 `organisation.concurrent-save` (try again) with nothing saved, never 500 and never hanging behind a stuck transaction.
    - **A refusal ends its transaction at once.** A request the count refuses (a cooldown, a cap, a lock timeout) rolls its transaction back before it answers (`IOrganisationUnitOfWork.RollbackAsync`), so a request waiting for a row it held goes on without waiting for the scope to end (review of #395). Any other request that commits nothing (a save that lost its race) leaves its transaction open until the request's scope disposes the context. Either way its locks and any row it inserted are rolled back, so no recipient or sender row is ever committed without a mail counted on it. The Wolverine outbox and the domain events of the command use that same transaction, which the unit of work commits.
  - Both rules take the database's clock, like #158's. Both errors map through `PharmacyFailures.From` to `ApiError.RetryLater`, so the answer is 429 with `Retry-After` and `retryAt`, as above. Migration `AddInvitationRecipientsAndSenders`.
- **Uniqueness is backed twice.** `Pharmacy.Invite` refuses an address that is invited or active (409 `organisation.already-member-or-invited`). A partial unique index on `(pharmacy_id, email)` where `status IN ('Invited', 'Active')` refuses the row from a writer past that check (409 `already-exists`). The index excludes revoked rows, so a revoked address may be invited again.
- **The invite's `201` names `/organisation/pharmacies/{id}`**, which `GET` answers; an invitation has no resource of its own.

## Alternatives

- **A domain-event reaction (what this replaced).** `SendInvitationMail` reacted to `MemberInvited` after the commit, during the request, with the raw token in the event. It lost mail: a failed send was only logged and never retried; a request cancelled after the commit dropped the mail, because the send honoured the request's token; and a deployment without `mail`, `mail-from` or `frontend-url` answered 201 and mailed nothing. It also broke AGENTS.md's rule that work which must not be lost is an integration event. It had been chosen to keep the raw token out of Wolverine's tables; issuing the token at send time does that without the reaction.
- **Reusing `RenewInvitation` at send time.** The handler would make a token it throws away, `MemberInvited` would keep carrying a raw token in memory, the expiry would run from the send instead of the manager's request ("Einladung läuft nach 14 Tagen ab"), and a late message (a dead letter replayed weeks later) would revive an invitation the manager let lapse. Rejected for `IssueInvitationLink`, which changes no expiry and refuses an invitation that has run out.
- **Deduplicating on the event identifier.** Rejected: it loses the mail whenever the send fails after the hash's commit (see Decision).
- **One link per invitation, replaced at each issue (what the amendment replaced).** A retry after a send that reached the server killed the link the invitee already held, and a retry that then could not send left the invitee with no working link at all. Rejected for one set of links per version, capped, cleared by a renewal, accept or revoke.

## Consequences

- **An SMTP outage delays the mail instead of losing it.** A send refused before the server took the mail withdraws its link, so the outage never reaches the link cap. It is retried for about a minute, then dead-lettered in the organisation database's `wolverine.wolverine_dead_letters` and replayed with `replayable = true` once SMTP is back. Nothing alerts anyone to a dead letter yet; it is visible in that table and the service's log.
- The invite and renew requests no longer wait for SMTP; the mail follows within moments.
- **An invitation has no working link until its mail is out**: an `Invited` row may have no row in `invitation_links`, and accepting by hash matches none until the consumer has committed one.
- The expiry runs from the manager's request. A message that arrives after the expiry is dropped with a Warning, and the manager renews.
- A redelivery after the version was recorded as mailed (the process died between that commit and Wolverine marking the envelope handled) sends nothing. A failure after `SendAsync` returned, in `DisconnectAsync`, counts as sent. A send that failed in a way that leaves open whether the server took the mail is retried, and the retry mails a second link that joins the first; neither mail's link is dead.
- **Two gaps remain, in which both links work and nothing is lost.**
  - **The send returned, but recording it failed.** The failure is logged and swallowed, so this run is not retried, but the mark is not stored, and a later redelivery of the message mails the version again. SMTP gives no way to make a send idempotent, so this is accepted; the link cap bounds it.
  - **Two runs of one version that overlap can each mail.** The mark is read before the link is issued and recorded after the send, so two runs of the same version that overlap (an invite's message and a quick renewal's, each run for the version it finds open, or a parallel redelivery) can both pass the check and both mail before either records it. "One mail per version" therefore does not strictly hold; each such run uses up one of the cap's links.
- **The re-read narrows the revoke and renewal window; it does not close it.** A revoke or renewal that commits after the re-read and before the SMTP server accepts the mail still lets the mail go out, with a link that is dead on arrival because the revoke or renewal cleared its links. That window is the send's own duration (at most the 10 s bound); closing it needs a lock held across SMTP, which is rejected as for ordering above.
- **A burst has a margin, not a guarantee.** Each consumer run bumps the pharmacy's row version, so parallel invitations of one pharmacy race and the losers are retried. In `OrganisationInvitationBurstTests` 10 parallel invitations all made it within the 7 attempts, with 22 concurrency conflicts and about 32 s of the retry wait to spare. More invitations of one pharmacy at once, or a slower host, can exhaust the attempts and dead-letter a mail without any SMTP fault; such a dead letter is replayed with `replayable = true` like any other.
- **Mails can arrive out of commit order.** Two quick requests (invite then renew, or two renews) give two consumer runs. The row version serialises their commits, the stored links are always the newest version's, and every committed token is mailed after its commit, so only the newest version's links work. The re-read compares the stored version and links with the run's own, so an earlier version's run whose link a renewal has already cleared before its re-read mails nothing. But when the later run commits after the earlier run's re-read, and the earlier run's SMTP send takes longer than the later run's retry wait (at least 1 s) plus its own send, the newest mail to arrive holds the dead link, and the invitee asks for a renewal. Closing that needs a sequential queue for this message type, a per-module line in `src/Host/Wiring/Messaging.cs` that AGENTS.md forbids, or a lock held across SMTP; accepted.
- **The consumer's write can make a manager's concurrent request on the same pharmacy answer 409 `organisation.pharmacy-changed`**: it bumps the pharmacy's row version, so a request that loaded the pharmacy before the consumer's commit and commits after it loses its race (ADR 0002's accepted price). The integration tests' `InviteAsync` waits for the invitation's mail before acting on the pharmacy for this reason.
- **Only a service that sends mail fails to start outside Development without `ConnectionStrings:mail`, `Mail:From` and `Frontend:BaseUrl`** (#158); before, every service did, because every service's host registered the mail. The AppHost hands all three to the services whose project says `<SendsMail>true</SendsMail>` alone (Organisation today), and published, only those apps reference and are granted `mail-connection-string`. A module that starts sending mail calls `AddModuleMail` in its `AddServices` and sets the flag in its host's project; `EveryHostThatSendsMailSaysSo` fails until both are done. Deploying needs `smtp-host`, `smtp-username` and `smtp-password` (URI-safe) for the server Keycloak uses too, `smtp-from` set to an address that server may send from, and `frontend-url` set to the web app's public URL; the connection string is composed from them into the Key Vault, so nothing else is set by hand. `AppHostParametersTests` holds the run-mode wiring and that the published sender has no default; no test yet holds the published `mail` Key Vault reference, which was read in the published Bicep by hand, and nothing has yet sent a mail from a deployment (#129).
- **No other service receives `InvitationMailRequestedV1`, and the broker routes none to the host.** Wolverine routes an event that a module of the host consumes to the local queue only (`ConventionalLocalRoutingIsAdditive()` is not set), and the host's broker convention excludes it, so there is neither an exchange nor a binding for it. A message published straight to a queue the host listens on still dispatches by type; for this event the worst case is a re-issued link to the same invited address, which the consumer's re-read still checks. The request/reply queue is not declared, so Organisation, which consumes no other service's event, has no broker listener at all. A broker-delivered host-local type is not refused by the handler (see Decision), so a future broker listener on the host would reopen the path. A module that needs to know about invitations gets an event of its own; the event's doc comment says so. The same holds for any later event a module of a host both publishes and consumes.
- **The tightened guards also run when EF reads a stored value back.** `PharmacyName` now refuses control and bidi characters, and `EmailAddress` refuses the RFC 5322 specials. A row stored under main's earlier guards with such a value fails to load, and the request answers 400. No database outside a developer's machine can hold one: nothing was deployed before #138 (#114 and #129 are open). A developer database with such a row: delete the postgres volume, or fix the row by hand.
- A local database that ran the two earlier migrations of this PR (`AddInvitationTokenHashAndUniqueness`, `AddInvitationUniqueness`) is rolled back to `AddPharmacyRowVersion` first, or its postgres volume deleted.
- **Renewals faster than 10 minutes wait**: the manager gets 429 with `Retry-After` and renews once it has passed. A pharmacy that onboards more than 50 people in a UTC day spreads it over days, or the deployment raises `Organisation:InvitationLimits:MailsPerPharmacyPerDay`.
- **The tally starts at zero with the migration, and an invitation stored before it has no cooldown** until its next renewal, which sets `invitation_requested_at`; it can be renewed once at once. Nothing was deployed before, so this touches developer databases only.
- **A fixed UTC-day window lets up to 2 × M mails out within minutes around 00:00 UTC**: M at the end of one day, M more at the start of the next. That matches "per day", and is accepted; a sliding 24-hour window would need a row per mail.
- **A database clock that moved back loses or keeps what it stored ahead** (#294). The database's clock is the one clock invitations trust, so a failover to a server whose clock is behind, or a restore, can leave stored days and instants ahead of `now`. Moved back by more than a day or a cooldown, it discards the affected tallies and cooldowns, each logged as a Warning: a mail day beyond tomorrow restarts at 1, so up to M (or S) more mails go out that day, and a request time or recipient instant a cooldown or more ahead is not trusted. Moved back by less, it keeps them until it catches up, which is bounded: the tally counts on tomorrow's day, and a cooldown lasts less than two cooldowns. Invitations live longer by the amount it moved back, since their expiry was stamped on the clock before. A hand-edited row has the same effects; only someone with write access to the database can do it, and the Warnings name the pharmacy, the membership or the sender; the recipient's names only the two instants.
- **The recipient cooldown discloses that an address was mailed recently** (#265). A manager of one pharmacy who invites an address that another pharmacy, or another manager, mailed within the last 10 minutes gets 429 `organisation.recipient-mailed-recently`, and so learns that the address got an invitation mail within that window; not where, from whom or for which pharmacy, and the answer names no other pharmacy, membership or address. The window is not blurred: `retryAt` and `Retry-After` are `LastMailedAt + R` to the second, so the refusal tells the exact instant the address was last mailed. Rounding `retryAt` for this code was weighed and not done (review of #300); it would hide the instant but not the fact. The sender cap discloses nothing about others: it counts only the caller's own mails. This follows from the owner's choice of a 429 with the module's own code over a silent drop, and **the owner accepted this disclosure** (2026-11-23).
- **One address can be held hostage** (review of #300). The cooldown is per address across every pharmacy, so a verified user who manages a pharmacy can invite an address the moment each cooldown ends and revoke the invitation at once; a legitimate pharmacy's invitation of that address then answers 429 almost every time. A manager of one pharmacy covers about 8.3 hours of it a day, since the pharmacy's cap of 50 mails is reached first (50 × 10 minutes); 16.7 hours, the sender's cap of 100, needs two pharmacies or a second sender. Two senders, each managing two pharmacies, cover a whole day (three with one pharmacy each), at the cost of one mail to the victim every 10 minutes. This stays as #265 specified (the orchestrator's default, open to the owner's overruling) while only verified managers can invite; before self-registration (#13) goes live it is revisited, with the options of not counting a mail whose invitation was revoked within some minutes, or keying the cooldown per address and sender, which weakens the protection against one address getting many mails.
- **A manager's concurrent invites or renewals, even in different pharmacies, now wait for each other on their sender row** (#369): each holds the row from its count to its commit, so they count one after the other and each answers as it would alone; a sender's very first two mails at the same instant both count on the one row the first inserts, and neither answers 409. Holding the row lengthens each such request by the other's commit, which only one sender's own requests share. Two requests mailing one address at once likewise wait for each other on its recipient row (#375): the second is told the address was mailed recently (429), not 409. It also gets that answer where, alone, it would have been told the address is already invited (two invitations of one address in one pharmacy, which both pass the pharmacy's check before either commits); both refuse it, and a retry after the cooldown gets the pharmacy's 409. A request waits at most 5 seconds for either row, then answers 409 `organisation.concurrent-save`, so a transaction stuck on a row delays others for that long at most.
- **Only the first refusal is reported**, so a `Retry-After` may be shorter than the wait a later limit then imposes.
- **The recipient table holds a pseudonym of every address ever mailed an invitation** (unsalted SHA-256, so not anonymous) and one instant; it adds no clear-text copy, since `memberships.email` holds the address already. Rows are not purged. A future erasure of a person's data must also delete `InvitationRecipientId.For(address)`.
- **The new tallies start empty with the migration**, so mails before it count toward neither; as for the pharmacy, a fixed UTC day lets up to 2 × S mails of one sender out around 00:00 UTC.
- **The integration run raises S to 1000** (`AspireFixture.InvitationMailsPerSenderPerDay`), since every invite and renewal as `owner` in a run counts on one tally; the boundary tests reach it as `editor-b`, whom only they invite as. The classes that invite or renew as `owner` share the `InvitationSenders` collection, so no class's request waits on `owner`'s row for another's, and a test that seeds, reads or deletes that row (#369) sees only its own requests.
- **The accept limit is per replica and starts afresh on a restart**: with n replicas a user gets up to n times the limit, and a restart gives everyone a fresh budget. With one replica (docs/adr/0005) it holds as configured.
- **UTC midnight is 01:00 (winter) or 02:00 (summer) German time**: a pharmacy at its cap late in the evening waits until then, not until local midnight.
- Self-registration in the realm (`registrationAllowed`, `verifyEmail`) is #13's, per the owner.
- "E-Mail-Erinnerungen nach MVP 1" can reuse `IMailSender`; `MailSdkStaysInBuildingBlocks` keeps MailKit and MimeKit out of the modules.
