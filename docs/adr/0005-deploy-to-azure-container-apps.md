# 0005: Deploy to Azure Container Apps from the AppHost

**Status:** Accepted (#114 PR-A: the publish model; PR-E: keyless blobs (ADR 0002), each app's secrets alone, encrypted peer traffic; PR-B: migrations as each service's init container, a database role per module that each service logs in as; PR-C: Keycloak's published image and realm, its own role and schema, the auth proxy and the public issuer; PR-D: the edge serves the SPA; PR-F: the deploy workflow, `deploy.yml`; the parameter checks, the rollback ADR and ADR 0011's D3 follow in later parts of #114 and are added here then)

## Context

- Issue #114 asks for a deployment of the whole application to Azure, in two environments, `staging` and `production`, from the one composition root, `src/AppHost` (AGENTS.md, "Project structure"): nothing hand-written beside it, no second description of what runs where.
- Aspire 13.6.5 publishes an AppHost as Bicep (`aspire publish -e <environment>`) and deploys it (`aspire deploy`). `Aspire.Hosting.Azure.AppContainers` turns every compute resource into an Azure Container App in one Container Apps environment; `Aspire.Hosting.Azure.PostgreSQL` and `Aspire.Hosting.Azure.KeyVault` provision a Flexible Server and a Key Vault.
- Until now nothing published. The AppHost could not even be published: the web app's Vite dev server is a build-only container that nothing consumed, which fails Aspire's validation, and every secret parameter was one Aspire generates and keeps in a developer's user secrets, which a deployment has none of.
- By default Aspire hands a secret to a Container App as a secure Bicep parameter, stored as a plain Container App secret: the database passwords and URIs (`DATABASE_PASSWORD`, `DATABASE_URI`), the broker's connection string, the Keycloak administrator's password, the model's key. Whoever may read the Container App's configuration may read them.
- On 2026-11-22 the owner decided OQ1, one `migrations` job with a manual trigger that never runs, whose image runs as each service's init container, and OQ8 (c), a database role per module, created by that init container, that each service logs in with instead of the server's administrator.
- The owner decided on 2026-11-21: Azure Container Apps; a Key Vault for every secret; PostgreSQL as a Flexible Server, Burstable for staging and General Purpose for production, without high availability or geo-redundant backups; one replica always running, nothing scaled to zero; everything planned for Germany West Central; and, for B8, that a second deploy may make no infrastructure or configuration change.

## Decision

- **Publish mode has one Container Apps environment, `aca`** (`src/AppHost/Wiring/ContainerAppsEnvironment.cs`), without the Aspire dashboard (`WithDashboard(false)`): the dashboard would show logs and traces, personal data among them, on a public `azurecontainerapps.io` URL. Logs stay in the environment's Log Analytics workspace. Run mode has no environment and runs as before.
- **Every compute resource is a Container App that keeps one replica.** Aspire 13.6.5 already writes `minReplicas: 1`; Keycloak and RabbitMQ also get `maxReplicas: 1` (`WithSingleReplica`), since neither is set up to run twice at once. Only the edge, `host`, and the auth proxy in front of Keycloak, `auth`, have external ingress (`WithExternalHttpEndpoints`); the services, Keycloak and the broker are internal.
- **The edge serves the SPA** (#114 PR-D). Run mode keeps the web app's dev server on 5173. Published, `web` is built once from the pnpm workspace (`web/Dockerfile`, context `web/`, so the lockfile is in it; a `FROM scratch` last stage holding `/app/dist` alone, without an entrypoint, so it is no Container App), and `host.PublishWithContainerFiles(web, "./wwwroot")` copies the build into the edge's image (`src/AppHost/Wiring/WebBuild.cs`). Aspire's experimental switch that disables the build-only container check is not used. The edge (`src/Edge/Wiring/`):
  - **`/api` is a prefix, nothing more** (`ApiPrefix.cs`): `UsePathBase("/api")` and then `UseRouting()`, before authentication, so `/api/me` is `/me` and `/api/<module>/...` reaches the service as `/<module>/...` with its query and token. Only the whole segment is stripped (`/apime` is 404).
  - **`GET /config.json`** (and `/api/config.json`, where the generated client asks) answers `FrontendConfiguration`, `{"oidcAuthority": <Authentication:Authority>, "clientId": "pharma-training-web"}`, anonymously, since the browser reads it before it signs in (`FrontendConfigurationEndpoint.cs`). The web app loads it through the generated `getConfigJson()` before it mounts (`web/app/src/bootstrap.ts`), checks it with Zod, and renders an alert instead of the app when it fails, so one build serves every environment; `VITE_OIDC_AUTHORITY` is gone.
  - **X1: the SPA fallback is for page loads only** (`SpaHosting.cs`, only where the web root holds `index.html`). A `GET` or `HEAD` with `Sec-Fetch-Mode: navigate`, or whose `Accept` lists `text/html`, answers `index.html` with `Cache-Control: no-cache`, before the modules' routes, since the app's pages share their paths with the modules' APIs (`/catalog`). Never under `/api`, never for a file (a last segment with a dot: `/config.json`, `/openapi/v1.json`), `/health` or `/alive`, nor for any other path the edge maps itself. Every other request, a call for data (`Accept: application/json`) or a `POST`, goes on to the module's service as before. Files are served to anyone; `/assets/*`, named by content, with `max-age` of a year and `immutable`, and a missing one is 404. `tests/Edge.Tests` holds this, in process.
  - **What every answer tells the browser** (`Wiring/SecurityHeaders.cs`, the security review of #114): every answer of the edge, its files, its own endpoints, its errors and what it forwards from a service, carries `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, set as the answer starts so they replace a service's own; outside Development also `Strict-Transport-Security: max-age=31536000; includeSubDomains`, sent whatever the request's scheme, since the edge is reached over HTTPS alone through the ingress and a browser ignores the header over plain HTTP. `index.html` carries a `Content-Security-Policy` (`ContentSecurityPolicy.cs`) built once, when `SpaHosting` reads the file: `default-src 'self'`, `script-src 'self'` and the SHA-256 hash of each inline `<script>` the served `index.html` holds (the theme and language before the first paint; Vite copies it byte for byte into `dist/index.html`), never `'unsafe-inline'` or `'unsafe-eval'`; `style-src 'self' 'unsafe-inline'` (components set inline styles); `img-src 'self' data:`; `font-src 'self'` (Inter is bundled); `media-src 'self' blob:`, where the editorial module reads an upload's duration from the file through an object URL; `connect-src 'self'` with the origins of `Authentication:Authority` (the realm's discovery and token endpoints) and, published, `Edge:BlobEndpoint` (the storage account's blob endpoint, which the AppHost passes the edge, for the signed upload URLs, ADR 0002); `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`. Signing in is a navigation to the identity provider, which `connect-src` does not govern. The web app sets Zod to `jitless` (`web/app/src/lib/zodWithoutEval.ts`), or its probe for `eval` before the first parse is reported as a violation on every page load.
- **No region is named in the AppHost.** This ADR's own choice, so one AppHost publishes for any region: `main.bicep` takes `location` as a parameter, and `deploy.yml` sets it to `germanywestcentral` (`Azure__Location`) and refuses a resource group that exists elsewhere.
- **Every publish-mode secret is a parameter the deployment sets, kept in the Key Vault `secrets`** (`src/AppHost/Wiring/DeploymentSecrets.cs`). `postgres-password`, `database-roles-key` (each module role's password is derived from it, below), `keycloak-admin-password`, `messaging-password`, each service's `messaging-<module>-password` (ADR 0011), `azure-openai-api-key`, `smtp-username` and `smtp-password` are secret parameters with no generated value and no published default; each is a Key Vault secret under its own name (the secret's resource is `<name>-secret`, as a resource may not share a parameter's name). Beside them, `postgres-username`, `messaging-username`, `smtp-host` and `smtp-from` have no default, `keycloak-admin-username` defaults to `admin` (each service's broker user is named after its module, with no parameter, ADR 0011) and `azure-openai-deployment` to `gpt-5-mini`, as in run mode. A deployment passes them as `Parameters__<name>`.
- **Every app reads the Key Vault secrets it references and no others** (`src/AppHost/Wiring/SecretAccess.cs`, the owner's answer to OQ8 on #114). The vault's default role (Key Vault Secrets User on the whole vault for every app that references it) is cleared, and `GrantEachAppTheSecretsItReadsAsync` registers, when the AppHost starts publishing and the model is final, a pass that reads each app's environment and arguments for the vault's secrets, directly or inside a connection string, and grants its identity, `<app>-identity` (`AppIdentities.cs`), Key Vault Secrets User on each of those secrets, scoped to the secret, in a Bicep module of its own, `<app>-roles-secrets`. Nothing lists them: a secret or an app added anywhere in the AppHost, before or after the call, is granted with it. Each app's own deployment takes that module's output `grants` (the number of secrets granted, carried as the tag `key-vault-secrets-granted`), which main.bicep passes on, so it starts only after its grants are deployed. A grant on a secret another resource writes (the Flexible Server's connection strings) takes that resource's name, so it is deployed after the secret exists. `WithSecret` refuses, in publish mode, a secret parameter the vault does not hold, naming it. `AppHostSecretAccessTests` holds the services, their init containers, Keycloak and the broker to it, one identity at a time.
- **Migrations run as each service's init container** (`src/AppHost/Wiring/Migrations.cs`, OQ1 and B9 on #114). Run mode is unchanged: every service waits for the completion of a MigrationRunner project of its own, `<module>-migrations`. Published, there is no such resource. The MigrationRunner is one Container Apps job, `migrations`, with a manual trigger (`parallelism: 1`, `replicaCompletionCount: 1`, `replicaRetryLimit: 0`, `replicaTimeout: 1800`), no reference, no environment, no secret and no identity besides the registry's: nobody starts it, and it exists so that the publish pipeline builds and pushes its image. Every service's Container App runs that image (`migrations_containerimage`) as its one init container, `migrations`, before its own container on every new replica, with `Migrations__Module`, `ConnectionStrings__database`, the administrator's connection string `connectionstrings--<module>-database`, and `ConnectionStrings__application`, the module role's `connectionstrings--<module>-database-app`, each as a Key Vault reference. Every service waits for (`WaitFor`) the job, so the pipeline deploys it only after the image is pushed; Container Apps itself ignores waits. The init container's environment is written into the app's Bicep (`PublishAsAzureContainerApp`), never through `WithEnvironment`, which would give it to the main container too.
- **Only the init stage can use the administrator's connection string.** Container Apps has no identity per container, but it has identity lifecycles (`configuration.identitySettings`, `Azure.Provisioning.AppContainers` 1.3.0). The init container's Key Vault references are resolved by a second identity of the app's, `<module>-migrations-identity`, with lifecycle `None`: the platform resolves the secret with it, and no container, init or main, can get a token for it. The service's own `<module>-identity` has lifecycle `Main`. `SecretAccess` grants each init container's identity the secrets it reads alone, in a module of its own, `<app>-migrations-roles-secrets`, whose output the app takes as the tag `key-vault-secrets-granted-migrations`, so the app also deploys after those grants. The registry identity keeps Aspire's default lifecycle; it pulls images, which hold no secrets.
- **A database role per module** (`src/BuildingBlocks/Persistence/ModuleDatabaseRole.cs`, OQ8 c). Given `ConnectionStrings:application`, the connection string its service is to log in with, the MigrationRunner, after the migrations and the event store's schema, ensures the role that connection string names, logged in as the administrator: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS INHERIT CONNECTION LIMIT -1 VALID UNTIL 'infinity'` with that password (an existing role gets the same `ALTER ROLE ... LOGIN ... PASSWORD` on every run, so a new password is picked up by the next run of the init container, and `ALTER ROLE ... RESET ALL` and `ALTER ROLE ... IN DATABASE ... RESET ALL`, so an expiry, a connection limit or a setting that an operator, or the role on itself, set since the last run no longer locks it out); `CONNECT` on its database revoked from `PUBLIC`, so no other module's role connects there; `CONNECT` and `TEMPORARY` on its database and never `CREATE`: `REVOKE CREATE ON DATABASE` runs on every run, so a `CREATE` an earlier run granted is taken back; and on every schema the administrator owns there (the module's EF schema, Marten's and Wolverine's `wolverine`, whatever a module declares) `USAGE`, `SELECT, INSERT, UPDATE, DELETE` on its tables, `USAGE, SELECT, UPDATE` on its sequences and `EXECUTE` on its functions, now and by default for what the administrator creates later, but no `INSERT`, `UPDATE`, `DELETE` or `TRUNCATE` on EF Core's `__EFMigrationsHistory`, which it may only read, so it cannot make the next run skip or repeat a migration; the revoke runs after every run's migrations, so a history table a migration just made loses the default grant in the same run. It gets no `CREATE` on the database or on those schemas and owns nothing in the database, no schema, table or function, so it cannot change the module's schema, nor attach code (a trigger, a rule, a policy, row level security) to anything that would run as whoever touches it, the administrator included: the host never migrates what the MigrationRunner owns. The password never reaches the server: the runner computes its SCRAM-SHA-256 verifier (RFC 5802/7677, 4096 iterations, a random 16-byte salt; `ScramSha256Verifier.cs`) and sends that as the `PASSWORD`, which PostgreSQL stores as sent whatever `password_encryption` says. The role's name and the verifier reach the server as bind parameters and are quoted there (`format('%I')`, `%L`); a failed `CREATE` or `ALTER ROLE` is raised again without the statement, so neither the password nor the verifier is in the error or the server's log. If the database grants change nothing (PostgreSQL only warns when the administrator neither owns the database nor is a member of its owner), the run fails: it checks `has_database_privilege` for the role's `CONNECT` and `TEMPORARY`, and that `PUBLIC` holds no `CONNECT`. It fails too if the role still holds `CREATE` after the revoke (through `PUBLIC`, or a role it was made a member of). Nor does it keep `CREATE` on any schema: every run revokes it on every schema from the role, on `public` too (which `pg_database_owner` owns and the grants skip), and from `PUBLIC` wherever `PUBLIC` holds it (PostgreSQL before 15 grants it on `public`), and fails if the role still holds one. And the run fails if the role owns anything in its database (`pg_shdepend`, `deptype = 'o'`; large objects, its own default privileges and its temporary objects, which reach no other session, aside), naming each object and the role: what it made while an earlier design granted it `CREATE` survives the revoke, and code on it would run as whoever touches it, the administrator included, should a migration adopt its schema. Keycloak's role (below) is held to the same, outside its own schema. Every administrator session of the runner, EF Core's and Marten's included, has `search_path` pinned to `pg_catalog, pg_temp` (`AdministratorSession.cs`), and the role's and the gate's SQL calls functions schema-qualified with typed arguments. The role holds no `CREATE` on the database any more, so it can no longer create a schema named after the administrator, first on the default `"$user", public`, and plant functions there that an administrator session would run with its rights (the CVE-2018-1058 pattern); the pinned `search_path` and the qualified calls stay as defence in depth, against a grant someone adds by hand or a role that held `CREATE` before. For any other administrator session, an operator's `psql` included, the runner also creates that schema itself, owned by the administrator and empty, before the migrations (`AdministratorSchema.cs`); if another role already owns it, the run fails. Runs on one database are serialized twice: the whole MigrationRunner run holds a session advisory lock of the database's (`MigrationGate`), and the role's statements a transaction advisory lock of the role's own. Neither wait has a command timeout (`CommandTimeout = 0`), so a second replica waits as long as the first migrates; cancellation still ends it. When the gate's session is gone by the time the run leaves it (the server ended it, the network dropped), the server has released the lock with it: leaving logs the failed unlock as a warning and never throws over the run's own failure, which is what the init container's log shows. Without `ConnectionStrings:application` (run mode) no role is made.
- **Each service logs in as its module's role, never as the administrator** (`src/AppHost/Wiring/Databases.cs`, OQ8 c and Q1 on #114). Published, the Flexible Server's own module writes, next to Aspire's administrator connection strings, one for every module database's role, `connectionstrings--<module>-database-app`: `Host=<server>;Username=<module>_app;Password=<password>;Database=<module>`, with the module's `-` as `_` in the role's name. The password is Bicep's `guid(database-roles-key, '<module>')`, derived from the deployment secret `database-roles-key`, which main.bicep hands to the server's module as a `@secure()` parameter. It writes the same for Keycloak's database, `connectionstrings--keycloak-database-app` with `keycloak_app` (below), and nothing is listed per module. The service's own container reads it as `ConnectionStrings__database` (`WithModuleDatabase`), its init container as `ConnectionStrings__application`, from which the MigrationRunner creates or updates the role. So `<module>-identity` is granted the role's secret and not the administrator's, and `<module>-migrations-identity` exactly both. The password is stable across publishes and deploys (B8); `guid()` is a name-based hash (36 characters of `0-9a-f-`, safe in a connection string), and a module's password does not lead back to the key or to another module's. To rotate every role's password, change `database-roles-key` and deploy: that rewrites the Key Vault secrets only. A running revision keeps the values it started with, so the passwords change only when each service gets a new revision or is restarted; its init container then runs `ALTER ROLE ... PASSWORD` and the service starts with the new one. Rotation is therefore: change the key, deploy, then give every service a new revision (or restart it). Until then the old passwords keep working; once the first new replica's init container has changed a role's password, replicas still on the old one cannot open new connections, so a service's replicas move together. #129 verifies this. Run mode keeps Aspire's reference to the database, as before.
- **The MigrationRunner builds Wolverine's storage as the administrator** (`src/BuildingBlocks/Persistence/ModuleMessageStorage.cs`, review of #231). After the migrations and the event store's schema and before the role's grants, it builds or updates Wolverine's inbox, outbox, scheduled and dead-letter tables in the schema `wolverine`, so the administrator owns the schema and everything in it, and the role's grants on every schema the administrator owns give the service what it needs there: `USAGE` and `SELECT, INSERT, UPDATE, DELETE`, never ownership. The runner and every service host configure the storage through one extension, `PersistModuleMessages` (`src/BuildingBlocks/Persistence/Wiring/ModuleMessagePersistence.cs`), which `src/Host/Wiring/Messaging.cs` calls too, so what the runner builds is what the service expects and the two cannot drift. The runner needs no broker, queue or publisher list for it: it builds a Wolverine host it never starts and migrates its storage (`IWolverineRuntime.Storage`, below). The service still leaves `AutoBuildMessageStorageOnStartup` at its default: at start Wolverine compares the storage with its configuration, finds nothing to change and changes nothing, so it issues no `CREATE SCHEMA` the role could not run; a missing table or column it would have to create fails the start with `42501`, loudly, instead of a service running without it. A Wolverine upgrade that changes its storage is therefore built by the runner, which runs as the init container of the same image before the service starts. If `wolverine` exists and some other role owns it, or it holds an object (a relation, function, type, operator and the like) some other role owns, the run fails, naming the schema, the object and the owner, as for the schema named after the administrator: the storage is never built on, or granted from, what a role made. Wolverine makes tables, their indexes and sequences there (and the internal triggers of their foreign keys), nothing that runs by itself, so a trigger, a rule, a policy, row level security or a `SECURITY DEFINER` function in `wolverine` fails the run too, naming it, whoever owns it. The run's hint names two ways out. Dropping the schema drops the inbox, outbox and dead letters in it as well. To keep them, remove what the role made that runs by itself (its triggers, rules, policies and functions in `wolverine`), then `ALTER SCHEMA wolverine OWNER TO <admin>` and `REASSIGN OWNED BY <module>_app TO <admin>`, which takes the privileges of both roles (on Flexible Server, `GRANT <module>_app TO <admin>` for the change and `REVOKE` right after), and run the migrations again: the checks above then confirm that the administrator owns everything there and that nothing runs by itself. The runner migrates through the store's Weasel database (`ApplyAllConfiguredChangesToDatabaseAsync`), as Wolverine's own `MigrateAsync` takes no cancellation token, so a stopped init container stops a migration waiting on a lock. Nothing has been deployed yet (#129 is the first deploy), so no database holds a `wolverine` schema an earlier role owns.
- **Traffic between the apps is encrypted**: the environment's peer traffic encryption is on (`peerTrafficConfiguration.encryption.enabled`, `ContainerAppsEnvironment.cs`). Aspire 13.6.5's Container Apps model (`Azure.Provisioning.AppContainers` 1.2.0) has no such property; the AppHost references 1.3.0, which has it.
- **Every Container App reads a secret as a Key Vault reference, never as a value.** `WithSecret` (`src/AppHost/Wiring/SecretEnvironment.cs`) hands a resource the Key Vault secret that holds a parameter in publish mode and the parameter itself in run mode. A database's connection string is a Key Vault secret the Flexible Server's own Bicep writes: the module role's (`connectionstrings--<module>-database-app`) for the service, the administrator's (`connectionstrings--<module>-database`) for its init container. The services and, in run mode, the migrations read what they reference as connection strings, service discovery and endpoints alone (`WithConnectionStringsOnly`): Aspire would also hand them each part of a connection as plain values, which nothing reads. `AppHostPublishParametersTests.No_container_app_receives_a_secret_as_a_plain_value` fails on any `@secure()` parameter of a Container App's module.
- **Each service's broker connection string is a Key Vault secret the AppHost composes** (`src/AppHost/Wiring/Messaging.cs`), `messaging-<module>-connection-string`, for that service's own user; no service reads the admin's, which is no longer stored. The broker reads its users from a definitions document that holds no password, and each user's password as a Key Vault reference of its own, `messaging-password` and `messaging-<module>-password` (ADR 0011, D4); the vault holds no definitions document. Each is `amqp://<user>:<password>@messaging:5672`, the broker's resource name and its endpoint's target port from the model. The Key Vault's Bicep cannot read a Container App's endpoint; given the broker's own connection string, Aspire writes `amqp://<user>:<password>@` without host and port. The name and target port are what Aspire itself writes for a service that references a TCP Container App.
- **PostgreSQL is one Flexible Server, `postgres`, with password authentication** (`src/AppHost/Wiring/Databases.cs`), a database per module, named after it, and one `keycloak`. Each service reads only its own as `database`, as its module's role; its migrations read the administrator's for it. Its administrator is `postgres-username` / `postgres-password`. The size follows the environment (`DatabaseServerSize`):
  - `staging`: `Standard_B2s`, Burstable, backups kept 7 days. `Standard_B1ms` allows 50 connections, fewer than seven services' pools (EF Core, Marten, Wolverine) and Keycloak open.
  - `production`: `Standard_D2ds_v5`, General Purpose (the smallest), backups kept 35 days.
  - Neither has high availability or geo-redundant backups. Any other environment name fails the publish, naming `staging` and `production`. Run mode keeps the Postgres container with its data volume.
- **RabbitMQ stays a container**, published with its named data volume at `/var/lib/rabbitmq` (Azure Files), the admin user and password `messaging-username` / `messaging-password`, a user of its own for every service (ADR 0011), and no management UI. Run mode keeps the management UI and Aspire's generated password.
- **Keycloak's administrator and mail server are parameters once published** (`src/AppHost/Wiring/KeycloakSettings.cs`): `KC_BOOTSTRAP_ADMIN_USERNAME` from `keycloak-admin-username`, the password, `SMTP_USERNAME` and `SMTP_PASSWORD` from the Key Vault, `SMTP_HOST` and `SMTP_FROM` from their parameters. The services send through the same server (`src/AppHost/Wiring/MailServer.cs`, docs/adr/0004): the AppHost composes their connection string `mail`, `smtp://<smtp-username>:<smtp-password>@<smtp-host>:587`, into the Key Vault secret `mail-connection-string`, which every service reads as `ConnectionStrings__mail`, and they send from `smtp-from`; `frontend-url`, the web app's public URL, has no default and must be the canonical https origin a browser sends, `https://host` or `https://host:port` in lower case, with no default port (`:443`), path, query, trailing slash or dot, or wildcard (the value must equal its own `GetLeftPart(UriPartial.Authority)`), since the storage account's CORS rule and the links in mail use it as it is: publishing refuses anything else, naming the parameter (`PublishedParameterChecks`). The development realm's bind mount and Keycloak's data volume are run mode only.
- **Published, Keycloak imports a realm of its own once** (`src/AppHost/keycloak/realm.json`, K1 and X4 of the PR-C plan, B10 on #114). It is the development realm, `src/AppHost/realms/realm.json`, without its local users and with `registrationAllowed: false` (until #158 settles brute-force detection, bot protection and enumeration; the owner's 2026-11-22 22:03 requirement), `verifyEmail: true`, `sslRequired: "external"` and `bruteForceProtected: true`; its `smtpServer` names `${SMTP_HOST}`, `${SMTP_FROM}`, `${SMTP_USERNAME}` and `${SMTP_PASSWORD}` on port 587 with STARTTLS and authentication; and its web client `pharma-training-web` accepts `${WEB_ORIGIN}/*` and `${WEB_ORIGIN}` alone and has no password grant (`directAccessGrantsEnabled: false`, which exists for the local tests). Keycloak replaces the placeholders from its environment when it imports the file. Roles, clients, mappers and required actions (`VERIFY_EMAIL` a default action) are the development realm's; `PublishedRealmTests` fails on any other difference. It lives outside `./realms`, which run mode bind-mounts as Keycloak's import directory.
- **Published, Keycloak runs an image built from Keycloak's own** (`src/AppHost/Wiring/KeycloakPublishing.cs`): the AppHost writes its Dockerfile (`WithDockerfileFactory`, context `src/AppHost/keycloak`): `quay.io/keycloak/keycloak:26.6`, `kc.sh build --db=postgres --health-enabled=true` in one stage, the built `/opt/keycloak` and `realm.json` in `/opt/keycloak/data/import` in the stage it runs, which starts with `start --optimized --import-realm`. It serves plain HTTP (`KC_HTTP_ENABLED=true`) behind the auth proxy and the environment's ingress and reads their `X-Forwarded-*` headers (`KC_PROXY_HEADERS=xforwarded`). Run mode keeps Keycloak's own image in `start-dev`, the development realm and the data volume.
- **Every base image a deploy builds or runs is pinned by digest** (the security review of #114), since a tag can be moved to an image nobody reviewed: Keycloak's published Dockerfile starts both stages from `quay.io/keycloak/keycloak:26.6@sha256:…` (`KeycloakPublishing.PinnedImage`; run mode keeps the tag alone), the auth proxy runs `mcr.microsoft.com/dotnet/nightly/yarp:2.3.0-preview.5` by its digest (`WithImageSHA256`, `AuthProxy.cs`), and `web/Dockerfile` builds from `node:22.23.5-slim@sha256:…`. Dependabot keeps `web/Dockerfile` current, tag and digest; it cannot see an image named in C#, so Keycloak's and YARP's are updated by hand, tag and digest together, from `docker buildx imagetools inspect <image>:<tag>`. The services' and the edge's own base images are .NET's, chosen by the SDK's container build.
- **The published realm is hardened beyond the development realm** (the security review of #114): it declares `admin-cli` as a public client without the password grant (`directAccessGrantsEnabled: false`), where Keycloak would otherwise create its own with the grant on, so no client of the realm takes a user's password at the token endpoint the auth proxy publishes; it records user events (`eventsEnabled`, Keycloak's default types, `LOGIN_ERROR` among them) and admin events (`adminEventsEnabled`); and brute-force detection locks a user out after 10 failed logins (`failureFactor`, Keycloak's default is 30), for a minute at first and longer with each further failure. `PublishedRealmTests` holds each.
- **Keycloak keeps its data in its own database, as its own role, in a schema that role owns** (Q2 on #114, X3). `KC_DB_URL_HOST` is the server's FQDN (its `hostName` output), `KC_DB_URL_DATABASE=keycloak`, `KC_DB_URL_PROPERTIES=?sslmode=require`, `KC_DB_SCHEMA=keycloak`, `KC_DB_USERNAME=keycloak_app`, and `KC_DB_PASSWORD` a Key Vault reference to `keycloak-database-password`, which the server's module writes as `guid(database-roles-key, 'keycloak')` beside `connectionstrings--keycloak-database-app`; no variable holds a password or the administrator. Keycloak's Container App runs the MigrationRunner's image as its one init container, `migrations`, as every service does, but in the runner's role-only mode: `Migrations__OwnedSchema=keycloak` and no `Migrations__Module`, with `connectionstrings--keycloak-database` and `connectionstrings--keycloak-database-app` resolved by `keycloak-migrations-identity` (lifecycle `None`); `keycloak-identity` (`Main`) reads exactly `keycloak-admin-password`, `keycloak-database-password`, `smtp-username` and `smtp-password`, and Keycloak waits for the `migrations` job. In that mode the runner (`MigrationRun.RunOwnedSchemaModeAsync`, under `MigrationGate`) ensures the role alone (`src/BuildingBlocks/Persistence/OwnedSchemaRole.cs`): `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS INHERIT` with the password as a SCRAM-SHA-256 verifier, `CONNECT` on the database revoked from `PUBLIC`, `CONNECT` and `TEMPORARY` but never `CREATE` on it, and the schema `keycloak` created owned by the role, so Keycloak creates and changes its tables there and nowhere else (it cannot create in `public` or create a schema). Creating a schema for another role takes the right to `SET ROLE` to it: the administrator, no superuser on Flexible Server, gets it once with `GRANT keycloak_app TO CURRENT_USER WITH INHERIT FALSE, SET TRUE`, inheriting none of the role's rights; once the schema is the role's, a run changes no membership. A schema `keycloak` some other role owns fails the run. Every check, the pinned `search_path`, the bind parameters and the scrubbed errors are `ModuleDatabaseRole`'s. A run naming neither a module nor an owned schema fails, naming both settings.
- **Published, the browser reaches Keycloak through the auth proxy alone** (`src/AppHost/Wiring/AuthProxy.cs`, OQ2 and X2 on #114): a YARP app, `auth` (`Aspire.Hosting.Yarp` 13.6.5), with external ingress and one replica at least, `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, and exactly two routes, `/realms/pharma-training/{**catch-all}` and `/resources/{**catch-all}`, to Keycloak's `http` endpoint. That is narrower than OQ2's "/realms": `/realms/master`, whose token endpoint takes the administrator's password, `/admin` and the management port answer 404 from YARP. Run mode has no proxy.
- **The public addresses come from the environment's default domain** (`src/AppHost/Wiring/PublicAddresses.cs`, X5): `KC_HOSTNAME=https://auth.<default domain>`, Keycloak's `WEB_ORIGIN=https://host.<default domain>` (the edge's address, which will serve the web app), and the issuer every host validates, `Authentication__Authority` of the edge and every service, `https://auth.<default domain>/realms/pharma-training`. They are built from the environment's Bicep output `AZURE_CONTAINER_APPS_ENVIRONMENT_DEFAULT_DOMAIN`, never from endpoint references between apps, which would make a cycle (the edge and the proxy reach Keycloak, which names them). `WEB_ORIGIN` is not `frontend-url`, which a deployment can set only once the environment exists, after the realm was imported once. Run mode keeps `<keycloak http>/realms/pharma-training`.
- **The server's maintenance database is closed to `PUBLIC` where the administrator can close it** (`src/BuildingBlocks/Persistence/MaintenanceDatabase.cs`, PR-B's security review). PostgreSQL grants `CONNECT` on `postgres` to `PUBLIC`, so every role, a module's or Keycloak's, could connect there and read the catalogs. Every role the runner ensures (`ModuleDatabaseRole`, `OwnedSchemaRole`) also revokes it; when that changes nothing because the administrator neither owns `postgres` nor is a member of its owner, the run logs a warning naming the database and goes on. A role's own database stays fail-loud.
- **The model's parameters reach every service as today** (`azure-openai-endpoint`, `azure-openai-deployment`), and the key as a Key Vault reference. Nothing provisions an Azure OpenAI resource; ADR 0006 says which endpoint a deployment uses.
- **The same commit publishes the same Bicep.** `.github/workflows/publish.yml` publishes `staging` and `production` on every pull request and on `main`, with a placeholder for every parameter without a default, publishes each a second time and fails on any difference (`diff -r`), and compiles every Bicep file it wrote with `az bicep build` (Aspire's `main.bicep` does not name the Container App modules, so compiling it alone would skip them). It signs in to nothing. `AppHostPublishTests.Publishing_twice_writes_the_same_bicep` checks the same in the tests.
- **`.github/workflows/deploy.yml` is the only path to Azure** (#114 PR-F, the owner's decision on #114: `aspire deploy` from CI). It runs only by `workflow_dispatch`, one run at a time and never cancelled. Its job `staging` (GitHub environment `staging`) runs first; `production` (environment `production`, whose required reviewers approve it) needs it. Each job signs in with `azure/login` through the environment's federated credential (OIDC, `id-token: write`; the client, tenant and subscription ids are variables, there is no client secret), refuses a resource group outside `germanywestcentral`, and runs `aspire deploy -e <environment> --non-interactive --clear-cache` (no deployment state saved earlier overrides what the environment sets) with `Azure__CredentialSource=AzureCli`, `Azure__Location=germanywestcentral` and every parameter `publish.yml` sets, each from the environment's secret or variable named after it in upper snake case (`Parameters__postgres-password` from `POSTGRES_PASSWORD`). Each service's broker password comes from `MESSAGING_<MODULE>_PASSWORD`, read with `jq` from `toJSON(secrets)` for every `src/Services/*/Host/Host.csproj`'s `<ModuleName>`, so no module is listed (ADR 0011, D3); a missing or unsafe one, or any empty parameter, fails the job naming it, never its value. A secret reaches a step only through an `env` entry. `deploy.yml` and `publish.yml` install the CLI (`dotnet tool install aspire.cli --tool-path "$HOME/.aspire/bin"`) and run its native binary by path, never through `dnx`: `dnx` is a `/bin/sh` script, and on Ubuntu `sh` is dash, which drops every variable whose name holds `-`, so every `Parameters__*` would be lost silently (observed: through `dnx`, a 9-character `database-roles-key` published without complaint; natively, `PublishedParameterChecks` refused it). `WorkflowsRunTheAspireCliNatively` fails on any Aspire command but `setup` run through `dnx`. The architecture rules `DeployWorkflowSetsEveryPublishedParameter` (every `Parameters__*` of `publish.yml` in both jobs, from its own name, no module named) and `DeployWorkflowDeploysStagingThenApprovedProduction` (trigger, OIDC, the two jobs and their order, location, credential source, secrets only in `env`, no `set -x`) hold it there. The one-time setup, the first deploy and rolling back are in the README.
- **Who may deploy is limited outside the repository too** (the security review of #114, README "One-time setup"): the deploying identity's `Role Based Access Control Administrator` carries a condition that lets it assign and remove Key Vault Secrets User, AcrPull, Storage Blob Data Contributor and Storage Blob Delegator alone, what the Bicep assigns, so it cannot grant itself `Owner`; the `production` environment's required reviewers have "Prevent self-review" on; and a tag ruleset lets only the people who may deploy create, move or delete `deploy/*` tags, which both environments accept. `deploy.yml` passes `toJSON(secrets)` to one step's environment in each job, and that step never runs with `set -x`, which would print it.
- **The tests read the publish model in process.** `tests/Integration.Tests/PublishedAppHost.cs` builds the AppHost with the CLI's publish arguments and runs its publish pipeline into a temporary directory. The tests themselves need neither Docker nor the Aspire CLI, but they live in Integration.Tests, whose assembly fixture starts the whole application first, so a run of them does need Docker; moving the AppHost's model tests to a project of their own is a later change. `AppHostPublishTests`, `AppHostComputeTests`, `AppHostPublishParametersTests`, `AppHostPostgresTests` and `AppHostMessagingTests` hold the decisions above to it.

## Consequences

- A grant that exists may still take a while to propagate in Entra, so a revision created right after its `<app>-roles-secrets` deployment can fail its Key Vault references once with "unable to fetch secret using managed identity" until a retry; the first deploy (#129) observes it.
- Publish mode and run mode now differ in the AppHost: each publish-only branch is an extension in `src/AppHost/Wiring/` guarded by the execution context, so `AppHost.cs` still reads as one model, and the run-mode integration tests (`AppHostParametersTests`, `AppHostBlobContainersTests` and the rest) pass unmodified.
- The broker's connection string assumes Container Apps' internal addressing (`<app>:<target port>` for TCP ingress), as Aspire's own does. Main.bicep does not URI-escape a value it assembles, so `messaging-username`, `messaging-password` and each service's `messaging-<module>-password` must be URI-safe (letters, digits, `-`, `.`, `_`, `~`); a wrong address or an unsafe password is first seen at the first deploy (#129).
- RabbitMQ on an Azure Files (SMB) volume, and internal TCP ingress in a Consumption environment, are first observed in #129.
- The Flexible Server's firewall allows all Azure IP addresses (`AllowAllAzureIps`, Aspire's default), so it has a public endpoint reachable from any Azure tenant, protected by its password and TLS (Npgsql's default `SslMode=Prefer` encrypts but does not verify the certificate). Private networking (a VNet for the environment, private access for the server) is part of the open decision on secrets and database roles below, to settle before #129.
- Each service's identity may read and write its own module's container alone, and ask for user delegation keys (ADR 0002); the migrations, Keycloak and the broker have no storage role.
- Each app's identity reads the secrets it references alone, the administrator's connection string is resolved for the init stage alone, and a service logs in as its module's role. A compromised service (code execution, or a request forged to its managed-identity endpoint) therefore reads and writes its own module's data (its tables, its event streams and its Wolverine envelopes, dead letters included) and no other module's: it cannot connect to another module's database or Keycloak's (`CONNECT` is revoked from `PUBLIC`), it cannot change its module's schema, and, owning nothing, it cannot attach code to anything that runs as another role. Whether it can still connect to `postgres` depends on who owns that database (below); there it would see the catalogs (names of tables, roles and the like), not their data. `AppHostSecretAccessTests.Only_init_stages_read_an_administrator_connection_string` holds it, Keycloak's init stage included.
- Keycloak logs in as `keycloak_app`, so a compromised Keycloak reaches its own data and nothing else; it creates its tables, with its own Liquibase migrations, in the schema `keycloak` alone. The owner's Q2 said `public`; X3 reads "owns the keycloak schema" literally, since on PostgreSQL 15 and later `public` belongs to `pg_database_owner`, which on a database created through ARM may be `azure_pg_admin`. `keycloak_app` is therefore the one role that owns a schema, and everything Keycloak creates in it, where a module's role owns nothing: Keycloak migrates its own tables with Liquibase at start, so it needs `CREATE` there, and no migration of ours builds them. That is acceptable because nobody touches `keycloak`'s tables as the administrator: the runner, in its role-only mode, only creates the role and the empty schema `AUTHORIZATION keycloak_app` and grants nothing on what is in it, so code Keycloak's role could attach to its tables (a trigger, a rule, a policy) runs only for Keycloak itself, never in an administrator's session; an operator who must change Keycloak's data does it through `kcadm.sh` or as `keycloak_app`, never as the administrator.
- The administrator works with Keycloak through `kcadm.sh` inside its container (`az containerapp exec ... kcadm.sh`), against `http://localhost:8080` and the realm `master`; no browser reaches `/admin`. Registration stays off until #158, so every account, invitees' included, is created that way until then, and turning registration on later is a change in the admin console plus the realm file for new environments.
- After the first deploy the bootstrap administrator `admin` is replaced by a named one and deleted, and the master realm gets brute-force protection and events through `kcadm.sh` (README, "The first deploy"); `kcadm.sh` asks for passwords rather than taking `--password`. The named administrator has no OTP: `kcadm.sh` signs in with the password grant and cannot send one, and the master realm's pages, where it would be set up, are not published. What stands in front of it is Azure's: only someone whose Entra sign-in may run `az containerapp exec` on `keycloak` reaches `kcadm.sh`. Requiring an OTP would mean publishing the master realm's login, or a client the administrator signs in to with a key instead (`kcadm.sh --client --keystore`); either is a decision of its own.
- Keycloak's internal ingress (`https://keycloak.internal.<default domain>`, the `http` endpoint) is reachable by every app in the environment, not only the auth proxy: a compromised service can reach `/realms/master` and `/admin` there, which the auth proxy hides from the internet. The master realm's brute-force protection and the named administrator's password are what protect it; narrowing that ingress to the auth proxy alone is not possible with Container Apps' internal ingress.
- The realm is imported once, on Keycloak's first start against an empty database (`IGNORE_EXISTING`): a changed `src/AppHost/keycloak/realm.json`, or a `WEB_ORIGIN` or SMTP setting it holds, reaches new environments only; an existing one is changed with `kcadm.sh`.
- The auth proxy runs YARP's preview image, `mcr.microsoft.com/dotnet/nightly/yarp:2.3.0-preview.5`, by digest (above), the image Aspire 13.6.5's default tag `2.3-preview` named when it was pinned; moving to a released YARP image is a later change, by hand like every pin Dependabot cannot see.
- A module's role holds no `CREATE` on its database, so a service creates nothing at start: a schema or table it needs comes from the MigrationRunner, as a migration or, for Wolverine, as the storage the runner builds. A library that builds its own storage at start (as Wolverine did before the review of #231) fails under the role with `42501` and has to be built by the runner too.
- **A dead-letter replay runs as the module role, never as the administrator.** Replaying (`UPDATE wolverine.wolverine_dead_letters SET replayable = true`, ADR 0004) uses the role's connection string (the Key Vault secret `connectionstrings--<module>-database-app`), or `SET ROLE <module>_app` from an administrator session: `GRANT <module>_app TO <admin> WITH INHERIT FALSE, SET TRUE` first (on PostgreSQL 16 `INHERIT` otherwise defaults to true, and every administrator session would silently hold what the role holds), then `SET ROLE <module>_app`, the replay, `RESET ROLE`, and `REVOKE <module>_app FROM <admin>` afterwards: the role has `UPDATE` there, and the operator touches nothing with more rights than the service has. And nothing the role owns is touched as the administrator. The role owns nothing now, so the second rule holds by construction; both stay the rule, against a grant or an ownership a later change brings back.
- `database-roles-key` may hold any characters: only its hash reaches a connection string. It must be at least 32 characters long: every role's password is derived from it, so the key is all that stands between a guess and every role, and publishing (and so deploying) refuses a shorter one, naming the parameter, before it writes anything (`src/AppHost/Wiring/PublishedParameterChecks.cs`, at `BeforeStartEvent`; a parameter not set yet is left to the deploy, which sets them all). That checks only a value given at publish, so main.bicep and the server's module both declare `@minLength(32)` on it as well, a floor Azure enforces however the key arrives, at a prompt or from the deployment's own parameters. Aspire writes main.bicep's parameters itself with no decorator; `MinimumLengthResolver`, one of the build options' infrastructure resolvers (`AzureProvisioningOptions.ProvisioningBuildOptions`) that Aspire builds main.bicep with, swaps that parameter for one that declares it (`MinimumLengthParameter`). Length says nothing of entropy (`aaaa…` passes): checking it belongs to `deploy.yml`'s parameter check (F2, #129). Each environment needs its own; a key shared with another environment gives both the same role passwords.
- The grants are computed from each app's environment and arguments wherever and whenever they are added, so the call's place in `AppHost.cs` no longer matters. A secret an app is given some other way (a file, a mounted volume) is still not found, and the app is refused it at the first deploy. Give every secret through `WithSecret`, `WithMessaging`, a reference or an argument.
- The Container Apps environment is declared with API version `2025-07-01` (`ContainerAppsEnvironment.cs` sets its `ResourceVersion`), which has peer traffic encryption, whatever version a later Aspire would write; `AppHostSecretAccessTests` holds it there. `Azure.Provisioning.AppContainers` is pinned above the version Aspire brings, for one property. An Aspire upgrade that brings 1.3.0 or later makes the pin redundant; one whose model no longer compiles against it shows in the AppHost's build.
- `postgres-password` must not contain `;`, `'` or `"`: Aspire assembles `Host=...;Password=...` into the Key Vault secret without quoting it. `deploy.yml` refuses a broker password (`MESSAGING_<MODULE>_PASSWORD`) that is not URI-safe before it deploys; the check of `postgres-password`, the other broker and SMTP credentials and `frontend-url` follows in a later part of #114 (F2), and until then a wrong value is first seen in Azure. `smtp-username` and `smtp-password` must be URI-safe too, as they are assembled into the mail connection string the same way.
- Peer traffic encryption covers the broker's AMQP, with its credentials, to `messaging:5672`, which is plain AMQP inside the environment; the services already reach Keycloak through the environment's internal HTTPS ingress (`https://keycloak.internal.<default domain>`). It adds some latency to every call between apps; whether it holds for internal TCP ingress is first observed in #129.
- The SPA the edge serves signs in through the published realm (PR-C). Nothing has been deployed before #129: `deploy.yml` has not run against Azure, and its first run is #129's.
- `aspire deploy` on the runner builds every image (each service, the edge with the web app, Keycloak, the MigrationRunner); the web app's base image comes from Docker Hub, whose pull rate limit may need a Docker Hub login in the job, not added until a run shows it. The CLI signs in with the session `azure/login` opened from the run's OIDC token; whether a deploy outlasts the access tokens that session holds is first seen at #129.
- `FRONTEND_URL` is a placeholder origin (`https://host.invalid`) at an environment's first deploy, since the edge's address exists only once the environment does; it is set to `https://host.<default domain>` and deployed again (OQ-4 on #114).
- Every new replica runs the migrations first, so a replica starts only as fast as an up-to-date database answers "nothing to do", and a failing migration stops the new revision while the old one keeps serving. A migration must therefore be safe to run while the previous revision serves (B12, expand and contract).
- First observed at the first deploy (#129), each with its fix in the AppHost or the runner, never the service:
  - whether Container Apps resolves a Key Vault reference with an identity whose lifecycle is `None`. Microsoft documents `None` as an identity no container may use, not whether the platform still uses it for secrets. If the first revision fails with "unable to fetch secret", the migrations identity's lifecycle becomes `Init` (one line in `Migrations.cs`): the main container still cannot use it, and only the runner, our own code, could during the init stage;
  - whether the pipeline deploys a service only after the `migrations` image is pushed, as the `WaitFor` dependency should make it; if not, a service's first deploy fails with "image not found" and a second run succeeds;
  - the init container has no resources of its own, so Container Apps' defaults apply; if it refuses the replica's total, give it 0.25 vCPU and 0.5 Gi;
  - on a Flexible Server a database created through ARM may be owned by `azure_pg_admin`, not by the administrator login; PostgreSQL then only warns on `REVOKE CONNECT ... FROM PUBLIC` and `GRANT ... ON DATABASE`, so the runner checks the result and fails the init container, and the previous revision keeps serving;
  - the maintenance database `postgres` is likely owned by `azure_pg_admin`; if the administrator is not a member of it, revoking `PUBLIC`'s `CONNECT` there changes nothing and every init container logs the warning, so every role can still connect to `postgres` and read its catalogs. Check the warning at #129; closing it then needs the owner's revoke (a support request or `azure_pg_admin`'s membership), not a change here;
  - whether the administrator may `GRANT keycloak_app TO <admin> WITH INHERIT FALSE, SET TRUE` and `CREATE SCHEMA keycloak AUTHORIZATION keycloak_app` on Flexible Server; if not, Keycloak's init container fails and, on the first deploy, nothing serves sign-ins;
  - the issuer behind the auth proxy and the ingress: with `KC_HOSTNAME` a full `https://` URL it stays `https://auth.<default domain>/realms/pharma-training`, whatever `X-Forwarded-Proto` the hops pass on (observed locally through YARP);
  - the edge and the services fetch the issuer's metadata through the public `auth` address, out of the environment and back in; if that is slow or refused, `Authentication:MetadataAddress` pointed at Keycloak's internal address is a decision on the pack's `src/Host/Wiring/Authentication.cs`;
- Run mode never logs a service in as its role (Q3 on #114): the services keep Aspire's development login, so the integration suite exercises the role's grants directly (`ModuleDatabaseRoleTests`: EF reads and writes, a Marten append, the real MigrationRunner building Wolverine's storage as the administrator and a Wolverine host working on it, and replaying a dead letter, under the role) rather than through the running services, and a grant a later feature needs (an extension, `LISTEN`) would first fail in Azure. Run mode could create the roles too, with a generated per-module password in the AppHost's user secrets; that is proposed as a follow-up, not part of this decision.
- A parameter without a value does not stop `aspire publish --non-interactive` (it writes Bicep alone), but the in-process test harness waits for input; both pass placeholders. `aspire publish` saves parameter values in `~/.aspire/deployments`; a developer who publishes locally with real values should remove that state afterwards.
- `fabric upgrade` regenerates files this decision changed and may conflict on them: `src/AppHost/AppHost.cs`, `src/AppHost/AppHost.csproj`, `Directory.Packages.props` and `tests/Integration.Tests/Integration.Tests.csproj`; PR-E changed `src/AppHost/AppHost.cs`, `src/AppHost/AppHost.csproj`, `src/BuildingBlocks/BuildingBlocks.csproj`, `Directory.Packages.props` and `README.md` again; PR-B changed `src/AppHost/AppHost.cs`, `src/MigrationRunner/Program.cs`, `src/Host/Wiring/Messaging.cs`, `src/BuildingBlocks/BuildingBlocks.csproj`, `.github/workflows/publish.yml`, `README.md`, `Solution.slnx` and `tests/Integration.Tests/Integration.Tests.csproj`; PR-C changed `src/AppHost/AppHost.cs`, `src/AppHost/AppHost.csproj`, `src/MigrationRunner/Program.cs` and `Directory.Packages.props`; PR-D changed `src/AppHost/AppHost.cs`, `src/Edge/Program.cs`, `web/app/src/main.ts`, `web/app/src/auth/oidcConfig.ts`, `web/app/src/auth/accessToken.ts`, `web/app/src/providers/auth.ts` and `web/app/src/vite-env.d.ts`, and `docs/adr/fabric/frontend-auth-client-oidc-client-ts.md` still names `VITE_OIDC_AUTHORITY`, which the web app no longer reads. Keep this decision's changes when resolving them. The new files (`web/Dockerfile`, `web/.dockerignore`, `src/Edge/FrontendConfiguration.cs`, `src/Edge/Wiring/*` beside `ModuleRoutes.cs` and `ServiceDocuments.cs`, `web/app/src/auth/runtimeConfig.ts`, `web/app/src/bootstrap.ts`, `src/AppHost/Wiring/*` beside `BrowserUploads.cs` and `ServiceHostProjects.cs`, `src/BuildingBlocks/Persistence/ModuleDatabaseRole.cs`, `MigrationGate.cs`, `AdministratorSession.cs`, `AdministratorSchema.cs`, `ScramSha256Verifier.cs`, `ModuleMessageStorage.cs`, `Wiring/ModuleMessagePersistence.cs`, `OwnedSchemaRole.cs`, `MigrationRun.cs` and `MaintenanceDatabase.cs`, `src/AppHost/keycloak/realm.json`, `tests/BuildingBlocks/Persistence.Tests`, `.github/workflows/publish.yml`, the tests above) are the project's own.
