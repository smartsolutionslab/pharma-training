# 0005: Deploy to Azure Container Apps from the AppHost

**Status:** Accepted (first part, #114 PR-A: the publish model; Keycloak, the SPA, keyless blobs, migrations and the deploy workflow follow in later parts of #114 and are added here then)

## Context

- Issue #114 asks for a deployment of the whole application to Azure, in two environments, `staging` and `production`, from the one composition root, `src/AppHost` (AGENTS.md, "Project structure"): nothing hand-written beside it, no second description of what runs where.
- Aspire 13.6.5 publishes an AppHost as Bicep (`aspire publish -e <environment>`) and deploys it (`aspire deploy`). `Aspire.Hosting.Azure.AppContainers` turns every compute resource into an Azure Container App in one Container Apps environment; `Aspire.Hosting.Azure.PostgreSQL` and `Aspire.Hosting.Azure.KeyVault` provision a Flexible Server and a Key Vault.
- Until now nothing published. The AppHost could not even be published: the web app's Vite dev server is a build-only container that nothing consumed, which fails Aspire's validation, and every secret parameter was one Aspire generates and keeps in a developer's user secrets, which a deployment has none of.
- By default Aspire hands a secret to a Container App as a secure Bicep parameter, stored as a plain Container App secret: the database passwords and URIs (`DATABASE_PASSWORD`, `DATABASE_URI`), the broker's connection string, the Keycloak administrator's password, the model's key. Whoever may read the Container App's configuration may read them.
- The owner decided on 2026-11-21: Azure Container Apps; a Key Vault for every secret; PostgreSQL as a Flexible Server, Burstable for staging and General Purpose for production, without high availability or geo-redundant backups; one replica always running, nothing scaled to zero; everything planned for Germany West Central; and, for B8, that a second deploy may make no infrastructure or configuration change.

## Decision

- **Publish mode has one Container Apps environment, `aca`** (`src/AppHost/Wiring/ContainerAppsEnvironment.cs`), without the Aspire dashboard (`WithDashboard(false)`): the dashboard would show logs and traces, personal data among them, on a public `azurecontainerapps.io` URL. Logs stay in the environment's Log Analytics workspace. Run mode has no environment and runs as before.
- **Every compute resource is a Container App that keeps one replica.** Aspire 13.6.5 already writes `minReplicas: 1`; Keycloak and RabbitMQ also get `maxReplicas: 1` (`WithSingleReplica`), since neither is set up to run twice at once. Only the edge, `host`, has external ingress (`WithExternalHttpEndpoints`); the services, Keycloak and the broker are internal.
- **The web app's dev server is run mode only.** Published, `web` is not a Container App; the edge will serve its build (a later part of #114). Aspire's experimental switch that disables the build-only container check is not used.
- **No region is named in the AppHost.** This ADR's own choice, so one AppHost publishes for any region: `main.bicep` takes `location` as a parameter, and the deploy workflow (later in #114) sets it to `germanywestcentral` and checks it.
- **Every publish-mode secret is a parameter the deployment sets, kept in the Key Vault `secrets`** (`src/AppHost/Wiring/DeploymentSecrets.cs`). `postgres-password`, `keycloak-admin-password`, `messaging-password`, `azure-openai-api-key`, `smtp-username` and `smtp-password` are secret parameters with no generated value and no published default; each is a Key Vault secret under its own name (the secret's resource is `<name>-secret`, as a resource may not share a parameter's name). Beside them, `postgres-username`, `messaging-username`, `smtp-host` and `smtp-from` have no default, `keycloak-admin-username` defaults to `admin` and `azure-openai-deployment` to `gpt-5-mini`, as in run mode. A deployment passes them as `Parameters__<name>`.
- **Every Container App reads a secret as a Key Vault reference, never as a value.** `WithSecret` (`src/AppHost/Wiring/SecretEnvironment.cs`) hands a resource the Key Vault secret that holds a parameter in publish mode and the parameter itself in run mode. A database's connection string is the Key Vault secret the Flexible Server's own Bicep writes (`connectionstrings--<module>-database`). The services and the migrations read what they reference as connection strings, service discovery and endpoints alone (`WithConnectionStringsOnly`): Aspire would also hand them each part of a connection as plain values, which nothing reads. `AppHostPublishParametersTests.No_container_app_receives_a_secret_as_a_plain_value` fails on any `@secure()` parameter of a Container App's module.
- **The broker's connection string is a Key Vault secret the AppHost composes** (`src/AppHost/Wiring/Messaging.cs`): `amqp://<user>:<password>@messaging:5672`, the broker's resource name and its endpoint's target port from the model. The Key Vault's Bicep cannot read a Container App's endpoint; given the broker's own connection string, Aspire writes `amqp://<user>:<password>@` without host and port. The name and target port are what Aspire itself writes for a service that references a TCP Container App.
- **PostgreSQL is one Flexible Server, `postgres`, with password authentication** (`src/AppHost/Wiring/Databases.cs`), a database per module, named after it, and one `keycloak`. Each service and its migrations read only their own as `database`. Its administrator is `postgres-username` / `postgres-password`. The size follows the environment (`DatabaseServerSize`):
  - `staging`: `Standard_B2s`, Burstable, backups kept 7 days. `Standard_B1ms` allows 50 connections, fewer than seven services' pools (EF Core, Marten, Wolverine) and Keycloak open.
  - `production`: `Standard_D2ds_v5`, General Purpose (the smallest), backups kept 35 days.
  - Neither has high availability or geo-redundant backups. Any other environment name fails the publish, naming `staging` and `production`. Run mode keeps the Postgres container with its data volume.
- **RabbitMQ stays a container**, published with its named data volume at `/var/lib/rabbitmq` (Azure Files), the user and password `messaging-username` / `messaging-password`, and no management UI. Run mode keeps the management UI and Aspire's generated password.
- **Keycloak's administrator and mail server are parameters once published** (`src/AppHost/Wiring/KeycloakSettings.cs`): `KC_BOOTSTRAP_ADMIN_USERNAME` from `keycloak-admin-username`, the password, `SMTP_USERNAME` and `SMTP_PASSWORD` from the Key Vault, `SMTP_HOST` and `SMTP_FROM` from their parameters. The services send through the same server (`src/AppHost/Wiring/MailServer.cs`, docs/adr/0004): the AppHost composes their connection string `mail`, `smtp://<smtp-username>:<smtp-password>@<smtp-host>:587`, into the Key Vault secret `mail-connection-string`, which every service reads as `ConnectionStrings__mail`, and they send from `smtp-from`; `frontend-url`, the web app's public URL, has no default. The development realm's bind mount and Keycloak's data volume are run mode only. Its production start, database and published realm come in a later part of #114.
- **The model's parameters reach every service as today** (`azure-openai-endpoint`, `azure-openai-deployment`), and the key as a Key Vault reference. Nothing provisions an Azure OpenAI resource; ADR 0006 says which endpoint a deployment uses.
- **The same commit publishes the same Bicep.** `.github/workflows/publish.yml` publishes `staging` and `production` on every pull request and on `main`, with a placeholder for every parameter without a default, publishes each a second time and fails on any difference (`diff -r`), and compiles every Bicep file it wrote with `az bicep build` (Aspire's `main.bicep` does not name the Container App modules, so compiling it alone would skip them). It signs in to nothing. `AppHostPublishTests.Publishing_twice_writes_the_same_bicep` checks the same in the tests.
- **The tests read the publish model in process.** `tests/Integration.Tests/PublishedAppHost.cs` builds the AppHost with the CLI's publish arguments and runs its publish pipeline into a temporary directory. The tests themselves need neither Docker nor the Aspire CLI, but they live in Integration.Tests, whose assembly fixture starts the whole application first, so a run of them does need Docker; moving the AppHost's model tests to a project of their own is a later change. `AppHostPublishTests`, `AppHostComputeTests`, `AppHostPublishParametersTests`, `AppHostPostgresTests` and `AppHostMessagingTests` hold the decisions above to it.

## Consequences

- Publish mode and run mode now differ in the AppHost: each publish-only branch is an extension in `src/AppHost/Wiring/` guarded by the execution context, so `AppHost.cs` still reads as one model, and the run-mode integration tests (`AppHostParametersTests`, `AppHostBlobContainersTests` and the rest) pass unmodified.
- The broker's connection string assumes Container Apps' internal addressing (`<app>:<target port>` for TCP ingress), as Aspire's own does. Main.bicep does not URI-escape a value it assembles, so `messaging-username` and `messaging-password` must be URI-safe (letters, digits, `-`, `.`, `_`, `~`); a wrong address or an unsafe password is first seen at the first deploy (#129).
- RabbitMQ on an Azure Files (SMB) volume, and internal TCP ingress in a Consumption environment, are first observed in #129.
- The Flexible Server's firewall allows all Azure IP addresses (`AllowAllAzureIps`, Aspire's default), so it has a public endpoint reachable from any Azure tenant, protected by its password and TLS (Npgsql's default `SslMode=Prefer` encrypts but does not verify the certificate). Private networking (a VNet for the environment, private access for the server) is part of the open decision on secrets and database roles below, to settle before #129.
- Each module's identity holds Storage Blob Data Contributor (and Aspire's table and queue data roles) on the whole storage account, not on its own container, so one service could read and write every module's blobs. That contradicts the owner's B2 (a role scoped to each module's container); the keyless-signing part of #114 replaces these grants with container-scoped ones.
- Every Container App's identity holds Key Vault Secrets User on the whole vault `secrets`, not on the secrets it references, and every module's database connection string uses the server's administrator login. So one compromised service (code execution, or a request forged to its managed-identity endpoint) could read every module's database, the Keycloak admin password, the SMTP credentials and the model's key. Secrets scoped per app, and a database role per module, are an open decision for the owner before #129 deploys (asked on #114).
- `postgres-password` must not contain `;`, `'` or `"`: Aspire assembles `Host=...;Password=...` into the Key Vault secret without quoting it. The deploy workflow (later in #114) checks this and the broker's URI-safe credentials before it deploys. `smtp-username` and `smtp-password` must be URI-safe too, as they are assembled into the mail connection string the same way.
- Traffic between the apps inside the Container Apps environment is not encrypted: the broker's AMQP, with its credentials, to `messaging:5672`. The services reach Keycloak through the environment's internal HTTPS ingress (`https://keycloak.internal.<default domain>`). Enabling the environment's peer-traffic encryption is part of the same open decision.
- Until the later parts of #114: Keycloak publishes in `start-dev` without a realm (no users, no clients), the SPA is not deployed, the blob signing still needs an account key the deployed account does not have (ADR 0002), and each `<module>-migrations` project publishes as a Container App of its own. Nothing deploys before #129, so none of this reaches Azure.
- A parameter without a value does not stop `aspire publish --non-interactive` (it writes Bicep alone), but the in-process test harness waits for input; both pass placeholders. `aspire publish` saves parameter values in `~/.aspire/deployments`; a developer who publishes locally with real values should remove that state afterwards.
- `fabric upgrade` regenerates files this decision changed and may conflict on them: `src/AppHost/AppHost.cs`, `src/AppHost/AppHost.csproj`, `Directory.Packages.props` and `tests/Integration.Tests/Integration.Tests.csproj`. Keep this decision's changes when resolving them. The new files (`src/AppHost/Wiring/*` beside `BrowserUploads.cs` and `ServiceHostProjects.cs`, `.github/workflows/publish.yml`, the tests above) are the project's own.
