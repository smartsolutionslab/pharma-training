# 0007: Four eyes is host configuration

**Status:** Accepted

## Context

- #18 adds the editorial workflow: an editor submits a draft for review, returns it to draft, publishes it and retires it. The `CourseVersion` aggregate already holds the rules; `Publish(editor, policy, now)` refuses the submitter with `FourEyesRequired` when the policy is `ReviewPolicy.FourEyes`.
- The domain README (row "Redaktions-Workflow") makes four eyes "eine Einstellung, zunächst aus — solange die Redaktion aus einer Person besteht". `ReviewPolicy`'s doc comment says it is "set per platform by the editorial team". The plan lists no settings endpoint and no settings screen, and the project has no settings module. Nothing in MVP 1 changes the setting at runtime.
- The AppHost must not get a line per module (AGENTS.md, "Topology: services"), and the Application project has no `IConfiguration` or `IOptions`.
- Each `CourseVersion` is its own aggregate; a course (`CourseId`) has none. Publishing a course's next version must leave the previous one `Superseded`, so that a course has at most one `Published` version. The aggregate's doc comment leaves that to the Application.

## Decision

- **Four eyes is deployment configuration, `Editorial:FourEyes`, off by default.** A deployment turns it on with the environment variable `Editorial__FourEyes=true` on the editorial service. There is no Aspire parameter, no AppHost line, no `appsettings.json` entry and no settings table: the default lives in code.
- **It is read once, at startup.** `EditorialSettings.ReviewFrom(IConfiguration)` (`Editorial.Api`) reads the key: absent or blank is `ReviewPolicy.SingleEditor`, `true` or `false` in any case (`bool.TryParse`) is `FourEyes` or `SingleEditor`, anything else throws `InvalidOperationException` naming the key and the values it accepts. `EditorialModule.AddServices` registers the result once as the singleton `ReviewSettings` (`Editorial.Application`, `ReviewSettings.Default` is `SingleEditor`), so a value the host cannot read stops it at startup, never on a publish. `PublishCourseVersionHandler` takes `ReviewSettings` by constructor.
- **A publish by the submitter under four eyes answers `403 editorial.four-eyes`.** The version is in the right state; only this caller may not publish it. ADR 0003 sets the precedent of `403` for "this caller may not here" decided behind the policy; its own code keeps it apart from a policy's `403`. Who may publish after whom is the Domain's rule, not a realm role, so `OnlyModulePoliciesCheckRoles` is untouched and the route keeps `editorial.edit`.
- **Four eyes also binds the question approvers** (the owner's decision of 2026-11-22, on #151). With four eyes on, the publisher must differ from the submitter and from everyone who approved any of the version's questions, so a second person has checked every question. The submitter may still approve questions before submitting; only the publisher is constrained.
  - `Publish` refuses an approver with `PublisherApprovedQuestions`, `403 editorial.publisher-approved-questions`.
  - When the publisher is both the submitter and an approver, the submitter's `editorial.four-eyes` wins.
  - A question copied from the previous version keeps its approver, and that approver counts too. The rule reads "approved any of its questions", and a copied approval is still that person's.
  - With four eyes off, nothing changes.
- **Four eyes also binds the editor who last changed the test blueprint** (the owner's decision of 2026-11-23, from the review of #241, #246). A changed blueprint resets every approval (#199), and the reviewers re-approve the changed test; the editor who changed it is a fourth eye only if someone else publishes.
  - `CourseVersion.BlueprintChangedBy` records the editor of every change of the blueprint that takes effect (the version is a draft and the new blueprint differs) **once the version has had an approval**: `CourseVersion.FirstApprovedAt` is set at its first approval (a next version takes its copied approvals' earliest; column `first_approved_at`). That is the issue's "changed after its last approval" (orchestrator reading of 2026-11-24, after #364's review, which the owner may overrule). It holds whether or not an approval is still there to reset, so neither a second change while nothing is approved nor an edit or chapter replacement that clears the approvals first hides a change from four eyes; a change before any approval records no one. The last change wins; saving the same blueprint again or a change refused as `NotADraft` leaves it as it is. Only the last changer is recorded, in the nullable column `blueprint_changed_by`. Rows that predate `first_approved_at` start without it; nothing is deployed yet (#114).
  - A return to draft and a resubmission keep it; `DraftNext` starts the next version without one, since the previous version's changes were reviewed before it was published.
  - Under four eyes `Publish` refuses that editor as it refuses the submitter: `FourEyesRequired`, `403 editorial.four-eyes`, whose fixed message (ADR 0027) now reads "Under four eyes, the editor who submitted this version or last changed its test blueprint cannot publish it." There is no new code.
  - It is checked with the submitter, before `PublisherApprovedQuestions`: a blueprint changer who also approved questions gets `editorial.four-eyes`.
  - Versions saved before the column existed have `null`, so nobody is refused for a change made before it.
- **Every approval reset raises `QuestionApprovalsReset(version, resetBy, reason)`** (#246), with the reason `TestSettingsChanged` (`SetBlueprint`), `QuestionEdited` (`EditQuestion`) or `ChapterReplaced` (`ReplaceChapter`). The three commands and their `PUT` routes carry the calling editor, and a caller whose token names no person answers `403 editorial.identity-incomplete`. The event is raised once per change, and only when at least one approved question went back to unreviewed; nothing is raised when nothing approved was reset, nothing changed, or the change was refused. It is `[DeliberatelyUnhandled]` and not stored: the four-eyes rule reads `BlueprintChangedBy`, saved in the version's own save, and a reaction runs after the commit and is never retried, so none could keep a reliable trail. A stored reset history would be rows of its own, as returns are (ADR 0013), and is a separate issue.
- **Supersede happens in the publish handler's single save.** The handler loads the version, then the course's `Published` versions (`ICourseVersionStore.ListPublishedForUpdateAsync`, tracked, without content), publishes, calls `Supersede()` on each predecessor and commits once with `TryCommitAsync`. A publish the Domain refuses saves nothing, so no predecessor is superseded by a publish that failed. It is not a domain-event reaction: a reaction runs after the commit, and one that throws is logged and never retried, which would leave two `Published` versions. It is not an integration event either: both aggregates live in this module, its DbContext and its transaction. Nothing announces a supersede; Catalog already takes a course's highest version number as current. Catalog derives each version's status (`Current`, `Superseded` or `Retired`) when it reads it (#182). A retirement of the newer version that reaches Catalog before that version's publish leaves the older one reading `Current` until the publish arrives, because `CourseVersionRetiredV1` carries no version number; that is eventually consistent and accepted.
- **At most one `Published` version per course is guarded by row versions (ADR 0002), not by an index.** `Supersede()` modifies the predecessor's row, so the save carries `WHERE xmin = @loaded` for it. Two publishes that supersede the same predecessor, or a publish and a retire of the predecessor at the same time: one commits, the other loses the race and answers `409 editorial.course-version-changed`.
- **No partial unique index on `course_id WHERE status = 'Published'`.** PostgreSQL checks a non-deferrable unique index per statement, and EF Core orders the two UPDATEs of one save by key, not by intent, so a publish could fail on its own supersede. The deferrable alternative, an exclusion constraint, fails with `23P01`, which `UniqueConstraintResponses` does not map, so the caller would get `500`.

## Consequences

- Turning four eyes on or off is a redeploy (or a restart with the new environment), done by whoever runs the platform, not by editors. If editors are to switch it in the app, that is a separate issue: an Application port backed by a table replaces the singleton, with an endpoint, a screen and a policy for who may change it. Only the registration and the handler's constructor change; the use case is not reworked.
- **The integration run has four eyes on (#246).** `AspireFixture` sets `Editorial__FourEyes=true` for the integration run only; the AppHost's run-mode default and the end-to-end (Playwright) run stay as they were, so a local editor still publishes their own version. The realm has three editors, `editor`, `editor-b` and `editor-c`; the integration tests publish as `editor-c`, who neither submits, approves nor changes a version's test settings. Four eyes off is covered by unit tests of the domain, the handler and `EditorialSettings`. This replaces the earlier choice that the integration tests show the default: proving the refusals end to end (#246) needed four eyes on, and a second application run was still too costly.
- Retiring stays a one-person step, also under four eyes (the owner, 2026-11-22). It breaks nothing: running sessions and issued certificates stay valid. Four eyes guards publishing. Recording who retired a version (`RetiredBy`), and who returned one (`ReturnedBy`, with a `CourseVersionReturned` domain event), follows #18 in its own pull request (every return with its reason since #181, ADR 0013).
- With #18 alone a course has exactly one version: `DraftFirst` gives each course a new `CourseId`. A second version needs `DraftNext`, through `POST …/{id}/next` (#20). The row versions do not cover two concurrent first publishes of one course with no predecessor; that needs two unpublished versions of one course, which only #20 can create. **Hand-off to #20:** add a unique index on `(course_id, number)` and the matching check in its handler ("Back every uniqueness rule twice", AGENTS.md), so two successors of one version cannot exist, and replace the integration tests' `SeedAsNextVersionAsync` with `POST …/next`.
- #19 adds `CourseVersionPublishedV1` and `TestDefinitionPublishedV1` inside `PublishCourseVersionHandler`, before its `TryCommitAsync`, so a lost race sends neither.
