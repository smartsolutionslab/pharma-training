# 0011: Each service has a broker user of its own

**Status:** Accepted (#183). The owner decided on 2026-11-22, in the review of #180, that each service gets its own broker user and secret parameters in run mode and once published. Amended after the review of 10e2dcd: user names are the modules' and placeholders like the passwords, and the broker's entrypoint fails closed (D3, D4). D5 (#202) adds the integrity of event types, which the owner required before going live in the review of #200.

## Context

- Until #183 every service connected to RabbitMQ with the one `messaging` credential, the broker's admin (`messaging-username` / `messaging-password`, Aspire's `guest` in run mode). Whoever held it could declare a queue, bind it to any exchange and read it, or publish any event.
- `TestDefinitionPublishedV1` (#180) carries every answer's `IsCorrect`. With the shared credential any service could bind a queue to its exchange and read every solution (review of #180, item 3c).
- What Wolverine declares on the broker (observed before the change, T0 of #183): every service listens on one queue named after its module (`Messaging:Queue`, fabric's `backend-topology-services` and `backend-bus-transport-rabbitmq`). Each event's exchange is a fanout exchange named after the event's full CLR name (`SmartSolutionsLab.PharmaTraining.Contracts.Editorial.TestDefinitionPublishedV1`). A listener declares its queue and the exchange of each event it consumes, and binds them, at startup; a sender declares the exchange of what it publishes on its first send and declares no queue. Every service host opens two Wolverine connections (listening and sending). An event a module both publishes and consumes is local to its host (ADR 0004): no exchange, sender or binding.
- RabbitMQ permissions are three regular expressions per user and vhost, not anchored: configure (declare or delete), write (publish to an exchange, bind a queue to it as the queue's side) and read (consume, `basic.get`, purge, and the exchange's side of a bind). Topic permissions apply to topic exchanges only.
- Aspire.Hosting.RabbitMQ 13.6.5 offers nothing for users or definitions. Published, the broker is an internal Container App without its management plugin (ADR 0005), and the AppHost does not run beside it.

## Decision

- **D1. Each service host's module `m` gets the user `m` on the vhost `/`, which may use its own queue, publish its own module's events and bind to the events it consumes, and nothing else.** With `C(m)` the exchanges of the events m's consumers take from the broker and `P(m)` the exchanges of the integration events in `SmartSolutionsLab.PharmaTraining.Contracts.<M>`, both minus the events local to m's host:
  - configure `^(m|P(m)…|C(m)…)$`: its queue and the exchanges Wolverine declares for it;
  - write `^(m|P(m)…)$`: its queue (the queue's side of a bind) and its own events' exchanges;
  - read `^(m|C(m)…)$`: its queue and the exchanges it binds to.

  Every pattern is anchored and each name `Regex.Escape`d; names are letters, digits, dots and (in a module's name) `_`, `~` and `-`, each literal in .NET's and RabbitMQ's regular expressions alike. So Catalog may not bind a queue to `TestDefinitionPublishedV1`, no service may read, declare or delete another's queue, publish to another module's events' exchanges, or publish straight to a queue through the default exchange (`amq.default`). What the broker limits is the exchange a service writes to, not the event type inside: Wolverine picks the handler from the envelope's `message-type` header, which the publisher sets (D5). No topic permissions are defined: every exchange here is fanout, and an existing fanout exchange cannot be redeclared as a topic one.
- **The admin user stays**, with the tag `administrator` and `.*` on everything, for the broker itself, Aspire's health check in run mode, operators and the integration tests. No service holds it.
- **D2. `C(m)` and `P(m)` are derived from the code, with no list of modules** (`src/AppHost/Wiring/MessagingTopology.cs`). `AppHost.csproj` builds every `src/Modules/*/*.Application` and `src/Contracts` through one glob `ProjectReference` without referencing their output (`ReferenceOutputAssembly="false"`, `IsAspireProjectResource="false"`), and records each assembly's path on its own assembly as `AssemblyMetadata("MessagingAssembly", <path>)`. `MessagingTopology.Of(module)` reads them with `System.Reflection.MetadataLoadContext`, loading no module code: the consumed events are the first parameters of the `Handle`/`HandleAsync`/`Consume`/`ConsumeAsync` methods of the module's exported `*Consumer` classes, the same rule as the host's `LocalMessageTypes` (`src/Host/Wiring/Messaging.cs`); the published ones are the `IntegrationEvent` types of its contract namespace. A module whose Application was not built fails, naming it and the glob. The architecture rules `ModulesPublishOnlyTheirOwnEvents` and `IntegrationEventsBelongToAModule` keep the convention true. A grant smaller than what Wolverine declares makes a service unhealthy, which every messaging integration test sees; a larger one fails `BrokerPermissionsTests`.
- **D3. Each user is named after its module, and its password is an Aspire parameter, created in `AddMessaging`'s loop over the service hosts.** No parameter overrides the name: an overridden name could equal the admin's or another module's and take over that user's definitions entry (the admin could lose `.*`, or one module take another's password). The AppHost refuses to start for a module whose name is not URI-safe (letters, digits, `.`, `_`, `~`, `-`) or two modules whose broker variables would be one. `messaging-<m>-password` is, in run mode, generated (22 letters and digits) and kept in the AppHost's user secrets like the admin's, so a data volume keeps working across restarts; published, it is a secret parameter without a default, held in the Key Vault like every other (ADR 0005). Each service gets `ConnectionStrings__messaging` for its own user and `Messaging__Queue` from one call, `WithMessaging(broker, secrets, module)`: in run mode as a value, published as the Key Vault secret `messaging-<m>-connection-string` (`amqp://<user>:<password>@messaging:5672`), which `SecretAccess` grants that service alone. The admin's connection string, `messaging-connection-string`, is no longer stored.
  - `.github/workflows/publish.yml` writes a placeholder `Parameters__messaging-<module>-password` for every `src/Services/*/Host/Host.csproj`'s `<ModuleName>` and fails when it finds none; no module is listed there.
  - No deploy workflow exists yet (#114, #129). The one #114 writes sets `Parameters__messaging-<module>-password` for every service host found the same way, each from a secret of a GitHub environment's own (`MESSAGING_<MODULE>_PASSWORD`), never by reading every repository secret into one step through `toJSON(secrets)`; a missing one fails the deploy, naming it. Should it miss one, the broker's entrypoint still refuses to boot (D4).
- **D4. The broker imports the users, the admin and their permissions from a definitions document at every boot.** The AppHost composes it as JSON and hands it to the container as the environment variable `BROKER_DEFINITIONS`, the same plain text in both modes and for every deployment: it carries no user name and no password. Each user's `name` (and the `user` of its permissions) and `password` are placeholders `@@<VARIABLE>@@` of variables of the broker's own: `RABBITMQ_DEFAULT_USER` and `RABBITMQ_DEFAULT_PASS` for the admin (as Aspire sets them), `BROKER_USER_<MODULE>` and `BROKER_PASSWORD_<MODULE>` (the module upper-cased, any character but an ASCII letter or digit as `_`) for each service, set in the same loop over the service hosts. `BROKER_USER_<MODULE>` is the module; in run mode each password variable is the password parameter; published, each is a Key Vault reference of its own, `messaging-password` and `messaging-<m>-password`, which `SecretAccess` grants the broker alone, and the vault holds no definitions document. The broker's entrypoint is `/bin/bash -c <script>` (`Wiring/Messaging.cs`). It fails closed: it walks the placeholders in the document, not the variables that are set, and refuses to boot, naming the variable and never printing its value, when a placeholder names a variable other than those four kinds, or one that is not set, is empty, or holds a character outside `[A-Za-z0-9._~-]` (spelled out in the script, so no locale widens it), when two user variables name the same user, and when anything that looks like a placeholder is left after the walk. That character set is what the connection strings need (URI-safe, see Consequences) and needs no escape in JSON, so no value can break the document or add an entry to it, and since no value holds `@`, none can bring in another placeholder that a later substitution would fill. It then writes the document to `/tmp` in the container's own layer (never the data volume), sets `load_definitions` in `/etc/rabbitmq/conf.d`, and `exec`s the image's `docker-entrypoint.sh rabbitmq-server` through `env` without `RABBITMQ_DEFAULT_PASS` and without every `BROKER_*` entry `env` lists (bash cannot unset an entry whose name is not a shell identifier, but hands it on). With definitions loaded, neither the image's entrypoint nor RabbitMQ reads `RABBITMQ_DEFAULT_PASS`; Aspire's health check connects with the connection string it holds itself. `BrokerEntrypointTests` runs the script in the broker's image against each refusal. The image starts as root; its entrypoint runs RabbitMQ as `rabbitmq`, so both files are root's with the group `rabbitmq` and mode 0640: the broker reads them but cannot change its own definitions. The image lets `rabbitmq` own `/etc/rabbitmq` and `conf.d`, and a container's writable layer outlives a restart, so a broker process could leave a symlink for the next boot: the script refuses to boot unless both directories are directories of their own, clears each file's path before writing it, writes with `noclobber` (which bash applies to regular files alone, so a write never replaces a regular file that reappeared), gives each file its mode as it is created (a `umask` of 027 for the two writes, never `chmod`, which follows a symlink; RabbitMQ itself still starts with 077), and changes a symlink's owner rather than its target's (`chown -h`). RabbitMQ 4.3 (both the plain and the `-management` image) hashes a plain-text `password` on import, observed in #183. Importing definitions, RabbitMQ seeds no default user, so the document carries the admin too, with the same user and password Aspire sets as `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS`. Users are ordered by module, so two publishes write the same Bicep.
- **D5. A service handles an event from the broker only when the module that declares it published it (#202).** Wolverine dispatches by the `message-type` the publisher sets, whatever exchange a message arrived on, so D1's grants alone let Organisation put a message typed as Editorial's `CourseVersionPublishedV1` on its own `MembershipStartedV1` exchange, bound to Compliance's queue, and Compliance would handle it.
  - Every message a service sends carries its own broker user as the AMQP `user_id` property. RabbitMQ refuses (`PRECONDITION_FAILED`, closing the channel) a `user_id` other than the connection's user; no user has the `impersonator` tag.
  - On receipt, `PublisherEnvelopeMapper` (`src/Host/Messaging/`, wrapping Wolverine's own `RabbitMqEnvelopeMapper` on every conventional listener and sender, `src/Host/Wiring/Messaging.cs`) keeps that `user_id` as the envelope header `pharma-broker-user-id`. It writes the header after the publisher's own headers, so a header of that name the publisher sets is replaced, or removed when the message has no `user_id`. The header travels with the envelope into the inbox and the dead letters, so a recovered or replayed envelope is checked the same way.
  - Only a module's integration event, in `application/json`, travels on the broker. The mapper gives anything else the type `pharma-training.refused-broker-message`, keeping what it came with in the header `pharma-refused-message-type`. It refuses a `message-type` that is not `SmartSolutionsLab.PharmaTraining.Contracts.<Module>.<Event>` with both segments of ASCII letters, digits and underscores only (`BrokerPublishers.ModuleOf`), and any content type but `application/json`. A control character, a space, punctuation or a non-ASCII letter in the type names no module, so it is refused like any other non-event: a NUL there reached the inbox's text column `message_type`, which PostgreSQL refuses (22021), and Wolverine paused the listener and redelivered the same message first, without end (#230, #232). What a publisher chose that the dead letter's row keeps as text is escaped, every control character written as `\uXXXX`: the `source` header, which becomes the row's `source` column, and the refused type in `pharma-refused-message-type`; the row's `message_type` is the refused type. A NUL in `source` made the dead-letter insert fail, and Wolverine completed the refused message, neither handled nor kept (#338, #232). No handler has that type, and `UnknownMessageBehavior.DeadLetterQueue` dead-letters it. Without this, Wolverine's own handlers, which no middleware wraps, would take such a message from the queue: a `scheduled-envelope` (`binary/envelope`) is forwarded to whatever destination the envelope inside names, a local queue among them, where the check below does not look, and agent commands reach the durability agents (review of #211). The mapper retypes the message rather than throwing, and does the same when Wolverine's own mapping throws on a header it cannot read (a `reply-uri` that is no URI): Wolverine 6.64.0 cannot dead-letter a message it failed to map (the dead-letter write throws a `NullReferenceException` on the envelope's missing destination) and reschedules it instead, without end. `BrokerPublisherIntegrityTests` shows both, that the next message on the queue is still delivered, and that the refused message is found in the dead letters.
  - The middleware `PublisherCheck`, before every consumer, refuses an envelope from anywhere but this host's local queues (`local://`), one without a destination included, unless its event lies in `SmartSolutionsLab.PharmaTraining.Contracts.<Module>` and its `user_id` is `<Module>`'s user. A refused envelope fails with `ForgedPublisherException`, which is dead-lettered at once, without the retries of any other failure: retrying cannot change who sent it, and replaying it fails the same way. A message without a `user_id`, or of a type outside a module's contract namespace, is refused too. Events on a host's local queues (ADR 0004) are its own and are not checked. Wolverine's control messages come through the database to its own handlers, which no middleware wraps, so they never reach the check; an envelope that names a `dbcontrol://` destination and does reach a consumer is checked like any other (`BrokerPublisherRefusalTests`).
  - Each service learns every module's user name from the AppHost, `Messaging__Publishers__<module>` = `<module>`, since every user is named after its module (D3), set in `WithMessaging` for every service host; no module is listed anywhere. A host refuses to start without the section or when two modules name one user. User names are no secret.
- Rejected: `rabbitmqctl` or the management API from the AppHost (run mode only; published, the AppHost does not run beside the broker and the management plugin is off); an init container or job calling the management API (it needs the plugin, a port and a second app holding the admin password, and does not run on a broker restart); a definitions file with `password_hash` (Bicep cannot hash, and published passwords exist only at deploy time); a file mount (not available for Container Apps, and the content is secret).

## Consequences

- Configure on an exchange also allows deleting it, so a consumer or the publisher of an event can delete its exchange, and the other consumers lose their bindings until they restart. That costs availability, not confidentiality, and is accepted.
- A service may bind an exchange of its own events to one it reads (`exchange.bind`) and so pass on events it already receives to its own consumers' subscribers. A service that reads an event can pass its content on in code anyway; accepted.
- Payloads stay in clear on the broker's volume (Azure Files once deployed) and in each service's Wolverine outbox, inbox and dead-letter tables in its own database: `TestDefinitionPublishedV1`'s solutions sit in Editorial's outbox until sent and in Assessment's inbox and dead letters. Accepted.
- Every boot re-imports the document, so a rotated password or a changed grant applies at the broker's next restart, and a new service host's user appears then. A user of a removed module is not deleted; remove it by hand (`rabbitmqctl delete_user`).
- A new module needs nothing in the AppHost, the workflow or the edge, but a deployed environment needs its password secret (`MESSAGING_<MODULE>_PASSWORD`) before its next deploy; #129's setup list grows by one secret per module.
- Every broker user name and password must be URI-safe (letters, digits, `-`, `.`, `_`, `~`): Main.bicep inserts them unescaped into the connection strings. The broker's entrypoint enforces it for every user name and password it puts into the definitions, so a deployment with an unsafe value, or a missing or empty one, gets a broker that does not start and a log line naming the variable, instead of a user whose password is the literal placeholder or empty.
- Until this design, the definitions were the Key Vault secret `messaging-definitions`, and Aspire named that secret's Bicep parameter in `secrets.bicep` after the whole expression, an identifier of several thousand characters, which Bicep refuses (BCP024, limit 255). Every password is now a Key Vault reference of its own, and the definitions, holding only placeholders, a plain value. `AppHostBicepIdentifiersTests` publishes staging and production and fails on any declared Bicep symbol longer than 255 characters, since Aspire names parameters after the expressions it is handed and any other expression could do it again.
- RabbitMQ's process does not hold the passwords, but the container's configuration does: every password variable stays in what `docker inspect` or the Container App's revision shows, and in the environment of a shell an operator opens with `docker exec` or `az containerapp exec`. Whoever may open a console on the broker may read every service's password, as they could read the definitions before; grant that access accordingly.
- Integrity of event types is covered (D5) for what arrives through the broker: a service can publish only its own module's events, under its own user. It does not cover the content: a service can still publish wrong data in an event of its own module. The admin user (operators, the integration tests) publishes under its own name, which no module's is, so whatever it sends is dead-lettered; a test that sends an event as its publisher does uses that module's credentials (`tests/Integration.Tests/Broker.cs`). `BrokerPublisherIntegrityTests` shows a forged type, a message without `user_id` and a forged course version inside a `scheduled-envelope` dead-lettered at once and never stored, and the broker refusing a `user_id` that is not the connection's. `BrokerPublisherReloadTests` and `BrokerPublisherRecoveryTests` show a legitimate event handled after a scheduled retry, a dead-letter replay and a restart of its service with the envelope in the inbox, so the header survives Wolverine's storage; `tests/Host.Tests` pins `BrokerPublishers.RefusalOf`, the mapper and the start-up checks. Run them after every Wolverine upgrade.
- Envelopes stored before D5 carry no `pharma-broker-user-id`: broker messages waiting in an inbox for a retry, and dead letters. After the upgrade they are refused as forged, and replaying them fails the same way. Before D5 goes live (#129), drain each service's queue, inbox and dead letters.
- With `UnknownMessageBehavior.DeadLetterQueue`, a message no handler takes is dead-lettered rather than logged and dropped, the deliveries of a stale binding (below) among them; operators find them in `wolverine_dead_letters`.
- The check runs before every consumer and reads the envelope's message type and one header; it costs no I/O. A forged message still takes a place in the consumer's inbox and then its dead letters, where an operator sees it with `ForgedPublisherException` and the user that sent it.
- Narrowing a grant does not remove a binding that already exists: durable bindings are not re-checked against permissions at import. A module that stops consuming an event keeps receiving it until its binding is removed, and a binding made while every service held the admin credential survives the switch on an existing data volume. For an existing broker (a developer's volume, or #129), list the bindings no read grant covers and remove them by hand once.
- `messaging-username`, the admin's name, is still a parameter the deployment sets. A value equal to a module's name fails the broker's boot (D4), so the admin's name must not be any module's.
- `MessagingTopology` reads a consumer's handler signature from metadata by name (`SignatureTypeNames`) and takes only the first parameter, the message, granting its exchange only when it is an integration event of the contracts (a helper named like a handler grants nothing), so a consumer that also takes a service of another assembly (`IDispatcher`, `ILogger<T>`, an injected `Wolverine.IMessageContext`, as AGENTS.md allows) no longer stops the AppHost: until #202 it decoded every parameter through `MetadataLoadContext`, which failed on an assembly it could not resolve. `MessagingTopologyTests` compiles a probe Application with such a consumer and reads it through `MessagingTopology.Of(module, assemblyPaths)`. Its lookup still assumes a module's `<ModuleName>` matches its `Modules.<Module>.Application` assembly (ignoring case) and that Wolverine names an exchange after the event's full type name (no `[MessageIdentity]` alias); either mismatch fails closed.
- RabbitMQ's regular expressions let `$` match before a final newline, so `^(catalog)$` also matches `catalog\n`: a user can create resources only under its own names, with or without a trailing newline; accepted.
- `fabric upgrade` may conflict on `src/AppHost/AppHost.csproj`, `src/AppHost/Wiring/Messaging.cs` and `src/Host/Wiring/Messaging.cs`, which this decision changes beyond the generated shape.
- The entrypoint on Container Apps (the image's user, `/etc/rabbitmq/conf.d` being writable) and Khepri on the SMB volume are first observed in #129.
