# 0013: Every return of a course version is recorded in the version's own save

**Status:** Accepted

## Context

- Until #181 a return of a course version to draft overwrote `ReturnedBy` and `ReturnedAt` on the version and raised `CourseVersionReturned`, which nothing handled. A second return lost the first, and no return said why. The owner decided on 2026-11-22 that every return is kept, with who returned the version, when and why, as an audit trail.
- A domain-event reaction runs after the commit; one that throws is logged and never retried (AGENTS.md, "Module style: domain-driven design"). A record written there could be lost while the version is already back in draft. ADR 0007 rejected a reaction for supersede on the same grounds.
- Every command on a course version loads it whole, chapters, questions and options, in one REPEATABLE READ snapshot of split queries (#170). No rule of the version reads its past returns, and their number grows with every resubmit and return.

## Decision

- **A return is a record of its own, `CourseVersionReturn`** (Domain, `CourseVersions/`): its id, the version, who returned it, when and the `ReturnReason`. It has no setters and no methods, and its only constructor is internal to the Domain, so only `CourseVersion.ReturnToDraft(editor, reason, now)` makes one. That method returns `Result<CourseVersionReturn, CourseVersionWorkflowError>`: on success it puts the version back in draft, keeps the latest editor and time on the version, raises `CourseVersionReturned(version, editor, reason)` and hands back the record. Four eyes does not apply to returning.
- **It is stored in the version's own save.** `ReturnToDraftHandler` adds the record through `ICourseVersionStore.AddReturn` and commits once with `TryCommitAsync`. The status change and the record are one transaction, under the version's row version (ADR 0002): `RowVersionBump` follows the record's foreign key to the tracked version, so of two concurrent returns one commits and the other answers `409` with neither its status change nor its record saved. A return the Domain refuses saves nothing.
- **`CourseVersionReturned` stays `[DeliberatelyUnhandled]`**, with the reason that the use case stores the record in the same save; a reaction would add nothing but the risk of losing it (agreed with the coordinator for #181).
- **Its own table, `editorial.course_version_returns`**, with a foreign key to `course_versions` (on delete cascade) and an index on `(course_version_id, returned_at)`. The aggregate has no navigation to it and its load does not include it, so no command pays for the history. `GET /editorial/course-versions/{id}/returns` (`editorial.edit`) reads it a page at a time, newest first, then by id (a Guid v7) newest first; an unknown version is `404 editorial.course-version-not-found`.
- **The reason rules** (`ReturnReason`): the text is trimmed and is 1 to 1000 characters after trimming, counted as Unicode scalar values (an emoji outside the BMP is one character, not two UTF-16 code units; PostgreSQL's `varchar(1000)` counts the same way), so a textarea's trailing newline does not tip a reason of 1000 characters over. It holds no control character but `\n`, `\r` and `\t`, and no character of the categories Format, LineSeparator, ParagraphSeparator, PrivateUse or OtherNotAssigned, so a text of zero-width characters alone is refused, as `ContentReviewAnswer` refuses it in a hint. An unpaired surrogate is refused too: it is no character at all. Markup is kept as written: it is the editor's own text, answered as a string and shown as text.
- **The body is required.** `POST /editorial/course-versions/{id}/return` takes `{"reason": "..."}` (`ReturnEditorialCourseVersionRequest`). The endpoint reads the body itself, after authorization (`401`, `403`) and after the caller's person is known (`403 editorial.identity-incomplete`), whatever the body's content type: the route carries no `Accepts` metadata, which would make routing answer `415` before either, and an operation transformer describes the required JSON body in the OpenAPI document instead. A reason that is missing or invalid answers `400 editorial.invalid-return-reason`, before anything is dispatched; so does a body that cannot be read (not JSON, no or another content type, a charset other than UTF-8, bytes that are not UTF-8), with the same code and message, so a caller has one code to handle. A body over 16 384 bytes answers `413`: a reason of 1000 characters, each escaped as `\uXXXX` (one outside the BMP as two), is at most 12 000 bytes plus its envelope, so no valid reason is refused.

## Consequences

- `ReturnedBy` and `ReturnedAt` stay on the version as the latest return, written by the same method as the record, so the two agree. The latest reason is the first item of `GET …/returns`; the version has no reason column.
- **No backfill.** A version returned before this migration has `returned_by` and `returned_at` and no record: the migration does not invent a reason. Those columns keep that last return visible.
- A future caller of `ReturnToDraft` must add the record it returns. There is one caller; its unit tests assert the stored record and the integration tests list it.
- The return route's contract changed: the generated client's `postEditorialCourseVersionsIdReturn` now takes a body. Nothing in the web app called it; the frontend's return dialog (#26) asks for the reason.
