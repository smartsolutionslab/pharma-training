# 0014: The invitation link's token crosses the sign-in in sessionStorage

**Status:** Accepted

## Context

- The invitation mail links to `{frontend}/invitations/accept#token=<43 URL-safe characters>` (ADR 0004). The fragment keeps the token out of access logs and `Referer`, but browsers still keep it in their history and synced tabs, and every script on the page can read `window.location` (review of #9, PR #138). #9's review asked the page to read the fragment once and clear it with `history.replaceState` before anything else loads.
- Accepting (`POST /organisation/invitations/accept`, #10) needs a signed-in caller: who accepts comes from the access token, the token only from the body. The web app sends every anonymous visitor to Keycloak at once (`SignedIn.vue`), so the token has to survive a round trip through the identity provider, and for a person without an account through Keycloak's registration and the verification mail as well.
- Before #13 the sign-in always came back to `window.location.origin` (`oidcConfig.redirect_uri`) and `createAuth` replaced the address with its path, so every deep link was lost on sign-in.
- Routes come only from `src/modules/*/routes.ts`, all under `/<module>/…`; `/invitations/accept` is at the root, and no module list may be written into `src/router.ts`.
- Self-registration in the realm belongs to #13 (ADR 0004, Context, per the owner on #9). The security review of #9 (comment of 2026-11-22 00:52 on #13) made limits on invitation mail a must-do before registration opens to the public: once anyone can create an account, anyone can register a pharmacy, become its manager and invite or renew without limit, from our sender domain. Those limits are #158 (lane backend; the owner's decision of 2026-11-22, with a per-user limit on accept added the same day).

## Decision

- **A page at an address of its own.** A module may declare `entries` in its `routes.ts` (`ModuleEntry` in `src/modules/index.ts`): a page that a link from outside the app opens, at an absolute path, with a title key and an audience, and an optional `beforeEnter` guard. `src/router.ts` builds them as it builds pages, by convention; the breadcrumbs name an entry by its title (Home › Einladung annehmen); the sidebar and the command palette leave entries out. Organisation declares `/invitations/accept`, audience `signed-in`: every signed-in user, with or without a pharmacy.
- **The token's round trip, in this order:**
  1. **Fragment.** The browser opens `/invitations/accept#token=…`. The fragment never reaches a server.
  2. **Route guard.** The entry's `beforeEnter` (`captureInvitationLink`, `src/modules/organisation/invitationLink.ts`) parses `to.hash` with `URLSearchParams`, validates the token with Zod (`/^[A-Za-z0-9_-]{43}$/`) and drops any token kept earlier.
  3. **sessionStorage, for this tab, for 30 minutes.** A valid token is kept under `invitation-token` in `sessionStorage`, and the time its link was opened under `invitation-token-kept-at`. Never `localStorage`, a Pinia store or a URL. A later link replaces both, so its 30 minutes start again.
  4. **Replace without the hash.** The guard redirects to the same path without the fragment with `replace`, so vue-router's `history.replaceState` takes the token out of the address and the current history entry. `replaceState` rewrites the current entry of this tab's session history only: the URL first loaded, with its fragment, may remain in the browser's global history and in the address bar's autocomplete, and nothing a page does removes it there. That is mitigated, not prevented: the token is single-use, bound to the invited and verified e-mail address (#10), and a token kept in the tab lapses after 30 minutes.
  - **A second link while the page is shown.** Opening another invitation link in the same tab while `/invitations/accept` is shown changes only the fragment; vue-router reuses the page and runs no `beforeEnter`. The page runs the same capture (`captureFrom`) in its `onBeforeRouteUpdate`: the fragment leaves the address without a new history entry (the redirect to the address already shown may end as a duplicate navigation, which changes no history), and the page takes the new token, which replaces the one before (ready, refused or still being accepted), and shows it ready to accept, posting nothing until the button is pressed; a malformed token leaves the page saying to open the link again. It also replaces an accept in flight, whose answer is then ignored: the user may already have joined the first pharmacy, and the pharmacy switcher catches up on its next read of the memberships. A newer link likewise wins over moving on after a success: the page neither tells the user about the first pharmacy nor leaves for Meine Schulungen, and the second link stays ready.
  5. **Sign-in, returning to origin + pathname.** `SignedIn` starts the sign-in only once the router's first navigation has settled (`router.isReady()`), so the fragment is gone before the first request to Keycloak. `createAuth` passes `redirect_uri: window.location.origin + window.location.pathname` to `signinRedirect`: no query, no fragment. oidc-client-ts keeps that `redirect_uri` with the request's state and uses it for the code exchange. This applies to every page: a deep link now survives sign-in. On the way back (`?code&state`) the guard finds no fragment and leaves the kept token alone; `createAuth` drops the query as before.
  6. **One read-and-remove.** When the page is set up (`useAcceptInvitation`) it takes the token with `takeInvitationToken()`, which reads and removes it and its time in one call and validates it with Zod again, since storage is untrusted input. A token kept 30 minutes or more ago, or kept without its time, is not taken: the page says to open the link again. It lives on in component-local memory only. The page then shows it ready to accept: a heading (Einladung annehmen), a sentence saying the user was invited to join a pharmacy, and an Einladung annehmen button. It does not name the inviting pharmacy (see the preview under Alternatives) and reads nothing about it before accepting.
  7. **One POST, on the click.** The page posts the token only when the user presses Einladung annehmen (the owner's decision on #13, 2026-11-23), never as it opens, and once however often the button is pressed, in the body of `POST /organisation/invitations/accept`; only then does it read the memberships and the pharmacy it joined. Retry is offered only where trying again can succeed (429, 409 `organisation.pharmacy-changed` or `organisation.invitation-changed`, the latter with a text of its own saying to try again, 5xx, the network) and posts the same in-memory token again, once however often it is pressed; nothing writes it back to storage. A Retry answered 404 `organisation.invitation-not-found` says the invitation may already have been accepted by the attempt whose answer never arrived, and leads to Meine Schulungen.
- **Not oidc-client-ts's state, and not the URL.** oidc-client-ts's `state` could carry data across the sign-in, but its state store is `localStorage`, shared by every tab and kept after the tab closes; the `state` sent to Keycloak stays its random id. A query parameter or a path segment would reach the dev server, Keycloak's logs and `Referer`, which the fragment exists to avoid.
- **Self-registration with a verified address.** The development realm (`src/AppHost/realms/realm.json`) sets `registrationAllowed: true`: an invited person without an account uses Keycloak's own Register link on its login page (Keycloak's pages, not ours). `VERIFY_EMAIL` is a default required action (`requiredActions`, `"defaultAction": true`): Keycloak adds it to every account created after the import, by registration or the admin API, so a new account must follow the verification mail (Mailpit locally) before it can sign in; a password grant before that answers `400 invalid_grant` ("Account is not fully set up"). The realm-wide `verifyEmail` stays `false`: imported users are created without default actions and keep signing in as they did, `unverified` (`emailVerified: false`) included, whose password grant #10's tests rely on. A realm file that lists any required action replaces Keycloak's defaults, so `requiredActions` is Keycloak 26.6's complete default list, read from a freshly imported realm, with only `VERIFY_EMAIL`'s `defaultAction` changed. Because the list replaces the defaults, a required action a later 26.x image adds to them is not in the realm until it is added to `requiredActions` in `realm.json`; compare the list with a freshly imported realm when the image is upgraded. Following the verification mail in the same tab completes the sign-in and returns to the page with the token still kept; in another tab (another `sessionStorage`) the page finds no token and says to open the invitation link again, which is still valid, since nothing accepted it.
- **The published realm may allow registration only once all of this is in place.** The realm in `realms/` is imported in run mode only (ADR 0005); the published realm is a later part of #114. Opening registration here opens it on developer machines and in CI, not to the public. #114 keeps `registrationAllowed: false` in the published realm until every one of these holds:
  - #158's limits on invitation mail are merged: a per-caller rate limit on invite and renew, a cooldown on renewing one membership, a cap on open invitations, a per-user limit on accept.
  - Keycloak's brute-force detection is on (`bruteForceProtected: true`), with lockout settings chosen for the published realm.
  - The registration form has bot protection (Keycloak's reCAPTCHA or an equivalent), so accounts cannot be created by script.
  - Account enumeration on register has been considered: Keycloak's registration form says when a username or e-mail address already exists, and the published realm either accepts that or closes it.
  - The same default `VERIFY_EMAIL` action, and redirect URIs that allow any path (`/*`), since the sign-in now returns to the page it left.

## Alternatives

- **Keep the token in the address until the page has accepted it.** Rejected: the address with the token would be in the history, sent to Keycloak as the `redirect_uri` and readable by every script for the whole round trip.
- **`localStorage`.** Rejected: shared by every tab and kept after the browser closes, so a token not used would stay on the machine.
- **A preview of the pharmacy before accepting.** Refused by the owner for MVP 1 (2026-11-22): a read-by-token endpoint would tell anyone holding the link, a forwarded one included, which pharmacy it is.
- **`verifyEmail: true` for the whole realm.** Rejected: it would ask the imported `unverified` user to verify as well, and #10's tests mint that user's token with a password grant. The default required action asks only accounts created after the import.

## Consequences

- Every deep link survives sign-in, not only the invitation's; a published realm's client must allow redirect URIs below the web app's root (#114).
- A token is lost when the visitor completes the verification in another tab or browser; the page then says to open the link from the mail again.
- **An existing local Keycloak keeps the old realm.** Keycloak imports `realm.json` only when the realm does not exist yet, and keeps it in the data volume `<apphost>-keycloak-data`. A Keycloak started before this change does not allow registration until that volume is removed (README, Local users).
- Keycloak's registration page is in English; translating it is a theme, not part of this decision.
