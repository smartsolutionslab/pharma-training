# 0016: Lost appends to a stream answer 409 through the use case

**Status:** Accepted (#40); amended for #277: a sweep announces a stored completion or pass whose announcement never left; amended for #307 (owner decision of 2026-11-24, option A): Assessment's failures and locks are swept the same way.

## Context

- An event-sourced use case loads an aggregate from its stream, checks a rule on what it loaded and appends the events it raised at the version it loaded (`MartenAggregateStore.SaveAsync`: `Append(id, version + n, events)`). Two requests that load the same version both pass the check on their own snapshot; Marten's expected-version check lets the first append land and refuses the second.
- Learning's progress reports (#40) race like that by design: the player reports on pause, at a chapter's end and every 30 s, from more than one device. Two reports that each complete the last open chapter would otherwise both raise `ContentCompleted`, and Assessment would hear of one completion twice in a cycle.
- The fabric ADR `docs/adr/fabric/module-event-store-marten.md` keeps a lost append at `500` unless the use case opts in. ADR 0002 decided the same question for EF Core row versions: a lost race the use case expects is a `Result` failure mapped to the module's own `409`, with no exception handler. AGENTS.md (Event store: Marten) asks for it too: "a save that lost a race fails, and the command reports it rather than retrying silently".
- Observed before the change (T4 of #40): twenty concurrent reports on one session through the edge answered `500` (`Concurrent_reports_on_one_session_answer_200_or_409_and_never_500`).

## Decision

- **`MartenAggregateStore.TrySaveAsync(IEventSourced, CancellationToken)`** (`src/BuildingBlocks/EventStore/`) saves like `SaveAsync` and answers how the append lost the race (`Result<Unit, LostRace>` since #384, below). Nothing is stored then (the session's transaction, with the inline projections' writes, rolls back) and the aggregate is not marked stored. It counts as a lost race:
  - `JasperFx.Events.EventStreamUnexpectedMaxEventIdException`, Marten 9.59's refusal of an append whose expected version the stream has moved past;
  - a PostgreSQL deadlock (`40P01`) or serialization failure (`40001`) anywhere in the exception's tree, as `ModuleUnitOfWork.TryCommitAsync` does (ADR 0002), since the inline projections' upserts share the append's transaction.
  - Not `ExistingStreamIdCollisionException`: two first starts of one session stay the host's `409 already-exists` (ADR 0010).
- **A module opts in** by declaring `Task<Result<Unit, LostRace>> TrySaveAsync(IEventSourced aggregate, CancellationToken cancellationToken)` on its own `I<Module>AggregateStore`, which the store's public method implements. `IAggregateStore` is unchanged, so a module that does not opt in, and its test doubles, are unaffected; its `SaveAsync` still lets a lost append through as a `500`, a race nobody expected.
- **Learning opts in for progress reports.** `ReportProgressHandler` maps a lost race through `LearningSessionFailures.LostRace`: a moved stream to `learning.session-changed` (`409`), a deadlock to `learning.concurrent-save` (`409`, since #384), and publishes nothing. The server does not retry; the client reports again, which is always safe because a report at or below the stored progress stores nothing.
- **No exception handler maps the race**, as in ADR 0002.

## Decision (#384): a deadlock is a concurrent save, to try again

This amends the section above, as ADR 0002 was amended for the EF Core modules with #336.

- **How a race was lost.** `MartenAggregateStore.TrySaveAsync` returns `Result<Unit, LostRace>` (`src/BuildingBlocks/Messaging`), no longer `bool`, and a module declares `Task<Result<Unit, LostRace>> TrySaveAsync(...)` on its `I<Module>AggregateStore`. `VersionMovedOn` is an append Marten's expected-version check refused (`EventStreamUnexpectedMaxEventIdException`): another append landed on the stream since it was loaded. `SaveDeadlocked(SqlState)` is a 40P01 or 40001 anywhere in the save, where the inline projections write in the same transaction; Marten 9.59 throws a 40001 as `ConcurrentUpdateException` and a 40P01, after its own retries, as `MartenCommandException`, each around the `PostgresException`. A deadlock beside a moved stream counts as the deadlock. The save is one transaction with nothing after its commit, so only a failure before it is classified.
- **The answers.** Each module maps the union with a switch without a discard arm: a moved stream keeps its changed code (`learning.session-changed`, `assessment.examination-changed`), meaning load again; a deadlock answers `409 learning.concurrent-save` or `assessment.concurrent-save`, meaning try again, since nothing was stored and what the caller loaded may still be current. A deadlock is logged as a Warning naming its SqlState, with the `PostgresException` attached.
- **The clients send it again.** The progress reporter sends a `concurrent-save` once more, as it does a changed session. The answer saver sends it again up to 3 times, as it does `examination-changed`, but only after `concurrentSavePause` (200 ms), since Marten has already retried the deadlock: at most 16 database attempts for one answer (Marten's 4 for each of the saver's 4 sends). Nothing of a refused save was stored, so a resend applies once.

## Decision (#277): a lost announcement is announced again

- **The marker.** Each module that announces a stored event records it in `announced_events` (`stream_id`, `stream_version`, `announced_at`; primary key on the first two), in the same outbox commit as the announcement. `stream_version` is Marten's version of the event in its stream, counted from 1: the aggregate's version before the save plus the event's place among the pending events. Learning records each `ContentCompleted` it announces as `ContentCompletedV1` (`ReportProgressHandler`). Assessment records every event a submit stores (`SubmitAttemptHandler`, #307): the `AttemptSubmitted`, announced as `TestFailedV1` when it failed, and the `ExaminationPassed` (`TestPassedV1`) or `ExaminationExhausted` (`AttemptsExhaustedV1`) that may follow it. A passed `AttemptSubmitted` is announced by its `ExaminationPassed`; its marker only keeps the sweep of failures from reading it. A marker exists exactly when the envelope committed, and a committed envelope is delivered by Wolverine's outbox.
- **The sweep.** Every `Interval`, each service sends its module's sweep commands (`ReannounceContentCompletions`; `ReannounceTestPasses`, `ReannounceTestFailures` and `ReannounceExhaustions`, #307) through a `PeriodicCommandService` each (`src/BuildingBlocks/Messaging/`). Each command sweeps one stored type, and all of them run one `AnnouncementSweepPass` (`src/BuildingBlocks/Messaging/`, #307), so the rules below hold for every type. A pass announces every stored `ContentCompleted` (`ExaminationPassed`, `AttemptSubmitted`, `ExaminationExhausted`) stored between `Lookback` and `GracePeriod` ago that has no marker, oldest first and at most `BatchSize` a pass, with the handler's own mapping (a failure and a lock are mapped with their examination, read from its stream up to the event, for the attempt's number and the course), records the marker, keyed on the stream the event is stored in (`mt_events.stream_id`), in the same commit, one commit per event, and logs a Warning naming the type, the stream and the version. A passed `AttemptSubmitted` found without a marker (its submit's commit was lost, and the sweep of passes announces its `ExaminationPassed`) is settled with its marker alone, in a commit of its own, announced and logged by nothing, and counts towards the batch like an announcement. An event that cannot be loaded or mapped is skipped: it gets no marker, so later passes try it again until it leaves the lookback. A pass logs the events it skipped once, as one Warning naming how many, the first and the last of them by stream and version, and the type of the first failure (`FirstFailureType`; `UnreadableEvents`, `src/BuildingBlocks/Messaging/`, #360), not one Warning per event, which at `MostEventsPerPass` would be up to 1,000 a pass on every replica every interval; it logs it also when a database failure then ends the pass. The Warning names the failure by its type alone and attaches no exception, as the per-event Warning did before it: a message about the stored data, a deserializer's or a mapping guard's, may quote it, and it is about a learner, so it does not belong in the logs; the stream and version find the event for whoever needs the full failure. A database failure is no unreadable data: it ends the pass, which the `PeriodicCommandService` logs as an Error. That includes a failure once Marten's command runs (a dropped connection, a command timeout), which Marten wraps in a `MartenCommandException`; the finders hand the sweep the `DbException` it wraps (`MartenDatabaseFailures`, #337), so the Application stays free of Marten. A pass reads a page of `BatchSize` events at a time, each page after the last event the one before held in Marten's sequence (`seq_id > @after`, #337), so it reads on past the events it skipped; it stops once it has announced `BatchSize` events, at the end of the window, after `MostPagesPerPass` (10) pages, or once it has read `MostEventsPerPass` (1,000) events, the last page asking only for what is left of them (#351), so that at the largest batch a pass costs each replica at most 1,000 loads, not 10,000. Raising `BatchSize` therefore no longer lets a pass read past more unreadable events than `MostEventsPerPass`: it only fills the same 1,000 rows in fewer pages. So skipped events hold up the events behind them only when as many of them as a pass reads (`MostPagesPerPass` batches, at most `MostEventsPerPass`) or more lie at the old end of the window, and then until they leave the lookback; every pass meanwhile logs its one Warning for them. The query (`UnannouncedEvents`, `src/BuildingBlocks/EventStore/`) reads the window through a partial index on `mt_events(timestamp)` for the swept type (`ix_mt_events_<type>_timestamp`), which the MigrationRunner makes right after Marten's own tables and Marten is told to leave alone; without the index, a pass that finds nothing, the normal case, would read the whole event table on every replica every interval. The runner builds it concurrently (`create index concurrently if not exists`, without a command timeout, #337), so on a large event table the appends of replicas still running during a rolling deploy are not held up for the build, as a plain build's SHARE lock would; a concurrent build that failed leaves an invalid index of the name behind, which the next run drops (`drop index concurrently`) before it builds it again. The build has no time limit, but its lock waits do (#351): its connection sets `lock_timeout` (the runner's setting `Migrations:IndexLockTimeout`, 30 s by default, #359; see below), so a writer or a session left idle in a transaction with an older snapshot fails the run on the lock timeout, logged after a line naming the index, instead of holding the new revision's init container for good. The server should also set `idle_in_transaction_session_timeout`, which ends a forgotten session at its source, so it neither fails the run nor holds back vacuum or the sweep's own snapshots meanwhile. A second replica's runner waits at the migration gate by polling, never in a statement the build would wait for, and logs once that it waits (ADR 0005). The settings, keyed by the sweep's command so that modules sharing a container never read each other's, are read once at startup from `<Module>:AnnouncementSweep` (Assessment's three sweeps read the one section, each on its own interval); a bad value stops the host:

  | Key | Default | Accepted |
  | --- | --- | --- |
  | `Interval` | `00:01:00` | `00:00:01` to `01:00:00` |
  | `GracePeriod` | `00:02:00` | `00:00:01` to `01:00:00` |
  | `Lookback` | `7.00:00:00` | `01:00:00` to `90.00:00:00`, and longer than `GracePeriod` |
  | `BatchSize` | `100` | `1` to `1000` |

- **The index's lock timeout** (#359). The MigrationRunner reads `Migrations:IndexLockTimeout` (`IndexLockTimeout`, `src/BuildingBlocks/EventStore/`) once as it starts, before it migrates anything: blank or absent, it is `00:00:30`; it accepts `00:00:01` to `01:00:00` in the same format as the sweep's durations, and any other value fails the run, naming the key and the value. Zero is refused because PostgreSQL reads a `lock_timeout` of zero as no bound. It bounds each lock wait of the index's build and of the drop of an invalid one, not the build itself. Backups and long reports trip it too, not only forgotten sessions: a `pg_dump` (one repeatable-read transaction) or a long reporting transaction that overlaps a rollout holds a snapshot older than the build's, so the run fails on the lock timeout after a full build of the index, and leaves it invalid. The next run's `drop index concurrently` then waits for the same snapshot, so the init container fails and retries until the dump or the report ends, and the rollout can pass its deadline meanwhile. Where such transactions are expected during a rollout, raise the setting for that rollout rather than run without a bound.

- **The window, at best and otherwise.** A lost announcement leaves within `GracePeriod + Interval` (3 minutes by default) only at best. The window grows, up to the `Lookback` (7 days by default), after which the event is never announced, when:
  - more than `BatchSize` events are unannounced at once: the rest wait a further `Interval` per batch;
  - passes keep ending on a database failure: nothing is announced until one succeeds;
  - no replica sweeps: every service of the module is down, or none has started its sweep;
  - `MostPagesPerPass` full pages (at most `MostEventsPerPass` events) of unreadable events lie at the old end of the window: the events behind them wait until those leave the lookback.
- **Exactly once.** The marker's primary key lets one of the handler, the sweep and every replica's sweep commit an event's announcement; the others roll back with their envelope, and a pass that loses so (a unique violation of `pk_announced_events`, and of no other constraint) is logged at Information. No lock and no leader election.
- **No order between the sweeps** (#307). A submit that fails the last attempt stores `AttemptSubmitted` and then `ExaminationExhausted`, and publishes `TestFailedV1` and `AttemptsExhaustedV1` in one commit, in the order the stream holds them (`SubmitAttemptHandler`). The sweeps of failures and of locks run independently, each on its own interval and timer, so after a lost commit `AttemptsExhaustedV1` can leave before the same attempt's `TestFailedV1`, or a pass later. Nothing relies on the order today, since `TestFailedV1` has no consumer. A future consumer of both must not assume that a lock arrives after the failed attempt that caused it.
- **Why a re-announce's fresh `OccurredAt` is safe.** A re-announce is a new publish: `IntegrationEventMetadata` gives it a new `EventIdentifier` and `OccurredAt` = the sweep's now, and `ContentCompletedV1` carries no time of its own (`TestPassedV1` keeps the stored `PassedAt`).
  - Assessment (ADR 0012) unlocks an exhausted examination only on a completion later than the exhaustion. While a completion is unannounced, Assessment has not seen it, so that cycle's examination stays unopened or locked, and the later `OccurredAt` opens or unlocks it as the original would have. There is one narrow case where it does not (#337): cycle 2's completion is stored at T1 and its announcement lost; the learner completes cycle 3 at T2, announced as usual, which unlocks the examination; the learner uses up its attempts at T3; the sweep announces cycle 2's completion at T4. Assessment then unlocks the examination once more, since T4 is later than the exhaustion, where the stored order (T1 before T3) would leave it locked: the learner gets one more set of attempts without working through the content again. This is accepted, as the Compliance case below: it needs a lost announcement and then a whole further cycle completed and exhausted within the window, `GracePeriod + Interval` (3 minutes by default) at best (see the window above), and the completion it rests on is real, only earlier than it now appears.
  - Compliance (ADR 0023) keeps, per learner and course, whichever completion or lock is latest by `OccurredAt`. There is one narrow reorder: session A's completion is stored at T2 and its announcement lost; session B of the same course, on another version, is exhausted at T3; the sweep announces A's completion at T4. Compliance then ends Available where the stored order ends Locked. This is accepted: at T4 Assessment opens A's examination, so Available is what the learner can in fact do, the window is `GracePeriod + Interval` at best (see the window above), and it needs a lost announcement and a second session of the same course within it.
  - Learning (ADR 0025) notes each `AttemptsExhaustedV1` by its `EventIdentifier`, and Compliance (ADR 0023) keeps the latest lock or unlock by `OccurredAt` (#307). A re-announced lock carries a new identifier and the sweep's time, but it is the only announcement of that lock that ever left, because the marker refuses a second, so Learning notes it once, as it would have noted the original. Compliance has one narrow reorder, accepted by the owner on #307: session A's lock is stored at T1 and its announcement lost; the learner completes the content of session B of the same course (another version) at T2, announced as usual, which unlocks; the sweep announces A's lock at T3. Compliance then ends Locked where the stored order (T1 before T2) ends Available, until the learner's next completion or lock. It needs a lost announcement and a completion of a second session of the same course within the window, `GracePeriod + Interval` (3 minutes by default) at best. A lock cannot be overtaken in its own session: Learning reopens its chapters only once it hears of the lock, so no completion of that session can follow it before the sweep announces it. `TestFailedV1` has no consumer; it carries no time of its own.
  - This holds only because the sweep re-announces nothing that left, which the marker and the backfill guarantee; see the next point.
- **Why not re-announce every terminal event in a window** and rely on the consumers' idempotency: a re-announce is a new publish under a new `EventIdentifier` and a later `OccurredAt`. Assessment unlocks an exhausted examination on a completion later than the exhaustion (ADR 0012), and Compliance's register keeps the latest completion or lock (ADR 0023); both would be misled by a second announcement of a completion that did leave. It would also announce every terminal event on every tick.
- **Why not Wolverine's envelope storage:** a sent envelope's row is deleted once the broker took it, and both announcements leave the service, so "no envelope" means both "sent" and "never stored".
- **Backfill.** The migration that adds `announced_events` (`AddAnnouncedEvents`, in each module) marks every terminal event already stored as announced, because the store cannot tell a lost announcement from a delivered one. A completion or pass lost before #277 stays lost. Assessment's `AddAnnouncedFailuresAndExhaustions` (#307) does the same for every stored `AttemptSubmitted`, passed or failed, and `ExaminationExhausted`; a failure or lock lost before #307 stays lost. A submit that a replica of the old revision stores while the new revision's migration has already run (a rolling deploy) carries no marker for its failure or lock, so the new sweeps announce it a second time after the grace period, and Learning counts a second lock. The same holds for #277's completions and passes, stored by a revision from before #277. A lower bound on the sweeps at the backfill's instant does not close it: the backfill marks every such event stored before it, so the unmarked ones an old replica stores all lie after that instant, inside the window; only the instant the last old replica stopped would bound them, and no migration knows it. Telling the new revision's events apart (a Marten header the new submit writes and the sweeps require) would close it, but it needs Marten's event headers turned on and a change to every sweep's query and partial index, for a gap that exists only while a revision without the marker still runs, once per environment. The release checklist closes it instead (README, "Deploy a release that adds a marker"): such a release is deployed while nothing is submitted, and the sweeps' Warnings are checked for events the old revision stored once it is gone. An environment that never ran a revision without the marker, such as one deployed for the first time with it, has no gap.

## Consequences

- Of any reports racing on one session, one append lands, so each chapter completes and the content completes at most once per cycle, and only the winner publishes `ContentCompletedV1`.
- The announcement (`ContentCompletedV1`, and `LearningSessionStartedV1` for a new session) is committed to the outbox in a second transaction after the append, and the request's cancellation no longer reaches it: a caller who goes away after the save does not lose it.
- A crash or failure between the append and the outbox commit delays `ContentCompletedV1`, `TestPassedV1`, `TestFailedV1` or `AttemptsExhaustedV1` by `GracePeriod + Interval` (3 minutes by default) at best, and up to the `Lookback` in the cases the window above names, logged as a Warning per re-announced event. The request that failed still answers `500`, as before.
- `LearningSessionStartedV1` (Learning) is still announced in a second transaction without a marker; a crash there still loses it. Since #307, Assessment's `TestFailedV1` and `AttemptsExhaustedV1` are swept like a pass, so a lost lock no longer leaves the learner locked without Learning or Compliance hearing of it.
- Publishing from what the stream stored (Wolverine's Marten outbox or a Marten subscription, in the append's own transaction) would remove both the gap and the sweep; it stays the alternative, a decision of its own.
- In the rare case where the sweep commits first and the handler's late commit hits the marker, that request answers `409 already-exists` although its change and announcement stand; the grace period makes this practically unreachable.
- A learner's client sees an occasional `409 learning.session-changed` when two of its reports overlap, or `409 learning.concurrent-save` when their saves deadlock (#384); it reports again.
- Assessment's SubmitAttempt opted in the same way with #271 (`assessment.examination-changed`).
- A Marten upgrade may rename the refusal's exception; the integration test above fails with a `500` if it does.
