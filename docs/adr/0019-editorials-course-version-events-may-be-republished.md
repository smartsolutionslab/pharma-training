# 0019: Editorial's course-version events may be republished; consumers deduplicate on the version id

**Status:** Accepted (#189); amended for #264: the republish releases a published version's chapter files again, with read URLs signed when it runs.

## Context

- Editorial announces a course version with `CourseVersionPublishedV1` and `TestDefinitionPublishedV1` when it is published, and with `CourseVersionRetiredV1` when it is retired. Each event goes to a fanout exchange named after its type (ADR 0011), and the broker drops an event when no queue is bound to that exchange.
- A service's queue is bound only from its first start. A service that consumes these events and is deployed after they went out (Certification, Assessment) never receives them, and has no copy of the versions published before it.
- The fabric ADR `module-communication-integration-events` tells consumers to deduplicate on `Metadata.EventIdentifier`. An event sent again gets a new identifier, so a consumer that followed that rule alone would apply it twice.
- A published version never changes: every content method refuses anything but a draft. Mapping the stored version again yields the payload it was announced with.

## Decision

- **The command.** `POST /editorial/course-versions/republish` (`RepublishCourseVersions`) sends again, through Editorial's own unit of work and broker user, the events of every course version Editorial announced.
- **What is selected.** A version with `PublishedAt` set gets `CourseVersionPublishedV1` and then `TestDefinitionPublishedV1`, and, when it has PDF or video chapters, `ChapterFilesReleasedV1` (#264); one with `RetiredAt` set gets `CourseVersionRetiredV1`. `Publish` and `Retire` set those fields in the save that stored the events, so they mark exactly what was announced. The selection is never by status: a row marked published any other way was never announced, and its consumers might refuse it.
- **The order.** By course id, then by version number; within a version, published, test definition, file release, retired, as they first went out. The order is best effort: one queue is delivered in parallel (ADR 0015), and no consumer may rely on it.
- **One commit per version.** Each version is loaded, its files signed, its two to four events published, and that version committed, so a transaction holds one version's content and a version's events stay together. Nothing tracked changes, so the commit cannot lose a race (ADR 0002); a commit that fails answers 500, and what was committed before it stays sent.
- **The files' read URLs are signed when the republish runs (#264).** A URL a release carries is a bearer credential that lives fifteen minutes (docs/adr/0002), so the ones first released are long expired and none is stored. The republish signs each version's URLs the way the publish does, through the same helper (`ChapterFileReadUrls.SignReadUrlsAsync`: `BlobUrlLifetime.Maximum`, `inline`, the kind's type), before the version's first event is published, since the outbox opens a transaction on the first publish. So a republished release differs from the original in its URLs and expiries, not only in its metadata; the files and chapters it names are the same, since a published version never changes. Superseded and retired versions are released too, as they were when published: a learner may still have a session on one.
- **`200` with counts.** The answer is `EditorialRepublishedEventsDto(CourseVersions, TestDefinitions, FileReleases, Retirements)`; `FileReleases` counts the versions whose files went out, one per version with PDF or video chapters (#264); the events are in Editorial's durable outbox when it answers, and the counts tell an operator whether anything went out. An empty catalogue answers `200` with four zeros.
- **`editorial.edit`.** The policy of publishing and retiring, whose announcements it repeats. It creates no fact and reveals nothing an editor cannot read already; its worst misuse is load that every consumer drops after one key lookup. `editorial.manage` is the module's sample policy and grants nothing editorial.
- **The rule for consumers.** A consumer of `CourseVersionPublishedV1`, `TestDefinitionPublishedV1` or `CourseVersionRetiredV1` deduplicates on `CourseVersionId`, against an insert-only copy whose key is that id, and reads nothing from `Metadata`. Catalog, Compliance, Learning and Certification already do; Assessment's consumer (#45) does too.
- **The rule for `ChapterFilesReleasedV1` (#264).** Learning, its only consumer, keeps no URL, expiry or row from it: it copies each file into its own container under the name `ChapterMedia.NameFor` derives from the version and the chapter, and a blob already under that name counts as copied (`BlobCopyOutcome.AlreadyThere`, docs/adr/0002). That name is the deduplication, never `Metadata.EventIdentifier`, which a republish renews. A release copies from its own URLs; whichever release copies a file first wins, and every later one, newer or older, finds it there and changes nothing. No order between releases is needed, since every release of a version names the same immutable files: an older release delivered after a newer one either finds the file copied or, its URLs expired, fails and is retried and dead-lettered, which leaves what the newer one copied as it is. Learning signs its learners' URLs on its own copy when they ask (`GET /learning/media/{chapterId}`), so no URL Editorial released outlives the copy.

## Consequences

- The republished payload follows the current mappings: if a mapping or `EditorialIntegrationEventMappings.MaxAttempts` changes after a version was published, its republished events carry the new shape. Every consumer keeps the copy that arrived first, so nothing already stored changes.
- Every subscriber receives a run, not only the one that was missing the events, and drops what it already has by version id.
- A run cut off part-way is simply run again.
- A file Learning never copied, because it was deployed after the publish or its first release expired before it copied (docs/adr/0002, #227), is copied from the next republish's release; one it holds is left as it is. A republish signs one read URL per file chapter of every published version Editorial holds, in run mode without I/O; deployed, signing may ask for a user delegation key (about once an hour), so a storage or identity outage fails the republish with 500 part-way, which a rerun completes.
- The republished URLs are bearer credentials for Editorial's blobs, in its outbox until sent and in a dead letter if a copy fails, worthless fifteen minutes after the republish; every subscriber of the exchange receives them, as it receives a publish's.
- A consumer of these events added later, in Certification or any other module, is bound by the rule above.
- `0016` was held by #206, and `0017` or `0018` might be taken by #194, when this was written. If `0019` is taken by the time #189 merges, this file and every reference to it (`RepublishCourseVersions`, its handler and endpoint, the three contracts' docs and the README) are renumbered.
