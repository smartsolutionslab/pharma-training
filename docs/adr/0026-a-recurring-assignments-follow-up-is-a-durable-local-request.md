# 0026: A recurring assignment's follow-up is a durable local request

**Status:** Accepted (#31). The owner-side default on #31 stands: a retired course still gets its follow-up.

## Context

- An assignment with a `RecurrenceInterval` (the yearly hygiene briefing) must be followed by a new one once it is completed: due one interval after the completion's day in Germany, the day the certificate runs out (domain README, Assignment). `Assignment.FollowUp` builds that next assignment, but nothing called it, and nothing recorded which assignment a follow-up follows, so a redelivery could not be recognised.
- `CertificateIssuedV1Consumer` completes the assignment and announces `AssignmentCompletedV1` in one commit. The partial unique index `ux_assignments_active_learner_pharmacy_course` forbids putting `Complete` and the follow-up's `Add` into one save: the completed row leaves the index while the follow-up enters it, and EF Core may run the INSERT first.
- A domain-event reaction runs after the commit, once: a failure is logged and nothing retries it (AGENTS.md, Module style DDD: "Work that must not be lost … is an integration event, not a domain-event reaction"). A lost follow-up silently ends a legal training obligation.
- ADR 0004 replaced a reaction that lost mail with `InvitationMailRequestedV1`, a module's own request it publishes in the same commit and consumes itself from the host's durable local queue.

## Decision

- **D1. A local request, not a reaction.** For a recurring assignment, `CertificateIssuedV1Consumer` publishes `AssignmentFollowUpRequestedV1(AssignmentId)` next to its `AssignmentCompletedV1`, before the same `CommitAsync`. A one-off assignment, and a completion the assignment refuses, request nothing. A module of the host both publishes and consumes the type, so `src/Host/Wiring/Messaging.cs` keeps it off the broker (no exchange, sender or binding) and Wolverine routes it to the durable local queue: saved with the completion, retried 1…32 s, then dead-lettered in `wolverine.wolverine_dead_letters`. No routing is written by hand. It carries the completed assignment's id only.
- **D2. `AssignmentFollowUpRequestedV1Consumer` creates the follow-up once.** In this order: it guards the id; reads the completed assignment (`IAssignmentStore.ReadAsync`) and throws `InvalidOperationException` when it is missing; returns when a follow-up of it exists (`HasFollowUpAsync`); skips, with an Information log of ids only, a learner who is no longer an active member of the pharmacy, and a learner who already has an active assignment of the course there; throws `InvalidOperationException` when `FollowUp` returns none (a one-off or not completed assignment is never requested a follow-up, so that is a bug or a forged message); otherwise adds the follow-up, announces it as `CourseAssignedV1` as `AssignCourseHandler` does, and commits.
- **D3. The idempotency key is `follows_assignment_id`.** `Assignment.Follows` (nullable, column `compliance.assignments.follows_assignment_id`) names the assignment a follow-up follows; one assigned by hand has none. The rule "one follow-up per assignment" is backed twice: `HasFollowUpAsync` in the consumer, and the unique index `ux_assignments_follows_assignment_id` (PostgreSQL counts NULLs as distinct). Two deliveries that race both insert; the index, or the active-assignment index, refuses the second, which throws and is retried, and the retry finds the follow-up. The consumer never catches that exception. It does not deduplicate on `Metadata.EventIdentifier`: the state key also absorbs a re-publish under a new identifier.
- **D4. The follow-up.** Same learner, pharmacy, course and recurrence; `AssignedBy` is the predecessor's assigner, since the obligation stays the manager's and there is no "system" person. Due on the German day of the predecessor's `CompletedAt` plus the interval in months, a day the shorter month lacks becoming its last day. `AssignedAt` is the consumer's clock, never earlier than the predecessor's `CompletedAt`.
- **D5. A follow-up refuses a certificate issued at or before it was assigned** (`CertificatePredatesAssignment`); an assignment made by hand keeps refusing only one issued before. With D4 the certificate that completed the predecessor can never complete its follow-up, whatever Certification's and Compliance's clocks say, so a redelivered `CertificateIssuedV1` neither completes the follow-up nor requests another: no chain.
- **D6. A retired course still gets its follow-up.** The README states the rule without exception and ADR 0007 says retiring breaks nothing. A course may be retired for a while before its next version is published; skipping the follow-up then would end the recurrence for good without anyone noticing. A follow-up that cannot be started yet shows as Open, later Overdue, and a manager can withdraw it. The consumer therefore asks no course store.
- **D7. The learner left: no follow-up.** A follow-up for someone who has left the pharmacy would be cancelled by the rule that cancels open assignments on leaving; when that sweep has already run, nothing would cancel it anymore. This mirrors `AssignCourseHandler`'s `LearnerNotAMember`.
- **D8. The learner already has an active assignment of the course: no follow-up.** The obligation is already open (a manager assigned it again in between), and inserting would hit the active-assignment index on every retry and end in a dead letter.

## Rejected

- **A. `IDomainEventReaction<AssignmentCompleted>`.** Smallest, but not durable: a crash or failure between the commit and the reaction loses the follow-up for good.
- **B. The follow-up's `Add` in `CertificateIssuedV1Consumer`'s own unit of work.** One `CommitAsync` is one `SaveChanges`, which the index constraint above forbids; two saves in one transaction would need a transaction API `IComplianceUnitOfWork` does not have.
- **C. Consuming Compliance's own `AssignmentCompletedV1`.** The host would then both publish and consume it, which takes it off the broker (ADR 0004: excluding a type removes its broker sender too), although it is a public event other services may bind to.

## Consequences

- One contract (`AssignmentFollowUpRequestedV1`, local to the Compliance service), one consumer, one nullable column with a unique index, and migration `AddAssignmentFollowsAssignment`. The broker's topology and the broker users (ADR 0011) do not change; `AssignmentCompletedV1` stays public.
- Accepted: a check-then-insert window remains between the consumer's membership check and its commit. A `MembershipEndedV1` whose sweep runs inside it leaves the follow-up active, as `AssignCourseHandler` already accepts; a manager withdraws it. Closing it would need a lock per learner and pharmacy across both consumers.
- Accepted: a request handled only after a dead-letter replay months later may make a follow-up due in the past, shown truthfully as Overdue. `FollowUp` does not refuse a past due date, because the obligation exists from the completion on.
- Numbering: `0026`, since `0024` and `0025` are held by other branches.
