# 0027: The certificate's PDF is rendered once, from a local message, and read through a signed URL

**Status:** Accepted (#50). Numbered 0027 because 0026 is taken by #51's open pull request; renumber at merge if the sequence on `main` differs.

## Context

- #49 issues a `Certificate` from `TestPassedV1` with `Document = Pending` and an `AttachDocument` that keeps the first reference. #50 asks for its PDF to be rendered "by a reaction", stored once, never re-rendered, and served to its holder.
- AGENTS.md (Module style: domain-driven design): a domain-event reaction that fails is logged and never retried, and "work that must not be lost … is an integration event, not a domain-event reaction". A PDF lost that way would leave the certificate `Pending` for good, and the export (Z3) without its document. ADR 0004 replaced exactly such a reaction for the invitation mail.
- ADR 0002 gives each module its own container, signs short-lived read URLs and keeps files from streaming through a service host. There was no server-side write: `IBlobUrls` signs, `IStoredBlobs` reads, `IBlobCopies` copies.
- The domain (`docs/domain/README.md`) fixes the PDF's content: name, course and version, date, result, valid until, a QR code for verification, and no pharmacy. The PDF is evidence for German inspections.
- PDFsharp changed its licence: 6.2.4 is the last MIT release; 6.5.0 and 7.0.0-preview-2 (2026-10-14) are AGPL-3.0-only on nuget.org, which does not fit a closed SaaS. QuestPDF's Community licence has a revenue cap, and PdfSharpCore depends on SixLabors ImageSharp, whose Split licence has one too.

## Decision

- **Rendering is requested in the issuing commit, as a local message.** `TestPassedV1Consumer` publishes `CertificateIssuedV1` and `CertificateDocumentRequestedV1(Guid CertificateId)` (`src/Contracts/Certification`, ids only) through `ICertificationUnitOfWork` before `CommitAsync`, so a refused commit sends neither. Certification both publishes and consumes the request, so `src/Host/Wiring/Messaging.cs` (`LocalMessageTypes`) keeps it on the host's durable local queue and off the broker, as it does `InvitationMailRequestedV1`. `CertificateIssued` keeps `[DeliberatelyUnhandled]`, with the reason updated. This deviates from the issue's wording "a reaction" on purpose.
- **`CertificateDocumentRequestedV1Consumer` renders once and writes create-only.** It guards the id by its name, loads the certificate tracked (`ICertificateStore.LoadAsync`; a missing one throws, since it was saved in the same commit), and returns for a `Stored` certificate without rendering or writing: a stored certificate is never rendered again. Otherwise it builds the verification link (`IFrontendLinks.LinkTo("/verify/{code}")`, before rendering, so a missing `Frontend:BaseUrl` fails before anything is written), lays out `CertificateContent` from the certificate's snapshot alone (`ICertificateRenderer`), writes it with `IBlobWrites.CreateAsync` to `certificates/{id:D}.pdf` (`CertificateDocuments.NameFor`) as `application/pdf`, attaches it and commits. A blob already under the name (an earlier attempt that wrote and then lost its commit, or a parallel delivery) is kept and attached as it is: the first bytes stored win. Anything else throws, so Wolverine retries (1 to 32 s) and dead-letters it; a replay is idempotent through the state check and the create-only name.
- **`IBlobWrites` (ADR 0002, amended)** puts a blob with `If-None-Match: *`; 409 `BlobAlreadyExists` and 412 `ConditionNotMet` are `AlreadyThere`.
- **The version number joins the snapshot.** `CourseVersionPublishedV1Consumer` keeps `VersionNumber` (at least 1) on Certification's copy as `CourseVersionNumber`, and `Certificate.Issue` takes it beside the title. Migration `KeepCourseVersionNumbers` adds both columns, existing local rows set to 1 in the migration only. `CertificateIssued` and `CertificateIssuedV1` are unchanged.
- **The PDF (German, A4 portrait, one page)**: heading "Teilnahmebestätigung", the holder's name, "hat die Schulung „{Titel}“ (Version {n}) erfolgreich abgeschlossen." (wrapped), Datum (the issue instant's day in Germany), Ergebnis (`85 %`), Gültig bis (`dd.MM.yyyy`), and at the foot a QR code of `{Frontend:BaseUrl}/verify/{VerificationCode}` (about 35 mm, ECC Medium, a quiet zone of 4 modules, drawn as vector rectangles) with "Echtheit prüfen: {link}" below it. Metadata: Title "Teilnahmebestätigung", Creator "PharmaTraining", CreationDate the issue instant. No pharmacy, certificate id or person id is printed. German only, like the invitation mail (0004); the PDF is a document, not UI (0007).
- **Libraries.** PDFsharp 6.2.4 (MIT), pinned in `Directory.Packages.props`, with a Dependabot `ignore` on every update type. Net.Codecrete.QrCodeGenerator 3.2.1 (MIT, no dependencies) gives the module matrix. Both are referenced by `Certification.Infrastructure` alone.
- **Font.** Inter 4.1 Regular and Bold, static TrueType (`extras/ttf` of the official rsms/inter release `Inter-4.1.zip`), SIL Open Font License 1.1, which allows embedding in documents. They are committed with `OFL.txt` under `Certification.Infrastructure/Documents/Fonts/` as embedded resources; `.gitattributes` marks `*.ttf` binary. PDFsharp's Core build finds no system fonts on Linux, so `InterFontResolver` serves them, set once on `GlobalFontSettings.FontResolver` behind a static `Lazy`. The frontend's `@fontsource-variable/inter` is a variable woff2, which PDFsharp cannot use.
- **The holder reads it through a read URL.** `GET /certification/certificates/{id:guid}/pdf`, `.RequireAuthorization()`, reads the caller from the token's subject (`CertificationCaller`) and dispatches `GetCertificateDocument`, which answers, in this order: 403 `certification.identity-incomplete` without a person; 404 `certification.certificate-not-found` for an empty or unknown id and for someone else's certificate, pending or not, so nobody learns which ids exist; 409 `certification.document-not-ready` while the holder's document is pending; otherwise `CertificationDocumentUrlDto(Url, ExpiresAt)`, a five-minute read URL signed inline as `application/pdf` (`IBlobUrls`, ADR 0002). Nothing is signed for a refused caller. A GET renders nothing: a query never changes state, and the message with its replay is the retry path. A 302 redirect was rejected: a fetch with a bearer token loses `Authorization` on a cross-origin redirect.
- **The web app's address reaches Certification without mail.** A service host's project says `<LinksToFrontend>true</LinksToFrontend>` beside `<ModuleName>`; the AppHost gives such a host `Frontend__BaseUrl` alone, as it gives it with the mail settings to one that says `<SendsMail>true</SendsMail>`. No module is named in the AppHost. `CertificationModule` registers `IFrontendLinks` itself, without `AddModuleMail`'s SMTP settings.

## Consequences

- A certificate's PDF follows its issue within seconds; until then the holder's GET answers 409 and the page (Z6) asks again. A failure that outlasts the retries leaves a replayable dead letter in `wolverine.wolverine_dead_letters`; the certificate stays `Pending` until it is replayed.
- The PDF is rendered from the snapshot alone, so a later title, name or validity change never alters it, and it is never rendered again. Changing its layout changes only PDFs rendered afterwards.
- Rendering runs in the Certification host and holds one PDF (about 60 KB, the fonts subset) in memory; PDFsharp's font resolver is process-wide, and only Certification's host loads PDFsharp.
- Staying on PDFsharp 6.2.4 means no upstream fixes under MIT. If a security fix is ever needed, the fallback is replacing the library, a new decision. PDFsharp 6.2.4 brings `System.Security.Cryptography.Pkcs` 8.0.1 transitively; the project's restore audits it like any other package.
- Blobs are never deleted (retention and DSGVO deletion are #115); the export ZIP (Z3) reads the same blobs by `DocumentLocation`.
- `fabric upgrade` may conflict on `src/AppHost/AppHost.cs`, `src/AppHost/Wiring/ServiceHostProjects.cs`, `.github/dependabot.yml` and `Directory.Packages.props`; keep this decision's changes.
