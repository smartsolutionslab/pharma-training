# 0040: The erased person's Keycloak account is deleted by Organisation's service account

**Status:** Accepted (#115, slice 6). Completes ADR 0036. Relies on ADR 0004 (a durable local message), 0005 (secrets in the Key Vault, a realm imported once), 0011 (local messages stay off the broker) and 0014 (only a verified address proves the account). The owner's decisions A to D of 2026-11-25 (#115) are recorded below.

## Context

- An erasure (ADR 0036) forgets the person in every service, but until this slice their Keycloak account stayed: they could still sign in, and their name and address stayed in Keycloak.
- The person's `PersonId` is their Keycloak subject (`CallerClaims`, docs/domain/README.md), so it is the user's id in Keycloak's admin API, `/admin/realms/pharma-training/users/{id}`.
- Nothing in the application could call that API. The realms held the web and API clients alone; the staging test runner's `x1-runner`, which may manage users, is created by a runbook on staging and is never imported, so production never has it.
- Q5 of #115: a person Organisation holds no address for (they never accepted an invitation, or every membership was forgotten) got no confirmation at all (`NoAddress`), though their account usually has an address.

## Decision

- **A confidential client of its own, in both realms (decision D).** `pharma-training-erasure` is declared in `src/AppHost/realms/realm.json` and `src/AppHost/keycloak/realm.json` alike: `publicClient: false`, `client-secret`, the client credentials grant alone (`serviceAccountsEnabled`; no standard, implicit or password flow), its secret `${KEYCLOAK_ERASURE_CLIENT_SECRET}`, which Keycloak fills from its environment at the import. Its service account, `service-account-pharma-training-erasure`, holds `realm-management`'s `manage-users` alone, which lets it read users too, and has no credentials. An import grants a service account its client role only through a `users` entry, so it is the published realm's one user (`PublishedRealmTests`).
- **One secret, read by Keycloak and Organisation alone.** The AppHost's secret parameter `keycloak-erasure-client-secret` (`src/AppHost/Wiring/AccountDeletion.cs`) is generated once in run mode (32 letters and digits, kept in the AppHost's user secrets, so it needs no escaping in the realm's JSON or a form body) and is a Key Vault secret once published, which `publish.yml` and `deploy.yml` set from the environment's `KEYCLOAK_ERASURE_CLIENT_SECRET`. Keycloak reads it as `KEYCLOAK_ERASURE_CLIENT_SECRET`; a service host whose project says `<ManagesAccounts>true</ManagesAccounts>`, Organisation's alone, as `Keycloak__Accounts__ClientSecret`, beside `Keycloak__Accounts__Address` (Keycloak's internal `http` endpoint: the auth proxy forwards no `/admin`), `__Realm` and `__ClientId`. Published, `keycloak-identity` and `organisation-identity` alone are granted it (`AppHostSecretAccessTests`). **This secret administers every account of the realm**: whoever holds it may read, change and delete any user. It is kept as the database and broker credentials are, and rotated with the runbook (README).
- **Organisation deletes the account after it forgot the person.** `ErasureConfirmationMailRequestedV1Consumer` publishes the local `AccountDeletionRequestedV1(ErasureId, PersonId)` beside `PersonErasureRequestedV1`, in the commit that forgets the person. It never reaches the broker (ADR 0011). Its own consumer, `AccountDeletionRequestedV1Consumer`, then:
  1. returns at once when the erasure is unknown (logged by its id) or its step `keycloak` is recorded (`Erasure.HasCompleted`), so a redelivery asks Keycloak nothing;
  2. reads the account; a client's service account (`serviceAccountClientId` set) is never deleted: it logs an error by the erasure's id and records nothing, so support sees the step `keycloak` missing;
  3. deletes the account, where "not found" on the read or the delete counts as deleted, and records the step `keycloak` at Organisation's clock.

  Since it is a work item of its own, a Keycloak outage retries the deletion alone, never the mails or the forgetting before it.
- **The admin API through a typed client** (`Organisation.Infrastructure/KeycloakAccounts.cs`, `IAccounts` in Application). Each call mints a token with the client credentials grant at `{Address}/realms/{Realm}/protocol/openid-connect/token` and keeps none (erasures are rare), then `GET`s or `DELETE`s the user. Any answer but success or 404 throws `AccountsUnavailableException`, naming the step (`token`, `read`, `delete`) and the status, never the secret, a token, an address or Keycloak's answer. `Keycloak:Accounts` is validated at start-up, each failure naming its key, never its value. `OrganisationModule` registers it only where that section exists, which the AppHost gives the one host that manages accounts.
- **The token request gets one attempt (decision A).** It is a POST, so the host's pipeline does not retry it, and the client does not opt in with `RetryEveryMethod`, which no module project can reach. A transient failure throws, and Wolverine retries the whole consumer (1 to 32 seconds, then the dead letter, whose body holds two Guids), which is idempotent by the erasure's state. The read and the delete are retried by the pipeline.

## Consequences

- **The account's address is used for the mail alone (decision C), a known limit.** Organisation does not erase by it, as it does by the addresses it held itself: an open invitation a pharmacy addressed to it is not revoked, a membership that holds it keeps it, and its invitation recipient row stays. An invitation is keyed to an address, not to a person, and was the pharmacy's to send.
- **Tokens outlive the account.** Keycloak ends the account's sessions when it deletes it, but an access token already issued stays valid until it expires (the realm's access token lifespan), since the services validate tokens locally. That remaining lifetime is the window in which the erased person could still call the API; the tombstones of ADR 0036 keep their name from being written back where a call could carry it.
- **Keycloak's own event store.** The published realm records login and admin events with no expiry; a login event holds the user's id, username (the address) and IP, possibly after the user is deleted. Setting an expiry is #448, outside this slice.
- **A realm imported before this slice lacks the client.** Keycloak imports `realm.json` once (`IGNORE_EXISTING`, ADR 0005), so a deployed environment, or a local Keycloak volume, imported earlier has no `pharma-training-erasure`, and every erasure stops short of the step `keycloak` until it is created: by the README's runbook (kcadm.sh, then `KEYCLOAK_ERASURE_CLIENT_SECRET` set and a deploy), or locally by removing the volume. The dead-lettered deletions can then be replayed. Locally, clearing the AppHost's user secrets without removing the volume leaves the imported client with the old secret.
- **To check after the first deploy.** The token is minted at Keycloak's internal address, and published Keycloak's `KC_HOSTNAME` makes its issuer the one the admin API expects. An erasure of a throwaway account on staging that lists the step `keycloak`, with the account gone, confirms it.
- `GET /organisation/erasures/{id}` lists the step `keycloak` like any other; the DTO, the OpenAPI document and the error codes are unchanged.
